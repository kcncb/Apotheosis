## 2. 被控对象（Plant）

### 2.1 结构

严格照搬 `tests/aim_pid_test.cpp` 的既成模型（不另发明一套），只在域上对齐：

```
         u[n]          ┌─────────────┐   camera_px        e[n]
 e[n] ──►PID──► 计数 ──►│ 执行延迟 d_a│──►(+)──►(目标-镜头)──► 测量延迟 d_m ──►PID
                        └─────────────┘
                              ▲
                        ×k (像素/计数)
```

时间线（第 n 拍）：

1. 目标世界位置 `target_px` 演化（阶跃 / 匀速 / 正弦）；
2. 真实误差 `anchor_true = target_px - camera_px`；
3. 进 **测量延迟线**（`meas_ticks = round(d_m/dt)`）后作为 `anchor_meas` 交给控制器；
4. 控制器输出整数计数 `counts = pid.step(anchor_meas, dt)`；
5. 计数进 **执行延迟线**（`act_ticks = round(d_a/dt)`），出线后 `camera_px += counts*k`。

### 2.2 参数取值（全部有出处）

| 参数 | 取值 | 出处 |
|---|---|---|
| `dt` | 1/120 s = 8.333 ms | 由实机日志 5.00 Hz/200 ms 摆动反推为 24 拍（见 §3.2） |
| 死区合计 | 46 ms | `boss_aim.h.mojibake.bak:44` → `kAimDeadTimeS = 0.046`；`tests/aim_pid_quantum_test.cpp:41` |
| 死区拆分 | 测量 1/3 + 执行 2/3（≈15 / 31 ms） | `tests/aim_pid_test.cpp:68` 注释给的是 30+20；本方案按 1/3 与 2/3 拆分，**总滞后 46 ms 守恒**（拆分不影响稳定性结论，只影响 ±1 拍对齐） |
| `k` (px/count) | 0.593 | `CLAUDE.md` 亚量化条目实测 `k̂=0.593`；另扫 0.25 / 1.0 / 1.9 |
| 噪声 | σ = 0.06 px（高斯）+ 量化台阶 | `boss_aim.h:62`：「框心逐帧变化中位 0.06px, 偶发 1.9px」 |
| 限幅 | 200 计数/拍 | `aim_pid.cpp` `kDefaultLimitCounts = 200` |

> **关于死区拆分的安全性**：两段延迟串联，对回路的等效作用只取决于**总滞后**，
> 拆分方式不影响稳定性结论（只在采样对齐上有 ≤1 拍的差异）。方案默认
> 30+20，且把 **total = 46 ms** 作为鲁棒性测试的摄动对象。

### 2.3 工况（Q2 = A，三工况加权）

| 编号 | 工况 | 设定 | 权重 | 检验什么 |
|---|---|---|---|---|
| C1 | 阶跃甩枪 | 400 px 阶跃 | 0.5 | 超调、调节时间、瞬态 |
| C2 | 匀速横移（跟枪） | 300 px/s 目标速度 | 0.3 | 稳态滞后、积分作用 |
| C3 | 正弦机动 | 200 px 幅度、1.5 Hz | 0.2 | 相位滞后、持续激励下的抖动 |

加权 IAE：

```
J = 0.5·IAE_C1 + 0.3·IAE_C2 + 0.2·IAE_C3
```

权重取 0.5/0.3/0.2 的理由：阶跃是唯一能定义"超调/调节时间"的工况，且是
用户体感最强烈的（甩枪那一下），所以过半；跟枪是常态使用场景（0.3）；
正弦机动最容易暴露抖动与滞后，但它不是主要作战工况（0.2）。

## 3. 稳定性边界（本方案的核心论证）

### 3.1 离散积分 + 纯延迟的临界增益

被控对象含积分性质（计数累积成位移），回路为「离散积分 + 纯延迟 d 拍」，
临界每拍增益有闭式：

```
g_crit = 2·sin( π / (2(2d + 1)) )
```

其中每拍增益 `g = Kp·dt·k`（k = 像素/计数）。

注意此式对 **d 向上取整**（保守一侧）成立；用 floor 会低估延迟。

### 3.2 用实机数据反推 d，并交叉验证

`CLAUDE.md` 记录：Kp=100 时误差以 **5.00 Hz / 200 ms** 摆动，且
`g = Kp·dt·k = 0.494`。

- 摆动周期 = 200 ms = 24 拍（若 dt = 8.333 ms）→ 反推 `d = (24-2)/4 = 5.5 拍`
  → `5.5 × 8.333 ms = 45.8 ms` ≈ **46 ms** ✅ 与 `kAimDeadTimeS` 独立吻合；
- 校验临界值：`g_crit(5.5) = 0.2611`，`g/g_crit = 0.494/0.2611 = 1.89`
  → 与 `CLAUDE.md` 记载的「1.9 倍临界」**完全对上** ✅。

> 复算脚本 `tools/pid_sim/_verify_crit.py` 的输出见 §8。
> **结论：dt 取 120 fps 是被实机数据钉死的，不是估计值。**

### 3.3 由此得到的 Kp 天花板

| d（拍，向上取整） | `g_crit` | `Kp_crit` @ k=0.593 | `Kp_crit` @ k=0.25 |
|---|---|---|---|
| 5 | 0.2846 | **57.6** | 136.6 |
| 6 | 0.2411 | **48.8** | 115.7 |

即 **`Kp ≈ 49~58` 是纯失稳边界**（本机 k̂=0.593）。
这与实机观测「Kp=30 稳、Kp=100 抽」以及 Q3 选的 `[5, 60]` 三者一致。

**设计决定**：对 `g = Kp·dt·k` 加一条**显式安全裕度约束**：

```
g ≤ 0.6 · g_crit(d)        # 即至少 1.67 倍增益裕度
```

这样即使某个个体在 IAE 上"好看"，只要越过稳定裕度就判为不可行（罚死）。
**理由**：目标是交付到实机的参数，实机 k̂ 有不确定性，踩在 g_crit 上的解
在仿真里可能收敛、在机器上就是极限环 —— 这正是历史上 Kp=100 翻车的原因。

### 3.3.1 ⚠ 加了裕度之后，安全上限比失稳边界低一大截（实测修正）

这是本步**真实运行**发现的一个冲突，必须写进方案，否则搜索域会与约束打架：

| k (px/count) | d=5 安全上限 | d=6 安全上限 |
|---|---|---|
| 0.25 | 82.0 | 69.4 |
| **0.593（本机）** | **34.6** | **29.3** |
| 1.0 | 20.5 | 17.4 |

也就是说：**本机 `k̂=0.593` 下，`Kp` 的安全上限只有 29~35**，而不是 49~58。
Q3 选的域名 `[5, 60]` **上端有相当一部分落在"稳但不安全"的带里**。

**处理方式（不隐瞒冲突，两条都做）**：

1. 搜索域仍取 **`Kp ∈ [5, 60]`**（尊重 Q3 的决定，且保留观察上界行为的能力）；
2. `g ≤ 0.6·g_crit` 作为**硬罚约束**同时生效 —— 于是 DE 实际可用的
   `Kp` 上端会被自动压到 ~35（d=5）附近；
3. 报告里**同时给出压裕度前/后的最优解**，让你看到"放宽裕度能买回多少 IAE"。

### 3.3.2 约束可行性实测（400px 阶跃, k=0.593, 46ms, 饱和 100px, 限幅 200）

先验证「超调<10% + ts<1s」到底有没有解（否则后面全白做）。实跑结果：

| Kp | 超调 | ts (s) | IAE | 判定 |
|---|---|---|---|---|
| 20 | 0.07% | 0.450 | 75.3 | PASS |
| 25 | 0.07% | 0.350 | 60.6 | PASS |
| 29 | 0.07% | 0.292 | 52.5 | PASS |
| **35** | 0.07% | 0.233 | 43.9 | PASS（裕度内上端） |
| 45 | 1.40% | 0.292 | 35.6 | PASS（超裕度） |
| 60 | 2.74% | 0.633 | 34.2 | PASS（超裕度） |
| 90 | 42.62% | 2.992 | 321.5 | fail |
| 120 | 69.30% | n/a | 544.5 | fail |

**三条结论**：

1. **约束是宽松可满足的**：`Kp=25` 就已 0.35 s 收敛、超调 0.07%。
   所以 `ts<1s` 与 `超调<10%` 不是本问题的瓶颈 —— **不是硬约束逼着参数走，是 IAE 逼着走**。
2. **IAE 在 `Kp≈60` 最小（34.2）**，但那已超出 0.6 倍裕度上限（34.6，d=5）；
   在裕度内取得的最优约 `Kp=35`（IAE 43.9）。**两者相差约 22% 的 IAE** ——
   这是"安全裕度"的显式价格，报告里会量化，由你决定是否付。
3. 失稳形态与 `CLAUDE.md` 记载一致：Kp=90 时超调 42.6%，印证「Kp 大了撞过目标」。

> 注：本节为**单点可行性扫描**（固定 Ki=1.0, Kd=0.01, 饱和 100px），
> 用的是与 `aim_pid_test.cpp` 同构的最小被控对象，目的只是"证明有解"。
> 真正的五维联合寻优在第二步由 DE 完成，指标以那一步的真实输出为准。

### 3.4 一个必须说清的风险：调节时间 < 1 s 是否可达

死区 46 ms 对 1 s 的调节时间目标是**宽裕**的（约 21 个死区时间常数），
所以 `ts < 1 s` 本身不成问题；**真正的张力在 `ts < 1 s` 与「超调 < 10%」同时成立**
—— 在受限增益下，想快就得往高增益走，而高增益撞过冲。

按 `aim_pid.h` 记录的独立扫描（400 px 阶跃，k=0.25，50 ms 死区）：

| Kp | 饱和开(100px) | 饱和关 |
|---|---|---|
| 20 | 16.2 px | 9.5 px |
| 30 | 15.0 px | 8.0 px |
| 40 | 14.5 px | 5.0 px |
| 60 | 25.0 px | 78.8 px |

对 400 px 阶跃，**超调 < 10% = 40 px**。上表在这个口径下都能过，
但注意 `p_full_scale_px = 100` 在低 Kp 段是**帮倒忙**的（§3.5）。

### 3.5 由 §3.4 推出的方案决定：`p_full_scale_px` 必须与 Kp 联合优化

`aim_pid.h:114-137` 已实证：饱和削减的是"接近速度"。
- Kp 小时，不加饱和本来就刹得住，饱和反而让积分多攒欠账 → 过冲**变大**；
- Kp 大时，不加饱和会以极高速度撞过目标 → 过冲**爆炸**，此时饱和救命。

**所以本方案把 `p_full_scale_px` 作为 DE 的优化变量**（而不是沿用 100 的默认值），
让优化器在 `[40, 300]` px 内自行决定，避免把「低 Kp + 强饱和」这个已知劣化组合
当成前提。这是相比"直接复用现役参数"的实质改进。

## 4. 控制律（第四步交付的代码将实现这个）

### 4.1 形式（沿用项目的 dt 归一化约定，不重新发明）

```
e_used = e                                  # 本方案不含前馈（项目已删前馈）
u_fb   = dt · Kp · [ e_used + Ki·∫e_used dt + Kd·de/dt ]
```

三个增益都带时间量纲，换帧率不用重调 —— 这是 `aim_pid.h` 已定的约定，保留。

| 增益 | 单位 | 作用 |
|---|---|---|
| `Kp` | 计数/(像素·秒) | 回路速度，唯一与游戏灵敏度挂钩的旋钮 |
| `Ki` | 1/秒 | 积分速率，`Ti = 1/Ki`，磨掉跟枪稳态滞后 |
| `Kd` | 秒 | 微分时间，压过冲 |

### 4.2 抗积分饱和（Q5 = A 明确要求）

两个机制**同时**上，缺一不可：

1. **钳位**：`|u_raw| > limit_counts` 时停止积分累加（条件积分），
   避免继续往积分器里灌"发不出去的欠账"；
2. **back-calculation（反算回退）**：
   ```
   ∫e ← ∫e + (dt/Tt)·( u_sat − u_raw ) / (dt·Kp·Ki)      # 量纲归一到像素·秒
   ```
   其中 `Tt` 为跟踪时间常数（建议 `Tt = √(Ti·Td)`，经典 IM C 法则）。
   它比纯钳位更平滑：饱和解除后积分器已回到合理区间，不会"憋一下再猛放"。

> 项目原本已有 `kIntegralUnwindTau = 0.2`（误差反号时快回退）。
> 该机制**保留**，与 back-calculation 互补：前者处理"过冲后反号"，
> 后者处理"执行器饱和"。

### 4.3 微分低通（Q5 要求）

一阶低通，τ = 20 ms（沿用 `aim_pid.cpp` 的 `kDerivativeTau`），
**不把它作为用户旋钮**（与 `boss_aim.h:58` 的既定原则一致：它与 Kp 耦合，一起调容易调乱）。

```
α = dt/(τ + dt);   d_filt ← d_filt + α·( (e − e_prev)/dt − d_filt )
```

保留 `aim_pid.cpp:15-25` 注释里的两条边界：`dt` 夹在 [1/2000, 1/15] s。

### 4.4 连续饱和（取代死区，沿用既有设计）

```
e_sat = p_full_scale_px · tanh( e / p_full_scale_px )
```

过原点、连续，所以不像死区那样制造"停—放"极限环。
（`aim_pid.h:105-141` 已论证死区会产生 10.2 次/秒的翻转，此处不重复。）
`p_full_scale_px` 由 DE 决定（§3.5）。

### 4.5 出口量化与零头累加（保留）

```
carry += u_sat
counts = round(carry)      # 或 trunc 向零
carry -= counts            # 零头攒到下一拍
```

整数只在出口出现一次。这样亚计数误差不会被丢掉，避免
`aim_pid.h:10-12` 描述的死区。零头绝对上限钳 0.5。

## 5. 优化（第二步）

### 5.1 不用 scipy 的理由

**实测**：`python -c "import scipy"` → `ModuleNotFoundError`（环境仅 numpy 2.4.6）。
所以自写 DE。反而更好：优化器成为可审计、可复现的项目内资产。

### 5.2 算法

- 策略：`DE/rand/1/bin`，`F = 0.5`（抖动 `F ∈ [0.5, 1.0]` 自适应），`CR = 0.9`；
- 种群：`NP = 15 × dim`（dim=5 → 75）；
- 迭代：`G = 200`（总评估 ≈ 15000 次，单次仿真 ~4 万步，numpy 化后秒级）；
- 边界：反射式重采样（不是简单钳位，避免堆在边界）；
- 初始：拉丁超立方（LHS）撒点，比纯随机覆盖好；
- 种子：固定 `seed=20260913`，**结果可复现**。

### 5.3 决策向量

```
x = [ Kp, Ki, Kd, p_full_scale_px, limit_counts ]
```
注意 `limit_counts` 也进优化（它是原神的 `smooth_max_pixel` 对应物）。

### 5.4 罚函数（硬约束）

```
J_total = J_IAE · (1 + P)
P = w1·max(0, OS − 0.10)/0.10        # 超调 < 10%
  + w2·max(0, ts − 1.0)/1.0          # 调节时间 < 1 s
  + w3·max(0, g/ (0.6·g_crit) − 1)   # 稳定裕度（§3.3）
  + w4·divergence_indicator          # 发散直接巨罚
```
其中 `OS = max(0, −min(e))/step`，`ts` = 最后一次超出 ±2% 带的时刻。
`w1, w2` 取得足够大（如 50、20），保证可行解永远优于不可行解。

> **指标定义必须写明**（否则"超调<10%"会被解释成两种东西）：
> - 超调 `OS`：**相对于阶跃幅值**，即 `|e_min| / 400`；阶跃工况下测量。
> - 调节时间 `ts`：误差进入并保持在 **±2% 阶跃幅值（±8 px）** 带内的最后时刻；阶跃工况下测量。

## 6. 鲁棒性测试（第三步）

### 6.1 参数摄动（Q3 要求 ±30%）

对 `Kp, Ki, Kd` 各做 ±30%，采用**蒙特卡洛**而非穷举 3³=27 组合：
- 300 个样本，每维独立 `U(0.7, 1.3)`；
- 记录 `OS`、`ts`、`IAE` 的分布（p50/p95/max）；
- 判据：**p95 仍满足硬约束**才算鲁棒通过（不是"均值通过"）。

### 6.2 被控对象摄动（对称 §2.2，不可省）

参数鲁棒 ≠ 系统鲁棒。同时对被控对象做 ±30%：
- `k` (px/count)：0.7~1.3 倍 —— 对应换灵敏度/换机器；
- 死区 total：0.7~1.3 倍（32~60 ms）—— 对应链路负载变化。

**这一条是关键**：因为 `g = Kp·dt·k`，`k` 摄动 30% 等价于增益摄动 30%，
直接顶到 §3.3 的稳定边界。所以 `k` 的 +30% 往往是**最先失稳的那一维**。

### 6.3 最坏情况表

输出「最坏 5% 分位」的参数组合表，而不是只报一个平均指标。

## 9. 需要你确认/知悉的四点

1. **dt 取 120 fps**：由实机日志（5.00 Hz / 200 ms = 24 拍）反推，且与
   `kAimDeadTimeS=0.046`、`g/g_crit=1.9` 两项独立吻合，**证据链自洽**。
   但若实机实际 tick 频率不是 120 Hz（例如被采集卡拖到 60 Hz），
   整张 `Kp_crit` 表都要重算。**请确认实机 tick 频率**（唯一还带外部假设的量）。
2. **安全裕度要不要 0.6 倍**：这是本方案里**唯一由我判断、且代价明确**的决定 ——
   它把 IAE 最优的 `Kp≈60` 挡在外面，换成 `Kp≈35`，代价约 +22% IAE。
   取值理由：实机 k̂ 有不确定性，`k` 摄动 +30% 等价于增益 +30%，
   踩在失稳边界的解在仿真里收敛、在机器上就是极限环（历史 Kp=100 即此）。
   **若你认为实机 k̂ 已足够可信**，可以把系数放宽到 0.8，第二步会同时给出两档结果。
3. **`ts < 1 s` 的口径**：本方案定义为「±2% 阶跃幅值（±8 px）带内」，
   与超调同为阶跃工况。若你要的是「±1.5 px 带」（现役 `aim_pid_test.cpp` 的口径），
   `1 s` 会明显更难，请指明。
4. **第四步是否动现役文件**：见 §7，默认只产出独立参考实现，
   **不动** `Apotheosis/mouse/aim_pid.{h,cpp}`。等你确认后再动。
