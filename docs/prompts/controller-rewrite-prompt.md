## 1. 要实现的目标行为（验收标准，逐条可验）

设误差 `e = 瞄点 - 准星`（检测图像素，浮点）。

### G1 静止目标：快速拉枪
从一次大误差（如 300~500px）起手，**尽快**进入命中容差带。
要求：`t90`（首次进入 ±5px 的时间）尽可能短；给出你达到的数值与对照组。

### G2 静止目标：精准停在锚点，不过冲
收敛后**过冲量**有界且小（定义：收敛后反向的最大超越量，单位像素）。
尾段稳态误差中位数应接近 0（逼近一个鼠标计数的量化下限，而不是停在几个像素外）。

### G3 运动目标：快速拉枪
目标匀速/变速横移时，从起手到贴上的时间要短，且在**目标机动（急停、换向、
加减速）**后能迅速重新贴上——这是"焊死"里最难的一半。

### G4 运动目标：不过冲
跟枪过程中不得出现明显的超调摆振（"甩过头再拉回来"）。

### G5 ★核心★ 无论目标如何运动，肉眼看上去焊死在锚点
这是本次重写的**主判据**。定义清楚并逐项验证：

- **稳态跟随误差**：匀速横移时，准星相对锚点的**平均偏移量**应小于 1 个视觉可辨
  阈值（建议以 ≤2px 为目标，并报告实测中位数/p90）。
- **无可见滞后**：不允许"准星稳定跟在目标后面一段距离"这种肉眼一眼可见的拖尾。
  注意：这里**允许**存在一个受控的、被明确记账的前置量（见 §4.2），但**不允许**
  稳态偏移随目标速度线性增长到几个像素以上。
- **无可见抽动**：输出不得自持地在 ±1~2 计数之间翻号（这正是本项目历史上 Kp
  调高后的病灶，见 `docs/aimmagic-comparison.md` §11 与
  `tests/aim_pid_quantum_test.cpp`）。
- **机动瞬间不脱靶**：换向/急停的那几拍，误差峰值有界，且之后迅速归零。

### G6 近大远小
游戏世界是 3D，推理看到的是 2D 画面。同一个世界速度 `v_world` 在画面里的角速度
与像素速度近似为 `v_px ≈ f · v_world / d`：**近处敌人画面速度显著大于远处**。
控制器必须显式处理这件事，而不是假设"画面速度 = 目标速度"：

- **尺度线索只用检测框高度 `bbox.height`**（本项目唯一的距离代理，用户已确认）。
  **不要**引入任何需要真实深度/相机内参的假设；本项目只有单目 2D 检测框。
  （`AimbotTarget::depth_at_pivot` 目前是恒为 -1 的占位，不可使用。）
- 近距（框高）：画面速度大 → 拉枪与跟随都必须**更快、增益更高**，
  但**不允许**因此过冲；
- 远距（框高小）：画面位移小（40m 外 5m/s 横移可能只有 ~0.7px/帧），会被检测框的
  **整数量化噪声淹没** → 此时速度估计不可信，**必须保守**（宁可少补/不补），
  并且**绝不**允许把量化噪声放大成控制抖动。
- 尺度变量必须**连续、有界**（例如映射到一个 `[min_scale, max_scale]` 的乘数），
  不许用硬开关（硬开关会在阈值附近产生"一顿一顿"的极限环）。

> ⚠️ 一个**必须避免**的错误：屏幕速度本身已经是世界速度的投影（`v_px ≈ f·v/d`），
> 所以**不允许**再乘一个与距离/框高成正比的因子去做"几何距离补偿"——那等于把深度
> 算了两遍。尺度变量真正在补偿的是「远处速度估计不可靠」与「近处画面速度更大、
> 需要更快响应」，不是几何投影本身。关于这一点见 `Apotheosis/mouse/aim_predict.h`
> 顶部"关于目标越小提前量越大"那一段，那里已经有过一次纠错。

### G7 不得回归的既有能力
- 帧率无关：同一组参数在 60 / 240 / 1000fps 下收敛时间与稳态误差一致（有断言）。
- 换目标 / 丢目标时的复位语义正确。
- 输出仍是**整数鼠标计数**，直接交给 `sendRawMove`，链路不做像素↔计数换算。
- `aim_path_mode = 0`（直线透传）时行为与不做整形逐位一致。

## 2. 现役架构与各环职责（动手前先确认你同意这份描述）

```
检测框 --(瞄点, target_to_aimpoint_exact)--> 【AnchorFilter α-β 平滑】
       --(AimPredict 瞄点预测, 默认关闭)--> 【AimPid】--> 输出限幅
       --> 【AimPathDriver 轨迹整形】--> sendRawMove(整数计数)
```

- `boss_aim.cpp::tick()` 是**唯一的接入点**：算瞄点 → 平滑 → 预测偏移 → 算误差 →
  调用 PID → 填遥测。`mouse_thread_loop.cpp` 每拍填 `EngineInput`（含 PID 参数快照）、
  算 `dt`（已做 25ms 一阶低通）、调 `engine.tick()`、再经 `AimPathDriver` 下发。
- 单位约定（**必须保留**）：误差/积分/微分全程在**检测图像素**域用 `double` 计算，
  只在出口取整一次成整数计数，**取整零头攒到下一拍**（`carry_`）。先把浮点误差取整
  再算，等于人为制造死区。
- 三个增益带时间量纲：`u = dt * Kp * [ e + Ki*∫e dt + Kd*de/dt ]`，所以换帧率不用重调。
- `AnchorFilter` 是**全链路唯一一道平滑**（准星枢轴的 One-Euro 与参考点惯性低通都已
  删除，理由是串联滤波各自引入滞后、参数还互相耦合）。**不要**再加第二道串联滤波。
- 输出限幅用**反算式抗饱和**：积分项自身贡献也夹在输出上限内。
- `dt` 在 `mouse_thread_loop.cpp` 里已做一阶低通（`kDtSmoothTau = 25ms`），
  因为实测拍间隔 p10=7.45 / p50=8.55 / p90=11.64 / max=23.22ms，等效增益一直在抖。

   `游戏机 --HDMI--> 采集卡 --USB--> 采集机`。k̂ 是**游戏机**的属性，只能从画面反推，

## 4. 设计自由度与纪律要求

本项目的历史教训是：**"更聪明"的机制往往比"更简单"的机制更容易翻车**——因为一个
测不准的量进了回路，错了就直接变成固定瞄偏或自激。所以你可以在下面的框架内自由
设计，但每引入一个机制，都要满足对应的纪律。

### 4.1 你可以改的

- `AimPid` 的形式（增益调度、非线性项、结构改造都可以）；
- `AnchorFilter` 的参数化方式（但**不加第二道串联滤波**）；
- `AimPredict` 的做法（但要满足 4.2）；
- 是否新增**独立于控制器**的模块（例如尺度估计、机动检测）；
- 配置旋钮的划分与命名（用户面参数**尽量少**，且每个都要说清"调过头会怎样"）；
- `boss_aim.cpp::tick()` 里各段的顺序与分工；
- 遥测字段（供 `chainlog` 记录与事后归因，**必须**能定位"这一拍为什么这么动"）。

### 4.2 若引入任何"提前量 / 预测"，必须满足全部五条

1. **可完全关闭**：关闭时与不做该机制的实现**逐位相同**（写成回归断言）。
   AimMagic 的预测开关默认就是关的（`aim_prediction_enabled = 0`），本项目也要有这个性质。
2. **硬上限**：提前量必须有明确的像素上限（量级参考：个位数像素，而非几十像素），
   且上限是**物理量**推导出来的，不是随手写的魔数。
3. **速度噪声门**：只有当速度估计**可信**时才给提前量。静止目标的估计速度是纯噪声
   （历史实测：静止目标 v̂ 噪声 p99=46、max=52 px/s），必须被门限挡住，
   否则会变成"瞄点嗡嗡抖"。建议用连续斜坡门限而不是硬开关。
4. **不许产生"稳态瞄偏随速度线性增长"**：纯反馈回路的稳态滞后是 `v/(Kp·换算)`，
   Kp 够大时只有几个像素；如果提前量恰好抵消这段滞后，是**可以**的，但你必须
   在注释与文档里写清"这是补偿了哪个物理量"，并给出该项在 0 / 低速 / 高速下
   的稳态偏移实测表。**不接受**一个与物理量脱钩、可任意调大、稳态就是 `v̂×T`
   固定偏移的旋钮——那正是用户实测明确否掉的"准星停在目标下一拍位置"。
5. **估计不出来就不启用**：若某拍速度不可信，该机制自动退化为 0，**并保持位置
   输出不变**（不要因为"猜不出"就抖一下）。

### 4.3 若引入"自身在途位移补偿"（Smith 类），必须满足

- 它只回答"**我自己发出去、还没落地的指令有多少**"，**不得**去估目标速度、
  **不得**吃任何标定常数。
- 补偿量必须有界，并且**补不足是安全的、补过头会正反馈发散**——所以宁可少补。
- 窗口长度必须与真实链路死区一致或更短。**历史教训**：本项目实测链路死区约 **46ms**
  （从实机振荡周期 5.00Hz/200ms 反推：`d ≈ 5.5 拍`；用"软件 E2E ≈ 11ms"会漏掉
  HID + 游戏帧 + 显示 + 采集缓冲，导致速度估计混进 `k*Δu/dt` 的假速度，
  再被前馈放大成上百像素假误差）。**不要**用 11ms，也**不要**超过真实死区。

### 4.4 关于"焊死"的物理上限（必须写进你的分析）

延迟决定了反馈回路能达到的增益上限：`u_n` 要过 `d` 拍才在画面里生效，纯反馈回路的
每拍临界增益约为 `g_crit = 2·sin(π / (2(2d+1)))`。本项目实测 46ms 死区 ≈ 5.5 拍，
所以 `g_crit ≈ 0.256`。**先算出你现在这组参数离这个上限有多远**，再决定"焊死"
靠什么达成：
- 靠提高增益 → 会先撞上这个上限（表现为目标附近来回晃）；
- 靠结构改造（前馈/补偿）→ 受 4.2 / 4.3 的纪律约束；
- 靠**非线性增益调度**（大误差段与末段用不同的等效增益）→ 这是本项目的"P 项饱和"
  已经在走的路，可以继续深化，但**函数必须连续、经过原点**，
  否则会制造"停—放"极限环（历史实测 5px 死区导致输出以 10.2 次/秒 在动/不动间翻转）。

**注意一个反直觉的实测结论**：P 项饱和对过冲到底有没有用**取决于 Kp**——
Kp ≤ 40 时饱和反而让过冲**变大**（20 → 16.2px vs 9.5px），
Kp ≥ 60 时才是救命的（100 → 56.0px vs 279.0px），转折在 60 附近。
完整扫描表见 `Apotheosis/mouse/aim_pid.h` 的 `p_full_scale_px` 注释。
你如果改这部分，**必须**重做这张扫描表。

## 5. 量化与"落不到位"的陷阱（必须处理）

1 个鼠标计数 = 链路的最小位移。实测本机 k̂ ≈ 0.593px/计数时，锁死后残差中位数只有
**0.26px——比一个量子还小**。任何在这个尺度上加的补偿都会把误差顶成反号，
进而 P 项反向、自持成 **±1 计数的 60Hz 抖动**（日志实证：Kp=100 时 43~54% 的帧在下发 ±1、
符号翻转 79%；同批 Kp=30 只有 13%——**不是检测噪声**，框自身逐帧变化中位仅 0.06px）。

必须处理，且必须**同时**满足：
- 修正项在误差小于半个量子以内时，**不许把误差顶成反号**（只夹修正项，不碰别的）；
- 停发时零头要**冻结而不是清零**（清零会把"20px/s 慢速横移所需的亚计数需求"一起丢掉，
  实测滞后从 0.8px 涨到 1.2px）；
- 亚量化残差**不进积分**；
- 加严条件后，**甩枪/跟枪的逐拍输出必须完全不变**（回归断言位相同）。

参考 `tests/aim_pid_quantum_test.cpp`：它用一个最小假游戏精确复现了
±1/±1/±1 抖动，并断言开启保护后 0 次下发、残差不退化。

## 6. 尺度（近大远小）的落地要求

- 尺度变量 `s(bbox.height)` 必须**连续、有界、单调**，并归一化到
  `[s_min, s_max]`（例如近处 `s → 1`，远处 `s → 某个小于 1 的下限`，**不要到 0**——
  到 0 就等于"远处完全不动"，会让准星在远处目标上慢慢漂走）。
- 明确它作用在**哪些环节**，并逐项说明理由。至少要考虑：
  - 拉枪/跟随的等效增益（近处更快）；
  - 允许的提前量上限（近处画面速度快，上限应更大）；
  - 速度可信度门限（远处位移小、量化噪声占比高 → 门限更严）；
  - 平滑强度（远处噪声占比高，是否要更强的平滑？注意加了会引入滞后）。
- **框高获取**：`bbox.height` 在 `boss_aim.cpp` 里是**滤波之前**的观测值还是滤波
  之后的值，你要明确选一个并说明理由；框高本身也有抖动，必要时可以对框高**单独**
  做轻度平滑（这不违反"不加第二道串联滤波"——那条针对的是**位置**路径）。
- **不许**把尺度用在"几何投影补偿"上（见 G6 的 ⚠️）。
- 你要**证明**它有效：给出一组对照（关掉尺度变量 vs 打开），在近距/中距/远距
  三种框高下的静态拉枪时间、过冲、跟枪稳态误差。

## 设计备注（给你自己看，别复制进提示词）

**为什么这个提示词长这样：**

1. **把"焊死"翻译成可判据。** "肉眼看上去焊死"没法直接验证，所以拆成：稳态跟随误差
   上限、无肉眼可见拖尾、无自持 ±1 抽动、机动瞬间误差峰值有界。不拆开写，AI 会给你
   一堆"理论上可以"的说辞。

2. **提前量上留了口子，但要求 4.2 五条纪律。** 你没勾选"禁止绝对像素提前量"，
   所以没有一刀切禁掉。但历史记录很清楚——纯提前量的稳态偏移 `v̂×T` 正是你实测否掉的
   "准星停在目标下一拍"。所以允许它存在**仅当**它能说清补偿的是哪个物理量、
   可关闭、有硬上限、有速度门、且给出稳态偏移实测表。

3. **近大远小的 ⚠️ 是最容易写错的一处。** `aim_predict.h` 顶部明确纠过一次错：
   屏幕速度已经是投影结果，再乘距离因子等于把深度算两遍。不写这条，AI 十有八九
   会写一个几何补偿出来。

4. **§4.4 的物理上限是判断"能不能够快"的标尺。** 没有它，AI 会无脑堆增益，
   然后在实机上撞上 46ms 死区造成的振荡——这正是 Kp=30 稳、Kp=100 抽的全部原因。

5. **§5 量化陷阱 + §9 反面清单**，都是本项目已经付过学费的具体教训，
   逐条对应到代码注释里可查的实测数据。给了 AI 这些，它就不必再踩一遍。

- 用户面参数打算放几个？现在是 5 个（Kp/Ki/Kd/饱和/限幅）+ 预测补偿 4 个。
