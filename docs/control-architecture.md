# 时间一致的视觉控制链

> **★★ 控制回路重大改动 (2026-09-13): 前馈/预测整条删除, 改为纯反馈 PID。★★**
>
> 现役实现只有两段:
> ```
> 检测框 --(瞄点)--> 【α-β 框平滑器】--> PID --> 输出限幅 --> 发送
> ```
> 文件: `mouse/anchor_filter.h`(框平滑) + `mouse/aim_pid.h`(PID), 接入点 `mouse/boss_aim.cpp::tick()`。
>
> 单位与形式: 误差/积分/微分全程在【检测图像素】域用 double 计算, 输出是【整数鼠标计数】,
> 只在出口取整一次, 取整零头攒到下一拍:
> `u = dt * Kp * [ e + Ki*∫e dt + Kd*de/dt ]`。**没有 `e_used`, 没有前馈项。**
> 三个增益都带时间量纲(Kp 计数/(像素·秒)、Ki 1/秒、Kd 秒), 所以换帧率不用重调。
>
> **为什么删掉前馈** —— 前馈 = `-在途自身位移 + 目标速度 x 死区`, 两项都需要
> 「每计数多少像素」(k̂)。而本项目的游戏运行在**另一台电脑**上(见下), k̂ 是游戏机的属性,
> 只能从画面反推; 两条可行的反推路径都已被实测证伪(见 `aimmagic-comparison.md` §6.7)。
> 一个测不准的参数进了回路, 估错就直接变成固定瞄偏 —— 历史上 +6.2px @300px/s 就是这么来的。
>
> 改抄**原神 AI 的纯反馈路线**: 它的预测开关是关着的(`aim_prediction_enabled = 0`), 靠
> 高增益 + 输出整形就做到了"静态快拉不过冲 + 动态跟死"。纯 P 回路追匀速目标的稳态滞后
> = `v/(Kp·换算)`, Kp 够大时只有几个像素, 不需要前馈去补。详见 §6.8。
>
> 已删除的文件: `mouse/anchor_observer.h`(α-β 观测器)、`mouse/aim_motion.h/.cpp`(在线估 k̂)。
> 已删除的 API: `AimPidFeedback` 整个结构、`AimPidParams::px_per_count`、
> `AimPid::feedforwardPx/feedforwardScale/subQuantumHold/predictTimeSeconds`、
> `AimEngine::beginCalibrationMeasure` 等整组标定 API、`runtime::calib` 全部遥测、
> 界面上的「每计数像素」输入框与「测量」按钮。
> 新增: `mouse/anchor_filter.h`(α-β 框平滑, 只输出位置, 速度不外传)。
>
> 已删除(2026-09-11): 原 AVA PIDF 整条管线(pidf_mode1/mode2、postprocess、update、axis_policy、
> aim_movement_pipeline、controller_orchestration、pid_input、qx_curve、process_humanization、

> **下面"状态观测器/预测锚点/自运动补偿/阶段切换"等段落描述的是那套已删除的实现, 仅作设计与教训

主程序保留 Media Foundation → NV12/CUDA → TensorRT（或 DirectML）的采集推理底座。目标关联、状态观测、控制输出和设备执行拥有独立的数据边界。

## 数据与时间

- `runtime::FrameContext` 随帧携带采集回调时间、帧序号和图像尺寸。两个推理后端按槽保存并发布这份上下文，不再从全局“最新帧”槽读取来源。
- `DetectionBuffer` 的发布时间与图像采集时间分开。切换模型后，尺寸不匹配的旧检测不会进入控制。
- 准星找色结果使用对应图像的采集时间判断新鲜度；异步处理结束时间不能冒充采集时间。
- 采集回调之前的设备延迟不属于软件探针已测范围，**也无法从软件侧测量**。日志里的时间戳就是原始采集戳，不做任何修正 —— 探针给出的是**下界**，这一点必须如实理解。
  （曾有一个手填的 `capture_age_offset_ms` 用来在时间戳上再减一刀，2026-09-13 已删除：它是"猜"不是"测"，而且控制器是纯反馈、不吃任何延迟估计。）

## 目标关联与观测

`AimEngine` 仅在新检测到达时运行目标关联和锚点计算。原 AVA 跟踪器保留用于关联候选；其预测框不再作为控制器的新观测。控制器收到的是原始观测框产生的锚点及其真实时间。

自身视角移动会先从关联状态扣除，避免快速拉点时把同一目标误认为另一个目标。短暂丢检后，如果原跟踪仍有效且同类候选通过关联门限，保留目标身份。真正丢失、换目标或锚点类别变化时重置对应状态。

独立的二维位置/速度/加速度观测器使用实际采集时间间隔，扣除观测区间内预计生效的自身指令后，再学习目标运动。框形变会提高观测噪声，降低把框抖动当作目标加速的程度。检测框"位置在跳、面积不变"的抖动不体现在框形变里，只会表现为新息连续变号；而真实换向/急停只变一次号、随后持续同号。因此"机动分支"按连续变号次数区分：连续变号（判为抖动）时把速度归零且不放大速度协方差；只变一次号时仍按原来的因果速度估计处理。否则一次 ±2.5px 的来回抖动会被当成约 600px/s 的速度，并经放大后的速度协方差在随后每帧重新注入（正常路径的速度增益约 1/dt），在锚点附近形成永不收敛的极限环。注意不要改用"按新息幅度抬高观测方差"来抑制抖动：真实的急停/换向同样产生大幅度新息，抬高方差会把本该做的位置吸附一起平滑掉（实测 continuous_tracking_test 的 reverse 场景 p95 会从 4.35px 退化到 14.75px）。X/Y 分别保存状态与协方差。

原 PIDF 参考实现中，两轴共用初始化标志而只初始化第一轴的问题也已修复并保留回归。

## 现役控制器 (2026)

每拍一次: 误差取 `anchor - crosshair`(像素, 浮点), X/Y 各一个 `AimPid`, 输出整数计数交给
`mouse_thread_loop.cpp`(先过 AimPath 整形, 再 `sendRawMouse`)。

- **误差与状态全程浮点像素**。整数只在出口出现一次; 取整零头(`carry`)攒到下一拍, 所以
  差 0.4 像素的误差不会像"先取整再算"那样被丢成 0 —— 那正是老实现"卡在差两像素不动"的来源。
  实测: 0.6px 常驻误差在 1.667s 里累出 20 counts, 与 `Kp*e*T` 的理论值一致。
- **框平滑 (α-β)** 在算误差之前、且是进 PID 的唯一预处理。它只做一件事: 滤掉检测框的抖动。
  检测框每帧都在跳(实测框心逐帧变化中位 0.06px, 偶发跳变 1.9px), 在 8.3ms 拍间隔下那是
  230px/s 的【假速度】—— PID 的 P 项放大的是这个噪声, 不是真实误差, 所以 Kp 一开大就开始抖。
  用 α-β 而不是一阶低通: α-β 带速度状态, 是"预测 + 修正", 匀速目标下预测本来就准、新息接近 0,
  所以几乎不落后, 而随机抖动照样被滤掉。一阶低通只知道位置, 追匀速目标会持续落后一个固定量,
  只能靠更大的 Kp 去补, 而 Kp 越大残留噪声放大得越厉害。**速度只是滤波器内部状态, 不外传。**
  时间常数是编译期常数 `kAnchorFilterTauMs`(30ms), 故意不做成用户旋钮 —— 平滑强度与 Kp 耦合,
  两个一起调极容易调乱。
- **全链路只有这一道平滑 (2026-09-13 收敛)**。同一时期还删掉了两道**冗余**的时间滤波:
  - 准星枢轴的 One-Euro 自适应滤波(`crosshair_smooth` + `crosshair_runtime.cpp` 的
    `OneEuro2D`)。准星找色检测本身保留, 输出改为原始质心。
  - 参考点 `StaticCrosshairRef` 里的惯性一阶低通(同一个 `crosshair_smooth` 驱动)。
    **它的另外两个职责保留**: 限速(挡单帧几十像素的假命中, 是抗野值不是平滑)与
    丢帧保持/限速滑回中心(挡"参考点跳回中心"那种阶跃)。
  为什么必须收敛成一道: 串联滤波**各自引入滞后、参数还互相耦合** —— 调了一个, 另一个就
  不对了, 而它们能滤掉的东西完全一样。留 α-β 是因为它就在控制器门口, 且对"匀速目标不
  落后"有解析保证(见上)。**"锚点跟不跟手"现在只有一个地方可调。**
- **积分只在误差不"赖着不走"时按满速累加**, 大误差按 `窗口/|e|` 衰减(防甩枪阶段在死区里绕成欠账),
  误差反向时按 0.2s 时间常数快速回吐(否则甩枪后会在目标附近留 8~9px、持续一秒以上的残余偏移)。
- **P 项连续饱和**(`p_full_scale_px`, 默认 100px)取代死区: `|e| <= 阈值` 原样透传(满增益,
  一个像素都不丢), 超过则按 `阈值/|e|` 衰减。它与死区的本质区别是这个函数【连续且经过原点】,
  误差多小都会出力, 所以不存在"停了"这个状态, 也就不存在死区震荡那个极限环
  (实测 5px 死区下输出以 10.2 次/秒 的频率在"动/不动"之间翻转)。
- **输出限幅**(`pidf_limit_*`, 0 = 内置 200/拍)被截掉的位移不攒成欠补发的欠账; 积分项自身也
  夹在同一个上限内(反算式抗饱和)。这一条相当于原神 AI 的 `smooth_max_pixel`。
- **复位时机**: `motion_suppressed`(换目标身份)或丢失目标时 `reset()` 清积分/微分/余量,
  框平滑器也一起复位 —— 换了目标, 上一段的位置/速度估计对新目标没有意义, 留着只会让它"预测"
  到旧方向去。
- **帧率无关**: 同一组参数在 60/240/1000fps 下收敛时间与稳态误差一致(回归里有断言)。
- **用户只调 5 个参数**: 追踪增益(Kp) / 积分增益(Ki) / 震荡抑制(Kd) / 移动死区 / 移动限幅。
  对应原神 AI 界面上的四个参数(追踪增益/积分增益/最大速度/震荡抑制)+ 死区。
  **「每计数像素」既不显示也不可填 —— 它不再影响任何行为。**

## 已删除实现的记录: 独立控制时钟与阶段切换

> 以下描述的是已删除的 AVA PIDF 管线, 仅作记录。

没有新检测时不重复更新观测器。控制输出依据独立节拍，将状态预测到新指令预计生效时刻，并扣除已发送及尚在途的最终位移。

- 接近：较快消除大误差。
- 收敛：根据预计残余误差与相对运动减小输出。
- 跟随：速度前馈加位置修正，避免移动目标进入死区后完全停止跟随。

输出以指令生效区间的中点为目标，兼顾位置误差与预测运动趋势；大模型创新触发短时降阶，位置突跳不被直接外推为持续极端速度。动作生效时间边界有不确定性时，降低对应观测对运动估计的影响。

阶段切换有迟滞。控制器不按丢失的节拍追发一串命令；观测过期时停止输出，短暂缺测时逐步降低预测输出。

## 最终指令与反馈

路径整形保持浮点图像像素，之后统一完成：

1. **计数限幅**(控制器已经把输出算成计数; 现役链路没有"像素到计数换算"这一步 ——
   控制器全程在计数域, 不需要「每计数多少像素」这个标定量)。
2. 单次量化与分数余量保存(**在控制器出口完成**: `lround(cmd + carry)` 并把零头留到下一拍)。
3. 进入 `CommandJournal` 并发送。

指令历史记录的是最终接受的计数和对应图像位移，包含 queued/sent/failed/cancelled 状态。覆盖、取消和发送失败不会作为已执行位移进入观测器；发送与取消竞争时，以实际完成的写入记录为准。限幅截掉的位移不会积累为以后必须补发的欠账。

MAKCUNEW 当前只提供串口写入成功，未提供每条移动的硬件执行确认。因此 `sent + effect_delay` 是预计生效时刻，不能称为固件/游戏已执行确认。视觉观测继续修正该模型；硬件执行确认需要后续固件协议支持。

## 硬件映射

「硬件 → 图像与鼠标映射」中的 `mouse_pixels_per_count_x/y` 与 `mouse_effect_delay/uncertainty_ms`
已随旧管路删除 —— 现役控制器不做像素<->计数换算, 也不需要把"生效延迟"作为回路内的模型常数。

**该分组现在没有任何持久化字段了**: `capture_age_offset_ms` 也已删除(2026-09-13), 因为它是
手填的猜测值、且控制器不吃任何延迟估计。硬件页上原来那个「采集回调前帧龄（估计）」输入框
同步移除。

这些默认值不代表本机已完成标定。映射应与游戏视角及开镜状态一致；当前没有自动识别开镜倍率。
新控制器里与游戏灵敏度挂钩的量只有 Kp 一个旋钮。**「每计数像素」已经完全不参与控制了**
(见下), 所以它也不再是调 Kp 的参考 —— 现在只能靠手感: 拖沓就往上加, 开始抖/画圈就退回来。

### 「每计数像素」怎么量 (2026-09-13 更正) —— 已作废, 不再需要

> **【2026-09-13 后续】这一整节的问题已经消失: 前馈删除后没有任何代码消费 k̂。**
> 下面保留的是"为什么当年量不出来"的完整记录 —— 如果将来有人想重新引入前馈,
> 请先读这一节, 那两条错路不要再走一遍。拓扑的结论仍然成立且很重要。

**先记住本项目的拓扑**: 程序跑在**采集机**上, 游戏跑在**另一台机器**上。

```
游戏机 --HDMI--> VC-009PRO 采集卡 --USB--> 采集机(程序 + CMP 40HX + MAKCU)
游戏机 <--------------- MAKCU 盒子输出(插在游戏机) ---------------┘
```

所以「每计数像素」是**游戏机**的属性, 只能在**游戏画面**里量。曾经走过的三条路都是错的,
不要再走:

1. ❌ **拿 `AnchorObserver` 的输出当测量源。** 它的职责恰恰是把"我们自己造成的位移"
   从锚点里**减掉**(`predicted = pos + vel*dt - k*u_eff`), 只留目标运动 —— 拿一个
   "专门剔除待测量"的信号去测那个量, 原理上不成立。而且大步长会让残差撞上 40px 野值
   门限被整拍丢弃, **甩得越猛越测不出来**(实测甩 469 计数只报出 31.1px)。
2. ❌ **读采集机的 `GetCursorPos`。** 那是另一台机器的光标, 只反映采集机的指针加速,
   与游戏灵敏度无关(实测 100 计数 -> 247px, 散布 0.0% —— 稳定但**无意义**)。
3. ❌ **在游戏机上跑个小程序读那边的光标。** 用户在游戏机上实测确认:
   **游戏运行时 Windows 光标是焊死的**, 读不到任何位移。

**唯一理论上可行的**: 从游戏画面里取一个**不依赖检测框**的参照(例如背景特征位移),
而且不经过任何观测器。但实测本项目的帧间位移量级(甩枪时每帧 23~93px)远超光流的
有效范围(约 7px), 要做得上模板匹配 + 金字塔, 工作量大且不保证成功 —— 而且**现在已经
没有消费者了**, 所以不做。

> **最终结论**: 不量了。前馈删除后 k̂ 不存在消费者; 控制器的"跟得紧不紧"完全由 Kp 决定,
> 而 Kp 是可以直接按手感调的, 不需要先知道 k̂。


## 验证边界

`predictive_controller_test`、`aim_engine_test`、`ava_chain_test`、`continuous_tracking_test` 与
`aim_scenario_sim` 已随各自被测的实现一起删除。

现役控制器的回归是 `tests/aim_pid_test.cpp`, 它自己搭了一个"假游戏"当被控对象(目标有世界速度、
镜头按我们下发的计数转、测量与执行各有延迟), 覆盖:

- 静止目标的收敛与稳态误差(60/240/1000fps, 断言帧率无关);
- 匀速目标的稳态滞后量 —— P-only 回路是 `v/(k*Kp)`, 积分把它磨小并消除残余偏置;
- P 项连续饱和: 大误差段输出有界, 但函数连续且过原点(小误差仍按比例出力);
- 框平滑器 `AnchorFilter`: 噪声被显著抑制, 且匀速段滞后远小于一阶低通;
- 输出限幅、分数余量攒到下一拍、NaN/dt 异常、非法增益、换目标复位。

逻辑测试不能替代 Windows 主程序编译及采集卡、CUDA、串口、固件、游戏的实机验证，尤其不能证明“任何运动都能零误差锁定”。实机验收应区分首次进入容差、稳定留在容差、过冲、断流停止、切换目标及最终指令执行状态。

**还没做实机验证的部分**(逻辑测试覆盖不到): 删除前馈后各游戏灵敏度下 Kp/Ki/Kd 该取多少
(纯反馈路线的调参方法与原神 AI 一致: 追踪增益往上加到手感跟得住, 开始抖就退回来,
用震荡抑制压抖; 积分增益只需压掉匀速目标的残余滞后, 调太大会出现"一抽一抽"的极限环,
那说明链路延迟偏高)。

## 调参指引 (2026-09-13, 纯反馈路线)

从原神 AI 的实测经验与理论推导得出, 三个增益的作用边界:

| 参数 | 作用 | 调过头会怎样 |
| --- | --- | --- |
| 追踪增益 Kp | **唯一决定"跟得紧不紧"的旋钮** | 输出在目标附近高频抖动(±1~2 计数自持翻号) |
| 积分增益 Ki | 磨掉追匀速目标时的固定滞后 | **"一抽一抽"** —— 极限环, 由链路延迟造成 |
| 震荡抑制 Kd | 压 Kp 带来的抖动 | 过大反而拖慢收敛、把检测框抖动放大成控制噪声 |

**"一抽一抽"的机理**: 发的指令要过很久才在画面里生效 → 控制器以为"没动"、继续加力 →
指令终于生效、已经过头 → 反向纠正又过头 → 循环。**延迟越大越容易抽。**
所以这个现象出现的门槛, 直接反映本项目的端到端延迟有多大。

**纯 P 回路的稳态滞后**(追匀速目标, 不靠积分):

```
滞后 px = 目标速度(px/s) / (Kp[计数/(像素·秒)] x k̂[像素/计数])
```

k̂ 未知也没关系 —— 上式说明"滞后与 Kp 成反比", 所以只需按手感把 Kp 加到滞后可接受为止。

本轮完整动程回归与同条件对照见 [连续运动对照](benchmarks/continuous-tracking.md)。
