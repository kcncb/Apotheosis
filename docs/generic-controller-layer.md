## 0. 用户决定（2026-09-17 第二轮，全部已定）

| # | 决定 | 影响 |
|---|---|---|
| **D1** | 不开找色时，准星 = **直接取画面中心** | 不需要"无准星视觉源"的估计器 |
| **D2** | 开找色时，**找到的准星就是当前准星**，据此移动即产生压枪 | 压枪不需要弹道表/独立模块/k̂ |
| **D3** | **一套参数只配一套倍镜**，换倍镜用户重新调参 | 不需要倍镜自适应、不需要自动估 k̂ |
| **D4-a** | 控制器**不需要知道**自己处于哪种 `cross` 模式 | L2 只吃 `cross` 这个 px 坐标 |
| **D4-b** | 找色**找不到 → 退回静态**（画面中心），重来 | 不需要"后坐力可见性失效"告警 |
| **D4-c** | **尺度调度不做**（`aim_scale` 不重建） | **Kp 是唯一增益旋钮**，见 §4.2 |
| **D4-d** | 控制节拍 **一帧一次**（无新检测就 `continue`） | 控制节拍 = 检测节拍 |
| **D5** | **Kalman 作为独立可选项，放在推理与 PID 之间**，观测后的结果喂给控制器 | 见 §3.5（**有前置条件**） |

### 0.1 用户决定的执行流程（2026-09-17 第三轮，已确认）

★★ 这一节是**用户逐条口述确认**的流水线，**取代**此前所有关于顺序的推测。
其中 D6~D9 是这一轮新定或新澄清的，**与 D1~D5 不冲突**。

```
推理输出（全部框 + 类别 + 置信度）
  ↓ ① 筛选 + 选靶
      按 Delete / Filter / Aim 筛 → 只留 Aim
      → 选一个：距准星最近 + 滞回（锁定后除非明显更近才换）
  ↓ ② 检测稳定器
      认目标 + 剔除异常框（只重画当前帧的框，不参考上一帧位置，无平滑）
  ↓ ③ 滤波（全链路唯一一处滤波）
      取稳定后框中心点 → 平滑中心点
      【α-β（默认） ┃ Kalman（可选）】← 二选一，卡尔曼打开时替换 α-β
  ↓ ④ 算瞄点
      滤波后中心点 + y偏移 → anchor
      ④b 基于中心点建坐标系 → xy 中轴
  ↓ ⑤ PID（两套增益 Kp_x / Kp_y）
  ↓ ⑥ 限幅 → 单次量化 + 余量结转
  ↓ 驱动抽象
```

| # | 决定 | 影响 |
|---|---|---|
| **D6** | **检测稳定器不是滤波**：只重画当前帧的框，**不参考上一帧位置**，无任何位置平滑 | 稳定器 = "认目标 + 剔除异常框"。位置平滑**只在 ③ 一处**发生 |
| **D7** | **卡尔曼替换 ③ 的平滑，而不是追加**：卡尔曼打开时，③ 的 α-β 平滑**不做** | 守住了 §3.5.1 的"禁止串联" |
| **D8** | **xy 中轴 = 两套增益**：`Kp_x` / `Kp_y` 分开 | ★ 见下方"D8 的连锁后果" |
| **D9** | **选靶加滞回**：锁定后保持，除非新目标明显更近才切换 | 否则两个目标交替最近 ⇒ 每帧换目标 ⇒ ②③ 每帧复位 ⇒ 滤波白做 |

**★ 明确不做（用户已表态，不要"顺手"加回来）**：

| 不做的东西 | 原因 |
|---|---|
| **检测延迟降权** | 用户判断"无法区分该帧是否是 200ms 前的"，约定**所有帧都当作可及时处理** |
| **置信度加权** | 会引入"置信度 → 有效增益"的耦合，与 §3.2 的"平滑强度与 Kp 耦合"是同一类问题 |

⚠️ 上表第一行**与 §3.3 第 1 条并存**：`staleLocked()` 那个二值门禁**仍然保留**
（超时全停），取消的只是"中间那段连续降权"。

**★ 要加的两条**：

1. **突变检测**（§3.2.1 的突变检测）：换目标 / 瞬移时**重置滤波状态**。
   ★ 它**不属于滤波**，无论开不开卡尔曼都需要 ⇒ 已按用户口述归入 ② 的职责。
2. **框宽高比合理性检查**：模型偶尔会吐形状离谱的框，一个便宜的检查比让滤波器消化它划算。

★★ **D8 的连锁后果（必须记账）**：§4.2 的稳定线 `g_crit` 是**单方向**推出来的，
D8 分成两套增益后：

- `Kp_x` 与 `Kp_y` 各自独立受 `g_crit` 约束 ⇒ **稳定线要算两遍**；
- 若用户给两者设不同的值，两个方向的**稳定裕度与过冲量都不同**；
- §5.3 的 UI 提示要从"一个比值"变成"两个比值"。

★ **起点值**：历史生产值 `Kp = 35`（单套）。分两套后**两个都先填 35**
（等价于原行为），等 §7 的实测表出来后再分开 —— 这样"改成两套"这个动作本身
**不改变默认行为**，是安全的起点。


★ D2 的推论**极其重要**：压枪在**像素域闭环**内就完成了，**全程没有 k̂**。
这正好落在 `aiming-controller.md` §4.2 那条铁律上 —— "稳态瞄偏不许随速度线性增长"
的历史翻车是**前馈**造成的，而 D2 这条路是**纯反馈**，不碰那个坑。

★ D3 的推论：`k̂`（像素/计数）**可以合法地消失**。换倍镜 = k̂ 变 = 稳定线对应的
Kp 变，用户重调 ⇒ 控制器内部**永远只看到一套自洽的 (Kp, k̂) 组合**。
所以本设计**不引入 k̂ 作为显式配置**（见 §5.2 的取舍说明）。

★★ **D4-c 的连锁后果（必须记下来）**：取消尺度调度后，`Kp` 是唯一增益旋钮。
`aiming-controller.md` §5 那张 G1/G2 表显示 **Kp=35 已经过冲 43.56px**，
而 Kp=30 只有 19.84px —— **可用窗口很窄，且离稳定线不远**。
尺度调度原本承担"近处减增益"的职责（`Kp·s_max = 52.5` 是顶格），现在这个职责
**回到了用户身上**：用户必须为远近目标折中一个 Kp 值。这是 D4-c 的**已知代价**，
不是缺陷 —— 但 §7 的未决问题 3 要改写成"远近折中值定在哪"。

## 1. 单位法 —— 这是设计的第一道门

`openspec/config.yaml` 的硬约束：**新中间量的合法单位只有两种**。

| 合法 | 说明 |
|---|---|
| **检测图像素** | 中心裁切后，1 检测像素 = 1 屏幕像素（`capture.cpp:498-502`；裁切边长恒等于 `detection_resolution`，无独立 `capture_crop`） |
| **整数鼠标计数** | 出口量化的唯一产物 |

用这道门去量"游戏特性"，结论如下 —— **这是本文最有价值的一张表**：

| 游戏属性 | 单位 | 能否进代码 |
|---|---|---|
| 目标在画面里的位移 | px | ✅ 核心输入 |
| bbox 尺寸 / 对角线 | px | ✅ 突变检测（`kSnapMult`）；★ 尺度调度已按 D4-c 取消 |
| 准星在画面里的偏移（后坐力抬枪） | px | ✅ D2 的压枪误差源 |
| 换向 / 急停**频率** | Hz (1/s) | ✅ 可逐帧数出来 |
| 目标在画面里的速度 | px/s | ✅ |
| 移动速度 m/s、滑铲 5m、交战 0–80m | **米** | ❌ **非法** |
| 灵敏度 / DPI / 倍镜倍率 | 游戏机属性 | ❌ 不可测；D3 下也无需测 |
| 弹道 / 后坐力曲线 | 计数 | ✅ 合法，但需用户录制 |

★★ **`docs/art-design.md` 里那一整张身法表（滑铲 5m、威龙 10m、AD 急停 60cm）是"米"，
且文档自己标注"来自社区测试，不完全确定"。它们只能当设计动机，不能写进代码。**
写进去就是把非法单位带进控制器 —— 而且这些数值**逐游戏不同、逐版本会变**，
正是"通用控制器"必须拒绝的耦合。

★ 因此本设计的立场是：**游戏特性不进代码，只决定参数取值。**
控制器永远只吃 px 和整数计数。

## 2. 三层结构

```
            ┌─────────────────────────────────────────────┐
            │  L0  数据面 (逐游戏配置, 非控制器)            │
            │  检测模型 / 类别桶 / FOV 椭圆 / 找色颜色      │
            └───────────────────┬─────────────────────────┘
                                │  检测框 (px, 带采集时间戳)
                                ▼
            ┌─────────────────────────────────────────────┐
            │  L1  观测面 (游戏无关, 只吃 px)               │
            │  ① 筛选(Delete/Filter/Aim) + 选靶(最近+滞回)  │
            │      │                                       │
            │      ▼                                       │
            │  ② 检测稳定器: 认目标 + 剔除异常框             │
            │     ★ 只重画当前帧的框, 不参考上一帧 (D6)      │
            │     ★ 含突变检测 → 换目标时重置下游滤波状态    │
            │      │                                       │
            │      ▼                                       │
            │  ③ 滤波: 平滑中心点 (全链路唯一一处滤波)       │
            │     【α-β (默认) ┃ Kalman (可选)】            │
            │     ★ 二选一, 卡尔曼【替换】而非追加 (D7)      │
            │      │                                       │
            │      ▼                                       │
            │  ④ 瞄点 = 滤波后中心点 + y偏移                 │
            │     ④b 基于中心点建坐标系 → xy 中轴            │
            │  准星还原: 找色(开) / 画面中心(关)  (D1/D2)    │
            └───────────────────┬─────────────────────────┘
                                │  误差 e = (ex, ey) = anchor − cross (px, double)
                                ▼
            ┌─────────────────────────────────────────────┐
            │  L2  控制面 (游戏无关, 只吃 px → 计数)        │
            │  PID (纯反馈, 无前馈/无预测)                  │
            │  ★ 两套增益 Kp_x / Kp_y (D8)                  │
            │  → 输出限幅 → 单次量化 + 余量结转             │
            │  ★ 无尺度调度 (D4-c); 节拍一帧一次 (D4-d)     │
            └───────────────────┬─────────────────────────┘
                                │  整数计数
                                ▼
                       驱动抽象 (MAKCU / MAKCUNEW / KMBOXNET)
```

**分层的判据**：任何一层都**不允许**出现上一层的游戏知识。L2 不知道自己在打什么游戏，
甚至不知道有没有开找色（它只看到 `cross` 这个 px 坐标，D4-a）。
**L2 也不知道滤波用的是 α-β 还是 Kalman** —— 它只收到一个瞄点。

★ **D5 的落点在图上是明确的**：Kalman 在 L1，**PID 之前**，
所以它对控制器是**透明**的（换来换去只改 L1 的一个开关）。
这也意味着 Kalman 的**任何副作用（滞后、超调）都会直接变成控制器的输入误差** ——
所以 §3.5.4 要求它开了之后必须重测稳定线。

## 3. L1 观测面

### 3.1 准星还原 (D1 + D2)

统一接口，**两种来源，同一个输出**：

| 模式 | `cross` = | 后坐力可见性 |
|---|---|---|
| 找色**关** (D1) | **画面几何中心**（`detection_resolution/2`, 常量） | 不可见 |
| 找色**开** (D2) | 找色质心（会随后坐力上下跳） | **可见 ⇒ 压枪自然发生** |

★ **这就是 D1+D2 的全部内容**，也是"压枪效果"的来源：开找色后 `cross` 不再固定在
中心，后坐力把准星抬上去 → 误差 `e = anchor − cross` 立刻变大 → 控制器下压把它拉回
目标。**不需要任何独立的压枪模块，不需要弹道表，不需要 k̂。**

★★ **必须在接口上标注的事实**：这两种模式给出的 `cross` 是**两个不同的物理量**。
控制器不需要知道是哪种（这是本设计的关键简化），但**日志和 UI 必须区分**，
否则排查时会把"没开后坐力可见性导致压不住"误判成"控制器调参不对"。

★ 找色不可用时的行为**保持现状**（`crosshair_runtime.cpp:232-246`）：丢帧惯性接力
1~3 帧保持上一有效位置，**绝不突变跳回画面中心**。原因写在那里 ——
"防止压枪抽搐"。这条是实测结论，不要改。

★ `crosshair_runtime.cpp:300-305` 的 ROI **故意偏上**（`roi_y = rows/2 - roi_h + 10`），
注释明写"不要顺手把它改成居中 —— 那会在连发时丢准星"。后坐力抬枪是**向上**的，
这个方向对所有 FPS 通用，**保持**。

### 3.2 稳定器 · 滤波 · 瞄点

★★ **2026-09-17 第三轮重写**：本节此前把"稳定器"和"滤波"混在一起。
按 D6/D7 拆成**三步独立职责**，顺序即 §0.1 的 ②③④。

#### 3.2.1 ② 检测稳定器 —— 不是滤波（D6）

**职责只有两条**：

1. **认目标**：这个框和上一帧锁定的那个是不是同一个（中心距离 + 尺寸相似度）
2. **剔除异常框**：形状离谱的框（宽高比检查）、尺寸突变的框

★★ **它不做位置平滑**：只**重画当前帧的框**，**不参考上一帧位置**。
所以它**不是滤波**，不违反"全链路只有一道滤波"。

★ **突变检测归这里**（原 §3.2.1 的突变检测）：
`kSnapMult = 1.15 × 平滑后 bbox 对角线`（`art-design.md:204`）。
瞬移（威龙式推进）或被换目标时，**必须硬重置下游的滤波状态**。
★ 它**与卡尔曼无关** —— 无论开不开卡尔曼都需要，所以放在 ② 而不是 Kalman 专属的一节。

#### 3.2.2 ③ 滤波 —— 全链路唯一一处（D7）

★ 照 `docs/control-architecture.md` 的现役结论，**不重新推导**：

- **平滑对象是"稳定后框的中心点"**（2 个数），**不是**四个角/宽高 ——
  框的抖动主要来自中心与尺寸，而平滑点数越少越不容易调乱
- **位置**：稳定器**之后**、算瞄点**之前**
- **α-β 是默认实现**（30ms，编译期常数 `kAnchorFilterTauMs`，
  故意不做成用户旋钮 —— 平滑强度与 Kp 耦合，两个一起调必乱）
- **速度只是滤波器内部状态，不外传**
- ★★ **卡尔曼打开时替换 α-β，不做串联**（D7）。二者是"同一个位置的两种实现"，
  同一个接口、只允许激活一个；运行时若两个同时激活**必须拒绝并报错**

#### 3.2.3 ④ 瞄点与 xy 中轴

```
anchor = 滤波后的中心点 + y_offset × 框高      (px)
y_offset ∈ [y_offset, y_offset_max]            框内相对位置, L0 逐游戏配置
```

★ `y_offset` 的语义是**框内相对位置**（不是像素），所以它跨游戏时**比像素偏移稳**。
⚠️ **但方案此前那句"人形目标胸口在任何游戏里都是 0.55"过于乐观**：
它依赖"框把什么框住了" —— 框全身 / 只框上半身 / 只框头，同一个 `0.55` 指向的位置完全不同。
⇒ **`y_offset` 的通用性依赖"框的语义一致"，这是 L0 的责任，不是白捡的。**

★ **④b xy 中轴**：基于（滤波后的）中心点建坐标系，把误差分解为 x / y 两个分量。
**这两个分量在 L2 用两套增益**（D8）。

### 3.3 目标丢失与新鲜度

★ 三级门禁**按现有形状保留**（这三条各自堵过具体的翻车）：

1. **检测新鲜度**：`detectionBuffer.staleLocked()`（阈值随实测检测间隔自适应，
   `clamp(2×last_interval, 50, 600)ms`）。堵的是"推理卡顿时追一个已经离开画面的幽灵"。
   ★ 按 D9 附带决定：这是**二值门禁**，**不做中间的连续降权**。
2. **找色新鲜度**：`kFreshnessMs = 20`（`crosshair_runtime.h:29`）。堵的是"压缩帧里
   小准星消失 → pivot 跳中心 → 控制器以为对准了"。
3. **目标身份**：换目标时**必须**复位积分/微分/余量，**且 ③ 的滤波状态一起复位** ——
   上一段的位置/速度估计对新目标没有意义，留着只会"预测"到旧方向去。
   ★ 触发者就是 ② 的突变检测 + ① 的选靶滞回。

### 3.4 选靶（①）—— 距准星最近 + 滞回（D9）

```
候选 = 类别桶为 Aim 的框
目标 = argmin( 到准星的距离 )
       ★ 滞回: 已锁定 T 时, 新候选 C 必须比 T 近 k 倍才切换 (k > 1)
```

★★ **滞回不是优化，是"滤波能不能起作用"的前提**：
两个目标交替成为"最近"时，无滞回会**每帧换目标** ⇒ ② 认目标反复失败、
③ 的滤波状态每帧重置 ⇒ **滤波等于不存在**。

★ **`Filter` 桶的语义必须在实现时明确**（现在代码里是死的：
`applyDeleteBucketFilter` 只处理 `Delete`，`Filter` 配了没反应）：

| 桶 | 语义 |
|---|---|
| `Delete` | 永远不考虑（队友、场景物件） |
| `Filter` | **参与检测但不瞄准**（想看见但不想锁） |
| `Aim` | 可瞄候选 |

★ 换游戏的标准动作 = 换模型 + 重配类别桶/瞄点/FOV + 重调增益，**控制器代码一行不改**。

### 3.5 Kalman —— ③ 的可选实现（D5 + D7）

**位置**：③，即稳定器与瞄点之间。**不是** `pid` 之内，也**不是**在 α-β 之外再加一道。

#### 3.5.1 与 α-β 框平滑的关系 —— 这是本节唯一必须守住的约束

★★★ **Kalman 不是"再加一道滤波"，而是 α-β 的替代品。二者必须二选一，不允许串联。**

理由**不是审美，是实测结论**（`control-architecture.md:81-84`）：

> 为什么必须收敛成一道：串联滤波**各自引入滞后、参数还互相耦合** —— 调了一个，
> 另一个就不对了，而它们能滤掉的东西**完全一样**。

这段结论是用**两个被删掉的滤波器**换来的：准星枢轴的 One-Euro
（`crosshair_smooth`）、参考点 `StaticCrosshairRef` 里的惯性一阶低通 ——
它们与 α-β 串联时，能滤的东西完全相同，却各自引入滞后、参数互相耦合。
**"锚点跟不跟手"最终被收敛成一个可调点**，这是有意为之。

★ 而且 α-β **本身就是 Kalman 的特例**：α-β 是"位置 + 速度"两状态的稳态卡尔曼，
`art-design.md:72` 把 Alpha-Beta 标为"简化 Kalman，同样有动力学假设"。
所以"开 Kalman"的正确含义是**用完整的 Kalman 换掉那个简化版**，
而不是"在简化版前面再加一个完整版"。

⇒ **实现形态**：`IFilter` 二选一开关（α-β 默认 / Kalman 可选），
**同一个接口、同一个位置、只允许激活一个**。运行时若两个同时激活，
**必须拒绝并报错**，不许静默叠加。

#### 3.5.2 Kalman 的已知风险（D5 要开，但风险要记账）

★ `art-design.md` §三把 Kalman 判为 ✗ 的理由是**动力学假设**：

> 三角洲的角色移动没有加速/减速过渡，方向反转在 1 帧内完成。
> Kalman 滤波器假设目标做匀速或匀加速运动，在每次急停/变向时都会
> 预测错方向并超调。

★ 这条**对"预测"成立，对"滤波"不完全成立** —— 这是把 Kalman 做成可选项的关键区分：

| 用法 | 零惯性下是否成立 |
|---|---|
| 用 Kalman 的**预测**位置当瞄点（外推） | ❌ 变向时预测错方向并超调 |
| 用 Kalman 的**滤波**位置当瞄点（只做估计，不外加外推） | ⚠️ 温和得多，但**过程噪声 Q 大**时退化成偏重平滑 |

⇒ **本设计只允许 Kalman 走"滤波"用法**：输出的位置喂 PID，
**不许把它的事件外推量加进瞄点**。若将来要加外推，那属于"预测"，
必须**重新走一遍 `aiming-controller.md` §4.2 的五条回归**，不能顺手开。

#### 3.5.3 Kalman 必须继承 α-β 的三个既有职责

★ 这三条都是**用实测事故换来的**，Kalman 替代 α-β 后**不能丢**：

1. **速度状态不外传**（`control-architecture.md:74`）。
   速度只做滤波器内部状态。α-β 的解析保证是"匀速目标下预测本来就准、新息接近 0，
   所以几乎不落后"—— Kalman 若要保住这个性质，**Q/R 的配比必须调到位**，
   否则就是"追匀速目标持续落后一个固定量"，只能靠更大 Kp 去补，
   而 Kp 越大残留噪声放大越厉害（这正是当年否决一阶低通的理由）。
2. **换目标必须复位**（§3.3 第 3 条）。Kalman 状态残留会让新旧目标之间来回振荡 ——
   **这正是 `art-design.md:15` 记的"切目标抖动：Kalman 状态残留"**，
   是当年换掉 Kalman 的**原因之一**。所以 Kalman 版必须实现同样的复位，
   且**框尺寸/突变检测一起复位**。
3. **突变检测照旧**（`art-design.md:204`，`kSnapMult = 1.15 × 平滑后 bbox 对角线`）。
   Kalman 的协方差**不能**取代它 —— 瞬移（威龙式推进）在任何滤波器下都需要硬重置。

★ 平滑强度**照 α-β 的做法做成编译期常数，不做成用户旋钮**（`control-architecture.md:73-75`）：
"平滑强度与 Kp 耦合，两个一起调极容易调乱"。Kalman 的 Q/R 同理，
**不要把它们直接敞给用户**。

#### 3.5.4 Kalman 的稳定线影响 —— 可能要吃裕度

⚠️ **待实测（不要在设计阶段断言）**：Kalman 若比 α-β 引入**更大**的相位滞后，
则 §4.2 的 `g_crit` 裕度会变小 —— 因为 `g_crit` 是由**回路总死区 `d = 46ms`**
推导的，而滤波器滞后是回路延迟的一部分。

⇒ **验收要求**：Kalman 开启后，**必须在同一 Kp 下重跑 G1/G2 阶跃表**，
确认"Kp=30 稳"依然成立。若 Kalman 把可用 Kp 压到 25 以下，
则要用 §4.2 的公式**重新算** `d`，而不是沿用 46ms。
★ 这条**没有实测数据支撑，是设计阶段的假设**，明确标为待验证。

#### 3.5.5 Kalman 的存在理由 = 自适应（2026-09-17 第三轮）

★★ **用户明确了 Kalman 的定位：要的是"自适应"**（不同情况自动调平滑强度），
**不是"另一个配比的 α-β"**。

这条澄清**解决了 Kalman 的存在性危机**：α-β **本身就是**"位置+速度"两状态的稳态 Kalman，
所以若 Kalman 的 Q/R 是固定常数，它就只是 α-β 的一个马甲，没有理由多写一套。
**只有"自适应"能让它比 α-β多给出东西**（α-β 的 30ms 是编译期常数，写死的）。

**为什么不能靠"Q 随速度自适应"**：直觉是"目标快 ⇒ 更可能变向 ⇒ 给大 Q"，
但**零惯性场景下这条不成立** —— 变向随时可能发生，**与当前速度无关**（`art-design.md:37`）。
⇒ 自适应**只能走 R（测量噪声）这条路**。

##### 采用的形态：R ∝ 1/框面积

```
R = clamp( k / (w · h),  R_min,  R_max )
        ↑ 框面积(检测像素, 合法单位)      ↑ 上下限
```

**理由**：框越小 ⇒ 中心点估计的相对误差越大 ⇒ 该给更大的 R（更不信测量）⇒ 更平滑。
★ 这与 `art-design.md:340` 的既有结论一致（"近处减轻平滑提高响应，远处加重平滑压制噪声"）。

★★ **`R_max` 是结构性保护，不是调参项** —— 这是本形态最容易出事的地方：
面积是**二次**的，所以 R 随框尺寸变化极剧烈：

| 框尺寸 | 面积 | 相对 R |
|---|---|---|
| 100×200（近） | 20000 | 1.0 |
| 30×60（中） | 1800 | **11.1×** |
| 10×20（远） | 200 | **100×** |

⇒ 远处 R 可比近处大**两个数量级**，**过度平滑** ⇒ 远处目标响应慢到跟不住。
**而远处恰恰是需要跟枪的场景。** 没有 `R_max`，表现就是"准星慢慢飘过去"。
⇒ **必须夹上下限**：`R_min` 防近处滤波太弱（噪声进来），`R_max` 防远处滤波过头（跟不上）。

##### 与 D4-c（不做尺度调度）的关系 —— 不冲突，理由要留住

| | D4-c 删掉的尺度调度 | 本节的 R 自适应 |
|---|---|---|
| 调什么 | **增益** `Kp` | **平滑强度** |
| 用户的折中负担 | 用户要为远近折中一个 Kp | **不变** |
| 效果 | 近处易过冲 | 近处响应快、远处更稳 |

★ **关键区别**：D4-c 的问题是"用户要为一个参数折中远近"，
而 R 自适应**不增加用户的折中负担，反而减轻**（它自动处理了远近差异）。
★ 且 §3.2.2 那条"平滑强度与 Kp 耦合，两个一起调必乱"针对的是
**"不让用户手动调平滑强度"**，**不是"平滑强度不能自动变化"** —— 两者不矛盾。

##### 待实测（见 §7）

⚠️ **`k` / `R_min` / `R_max` 三个值没有任何实测依据。**
⚠️ **更根本的一条**：`art-design.md:340` 的前提是"远处噪声大"。
若本项目当前的检测质量本来就好（用户反馈"找色识别效果很好、准星不会很抖"），
则**远处加平滑的收益有限，而代价（响应慢）是实在的**。
⇒ **建议做成可选开关**：不合适关掉即可，**不要默认开启**。

## 4. L2 控制面

### 4.1 控制律 —— 纯反馈，无预测

★★ **不做前馈、不做预测、不做动力学模型**。这不是偏好，是三条独立证据的合流：

1. **零惯性系统否决动力学模型**（`art-design.md:37`，实测）：三角洲的移动接近阶跃，
   Kalman 假设匀速/匀加速，每次变向都预测错方向并超调。
2. **前馈需要 k̂，而 k̂ 估错 = 固定瞄偏**（`aimmagic-comparison.md` §6.7）：
   历史上 +6.2px @300px/s 就是这么来的。
3. **纯 P 回路的稳态滞后本来就只有几个像素**：`e_ss ≈ v/(Kp·k̂)`，
   不需要前馈去补（`control-architecture.md` §6.8）。

★ 而且第 1 条对**其他游戏同样成立或更宽松**：有惯性的引擎（穿越火线式老引擎）
也不会因为"不预测"而变差 —— 它只会让变向时的超调**更小**。**"不预测"是稳健选择的
上界**，这正是"通用"的含义。

### 4.2 稳定线 —— 唯一不能越过的约束

`docs/aiming-controller.md:318-331`，**实测反推**，两条独立证据：

```
链路死区 d = 46ms  (★ 实测，不是估算)
g_crit = 2·sin(π / (2(2d+1)))
120fps → d = 5.5 拍 → g_crit = 0.2602
→ Kp_equiv = g_crit / (dt · k̂) ≈ 52   (本机 k̂ ≈ 0.593)
```

**每条证据都别丢**：
1. Kp=100 时误差以 5.00Hz / 200ms 摆动 = 24 拍 → `d = 5.5` 拍 ≈ 46ms；
   同时 `g = Kp·dt·k̂ = 0.593 = 2.28×g_crit` —— 这解释了"Kp=30 稳、Kp=100 抽"。
2. 起手那几拍连发 259 个计数，而画面里的瞄点 50ms 纹丝不动。

★★★ **不许用"软件 E2E ≈ 11ms"**：它只量了程序内部采集→输出，
**漏掉 HID 固件、游戏帧更新、显示输出、采集卡缓冲**。用它会在速度估计里
混进 `k̂·Δu/dt` 的假速度。

★★ **D8（两套增益）之后这条线要算两遍**：`g_crit` 是**单方向**推出来的，
而 `Kp_x` 与 `Kp_y` 各自独立受它约束。若两者取值不同，两个方向的稳定裕度与
过冲量都不同 —— §5.3 的 UI 提示也因此从"一个比值"变成"两个比值"。
★ 起点：两者都先填 35（等价于历史单套行为），等 §7 的实测表出来再分开。

★ **D4-c 已取消尺度调度**，所以没有 `s_max` 这一侧了：稳定线直接约束 `Kp` 本身。
历史生产值 `Kp=35` 对应 `g/g_crit = 0.67`（`aiming-controller.md` §5 G1/G2 表），
**距离天花板还有约 1.5 倍余量，但过冲已达 43.56px** ——
所以实际可用窗口的上界**不是稳定性，是过冲**。

★★ **D4-d（一帧一次）与稳定线是同一件事的两面**：
`d = 46ms` 是在**控制节拍 = 检测节拍**的前提下测出来的。
若将来改成一帧多发（AimMagic 的 1kHz 内环），`d` 会变、`g_crit` 会变、
**整个 §5 的实测量表作废**。所以 D4-d 不只是节拍选择，它是**稳定线的前提**。

### 4.3 控制律与出口（2026-09-17 第三轮定稿）

#### 4.3.1 用户对控制器的要求（原文照录）

> 无论静态目标还是动态目标，都能够**快速拉枪到目标框内**，且**过冲不过目标框**；
> 无论敌人如何移动都能**保持准星在目标框内**，**距离锚点越近越好**
> （可以多预测超过锚点，也可以预测量不足远于锚点，但**越贴近越好**）。

翻译成控制语言，**这条要求排除了经典 PID 的默认形态**：

| 要求 | 控制含义 |
|---|---|
| 快速拉枪 | 上升时间短 ⇒ 误差大时出力猛 |
| **过冲不过框** | 超调有**硬上限**，不是"折中目标" |
| 敌人怎么动都跟得住 | 抗扰动 ⇒ 不能只靠 P |
| 越贴近越好 | 稳态误差小 ⇒ **需要 I**（用户已确认要消匀速滞后） |
| 多预测/不足都行 | ★ **允许非零稳态误差，只要在框内** |

★★ 最后一行**降低了优化的尖锐度**：目标不是"零误差"，是"在框内且尽量贴近"。
所以**不需要为消除最后几像素误差去冒稳定风险**。

#### 4.3.2 控制律（FK 结构，六个增益分方向）

```
── 每个方向 d ∈ {x, y} 各算一遍 ──

e_d    = anchor_d − cross_d                        (px, double)

P_d    = Kp_d · e_d

I_d   += Ki_d · e_d · dt   → clamp(±I_max_d)       积分
         if (e_d · e_prev_d < 0)                     ★ 按分量判反向
             I_d *= exp(−dt / τ_unwind)              ★ τ_unwind ≈ 30ms（待实测）

D_d    = Kd_d · LP(de_d) / dt                       ★ D 项单独轻低通

u_d    = dt · Kp_d · ( e_d + I_d + Kd_d·de_d/dt )

counts_d = lround(u_d + carry_d)                    唯一一次量化
carry_d  = (u_d + carry_d) − counts_d               余量【分方向】结转
```

**量纲核对**（单位法，§1）：`dt`=秒, `Kp_d`=计数/(像素·秒), `e_d`=像素,
`Ki_d`=1/秒 ⇒ `Ki_d·e_d·dt` 无量纲(乘在 `e_d` 上仍以像素计),
`Kd_d`=秒, `de_d/dt`=像素/秒 ⇒ 像素。括号内**三项同为像素**，乘 `dt·Kp_d` 得**计数** ✅
★ 六个增益**都带时间量纲** ⇒ **换帧率不用重调**。

**为什么是 FK 结构**（`u = dt·Kp·(e + I + Kd·de/dt)`，而不是三项各自独立乘增益）：
改 `Kp_d` 时三项**同比例缩放**，调参时不会互相打架 ——
这正是 §3.2.2 那条"参数耦合，两个一起调必乱"教训的直接应对。

#### 4.3.3 六条设计决定（第三轮，用户逐条确认）

| # | 决定 | 理由 |
|---|---|---|
| **P1** | **保留积分项**（消匀速滞后） | 纯 P 下匀速目标稳态滞后 `e_ss ≈ v/(Kp·k̂)`，取 Kp=35/k̂≈0.593/v=300px/s 得 **≈14.5px**（目标框宽 30px 时=落后半个框）。用户判定不可接受 |
| **P2** | **六个增益全部分方向**（`Kp_x/y`, `Ki_x/y`, `Kd_x/y`） | 用户明确要求全部区分，尽管调参量翻三倍 |
| **P3** | **积分回吐按分量判，且 τ 从 0.2s 收紧到几十毫秒** | ★ 见下方"为什么 0.2s 太慢" |
| **P4** | **抗饱和用 clamp**（非反算式） | 反算式需要整定 `Tt`，而 `Tt` **没有实测依据**；clamp 不需要额外参数，`I_max_d` 直接绑输出限幅 |
| **P5** | **`Kd` 单独加轻低通**（只作用于 D 项） | ★ 见下方"零惯性下的微分尖峰" |
| **P6** | **`cross` 不做平滑** | 用户判定找色质量好、枪械准星不抖（"不是上下乱跳那种"），`cross` 干净 ⇒ 不需要额外滤波 |

★★ **P3 的关键依据 —— 0.2s 对你的场景太慢**（这是用户提出的修正）：
`art-design.md:326` 记 AD 急停 **2-3 Hz** ⇒ **变向间隔 330-500ms**。
若回吐时间常数取 `0.2s`，则变向后要 200ms 才吐干净，而 330ms 后就又要变向 ——
**积分几乎永远处在"没吐干净"的状态，一直在拖后腿**。
且 `art-design.md:185` 记"急停后约 130ms `v_slow` 追上新方向"，
说明系统自然响应尺度是**百毫秒级**，`0.2s` 恰卡在这个尺度上。
⇒ **收紧到 30ms 起步**。⚠️ 但**具体值仍需实测**（见 §7），
不能把 30ms 当成已定论 —— 它只是比 0.2s 合理的起点。

★★ **P5 的关键依据 —— 零惯性下的微分尖峰**：
零惯性意味着**目标速度是阶跃的**（1 帧内从满速到零），而**阶跃的微分是冲激**。
⇒ 目标急停那一帧 `de` 出现巨大尖峰，`Kd` 会把准星**朝目标原来的运动方向**猛推一下 ——
而目标已经停了。**这正是 `art-design.md:12` 记的"AD 急停超调"的成因。**
⇒ 解决：`Kd` 作用在**低通后的 `de`** 上。
★ **这不违反"全链路只有一道滤波"（D7）**：它不是位置滤波，而是**微分器的实现细节** ——
真实微分器本来就带低通，否则物理不可实现。`LP()` **只影响 D 项**，不碰 `e`、不碰 P/I。

#### 4.3.4 默认值起点（安全原则）

六个增益的**默认值必须等于历史单套行为**，这样"改成六套"这个动作本身**不引入风险**：

```
Kp_x = Kp_y = 35        历史生产值
Ki_x = Ki_y = 0         纯 P 起步
Kd_x = Kd_y = 0         纯 P 起步
```

⇒ **默认行为 = 历史行为**。之后逐项实测再逐个打开（§7）。

★ **积分余量必须结转**（P6 之外的另一条老结论）：不结转的话，差 0.4px 的误差会被丢成 0 ——
那正是老实现"卡在差两像素不动"的来源。实测：0.6px 常驻误差在 1.667s 里
累出 20 counts，与 `Kp·e·T` 理论值一致。
★ **D8 之后 carry 必须分方向**（`carry_x` / `carry_y`）：否则水平方向的余量会被
垂直方向"借走"，产生**跨轴串扰**。

★★ **P2（六套增益）的连锁后果**：§4.2 的稳定线原本是**单方向单增益**推出来的，
现在六个增益各自影响裕度 —— `Kp_*` 各自受 `g_crit` 约束、`Ki_*` 各自引入相位滞后、
`Kd_*` 各自引入噪声放大。**§5.3 的 UI 提示必须相应扩充**（至少显示两个 `Kp_*` 的比值），
否则用户看不到自己在往稳定线上撞。

## 5. 配置面 —— 用户手填什么

### 5.1 旋钮表（2026-09-17 第三轮：六增益 + 限幅；死区已删除）

| 旋钮 | 单位 | 默认 | 作用 |
|---|---|---|---|
| **Kp_x** | 计数/(像素·秒) | **35** | 水平追踪增益（跟枪） |
| **Kp_y** | 计数/(像素·秒) | **35** | 垂直追踪增益（压枪） |
| **Ki_x** | 1/秒 | **0** | 水平积分（消匀速滞后） |
| **Ki_y** | 1/秒 | **0** | 垂直积分 |
| **Kd_x** | 秒 | **0** | 水平微分（压超调） |
| **Kd_y** | 秒 | **0** | 垂直微分 |
| ~~移动死区~~ | — | **已删除** | ★★ 见下 —— 被实测证伪，**整项移除** |
| 移动限幅 | 计数/拍 | 0 = 内置 200 | 输出上限 |

★★ **默认值全部等价于历史行为**（`Kp=35` / PI 项均 0）：
这样"从单套改成六套"这个动作**本身不改变任何行为**，是安全的起点。
之后逐项实测再打开（§7）。

★ **限幅保持共用一套**（不分方向）：它受驱动单次位移上限约束，是全局量。
**增益分方向是因为跟枪/压枪需求不同，限幅没有这个差异。**

★★ **死区已整项删除（2026-09-17 第三轮，用户决定）** ——
不是"默认 0 但保留旋钮"，而是**代码里不再有这个参数**。

理由：**它已经被实测证伪，且它的替代品已经在位**。

1. 死区的**唯一效果**是"误差小于阈值时完全不出力"，而那正是抖动的来源。
   `aimmagic-comparison.md` §3.1 实测：5px 死区意味着
   "误差小于 5px（离开要 7.5px）时控制器完全不出力"，
   而实测的 **10.2 次/秒"动/不动"翻转抖动就是这个极限环**。
2. 死区想解决的问题（末段不冲过头）**已经由 `pFullScalePx` 连续饱和负责** ——
   后者**连续且经过原点**，所以不存在"停了"这个状态。
3. ★★ **保留一个"能调但调了就坏"的旋钮，比没有更糟** ——
   它会让人以为死区是个可用的调参手段。这与仓库里
   "配了没反应的死旋钮"是同一类坑的**反面**，但同样是坑。

⇒ **若将来真机发现准星在锚点附近高频微动，先怀疑检测噪声与滤波，
不要重新引入死区**（记入 §7）。AimMagic 当年也是**没有死区**的，
它用增益调度解决末段问题 —— 本设计的对应物就是 `pFullScalePx`。

### 5.2 关于 k̂ —— 明确的取舍

★★ **本设计不把 k̂ 做成配置项**，理由有三条，**必须分清**（历史上这里被混成过一条）：

1. **k̂ 不可自动测量** —— 真的。双机架构下两条反推路径都已实测证伪
   （`aimmagic-comparison.md` §6.7：`anchor_observer` 的输出职责就是把它减掉，
   甩 469 计数只报出 31.1px；采集机的 `GetCursorPos` 是另一台机器）。**这条成立。**
2. **但 k̂ 可以用户手填** —— `aimmagic-comparison.md` §6.7.1（2026-09-15，标题即"更正"）
   已明确：AimMagic 的 `kalman_counts_per_pixel_x/y` **是普通用户设置项，不是测量值**，
   默认 1.0 = 不做换算，且"用户在自己游戏里知道灵敏度，这条路是通的"。
   **"不可测量"被错误地升级成了"不可存在"** —— 这是 `CLAUDE.md` 现有表述与
   `aimmagic-comparison.md` §6.7.1 的矛盾之处，以 §6.7.1 为准（它更晚、且是自我更正）。
3. **但 D3 下不需要它** —— 用户一套参数只配一套倍镜，换倍镜重调。
   于是 k̂ 全程**不需要出现在用户面前**，也不需要在控制器内部出现。

★ **为什么仍不做成配置项**：`config.h:68-78` 那段注释的理由**依然有效** ——
"保留这个键会**诱导**后来的人重新把 k̂ 接回控制器"。而 §5.2 第 3 条说明
**在 D3 下它没有用武之地**。所以结论是"不需要"，**不是"不合法"** ——
这个区别要留住：将来若真要做跨倍镜自适应，合法形式是**用户手填 k̂**，
而不是"程序标定"。

### 5.3 稳定线的 UI 表达（建议）

用户在 §5.1 调增益时，UI **实时把 `Kp_·dt·k̂ / g_crit` 的比值显示出来**
（k̂ 用内部常量），超过 1.0 就标红。★ **D8: 显示两个比值**（x 与 y 各一）。理由：稳定线是 `Kp × k̂` 的**乘积**，
用户只调 Kp 看不到这条线；换游戏/换倍镜后最容易踩的就是这里。
**这只是把已有的实测约束暴露出来，不引入新参数。**

★ **D4-c 之后这条更重要了**：尺度调度取消 ⇒ 没有"近处自动减增益"的兜底，
用户为远近折中的那个 Kp **会天然偏高**（要照顾远处），
所以它比过去更容易接近过冲/稳定边界。**这个提示从"nice to have"升级为必需。**

## 6. 逐游戏配置面 (L0) —— 通用性体现在"不用改控制器"

| 项 | 逐游戏？ | 说明 |
|---|---|---|
| 检测模型 + 类别桶 | ✅ | `Delete/Filter/Aim` + `aim_classes` 有序优先级 |
| 瞄点 `y_offset` | ✅ | `1=框顶 / 0.5=中心 / 0=框底`，`y_offset..y_offset_max` 为随机区间 |
| FOV 椭圆 `fovX/fovY` | ✅ | 检测像素的瞄准区直径 |
| 找色开关 | ✅ | per-hotkey 布尔；**只有三角洲用**（D1/D2） |
| 找色颜色面板 / ROI | ✅ | H/S/V 三段 + `rect_w/h` + `min_pixel_count` |
| **Kalman 开关** | ❌ | 游戏无关（§3.5）；若实测证明某游戏更适合，**说明它该按游戏选**，记下来 |
| **控制律 / 增益 / 稳定线** | ❌ | **完全游戏无关** |

★ 换游戏的标准动作 = **换模型 + 重配类别/瞄点/FOV + 重调五个旋钮**。
**控制器代码一行不改** —— 这就是"通用"的验收标准。

★ `y_offset` 的语义是**框内相对位置**（不是像素），所以它天然跨游戏：
人形目标"胸口"在任何游戏里都是 `y_offset ≈ 0.55`。

8. **`Kd` 低通时间常数 `τ_d`**（§4.3.3 P5）。同样**无实测依据** ——

## 9. 接线（2026-09-17 第三轮续，已落地）

§1~§8 是设计。本节记录**它被接进主程序时实际发生了什么** —— 含一个被抓出来的真 bug。

### 9.1 接线点

| 文件 | 职责 |
|---|---|
| `Apotheosis/runtime/aim_loop_config.cpp` | **纯映射**：`FlatConfig` → `control::ControllerConfig`。不依赖 OpenCV ⇒ 逻辑测试也编它 |
| `Apotheosis/runtime/aim_loop.{h,cpp}` | 运行期外壳：取检测 / 取准星 / 算 dt / 下发。**不写控制逻辑** |
| `Apotheosis/detector/trt_detector.cpp` | 检测发布**之后**调一次 `runtime::aim_loop::tick()` |
| `Apotheosis/runtime/inference_session.cpp` | `stop_locked()` 在 `join_all_locked()` **之后**调 `runtime::aim_loop::reset()` |
| `Apotheosis/config/config.{h,cpp}` | `HotkeyProfile` 新增 15 个 `ctl_*` 槽位（load/save/clamp 三处对齐） |
| `tests/control_wiring_test.cpp` | 接线回归，63 条断言 |

### 9.2 三条硬约束（接线时必须守）

1. **`tick()` 必须在 `detectionBuffer.mutex` 释放之后调** —— 它自己要拿那把锁拷检测，
   持锁调用会**自死锁**。
2. **`reset()` 必须在 `join_all_locked()` 之后** —— 检测线程是控制器的调用者，
   线程还在跑时 reset 会与 `tick()` 抢状态。
3. **边界上零单位换算** —— `control/` 的输出就是整数鼠标计数，与 `sendRawMove` 同单位。
   任何缩放都破坏"全链唯一一次量化"这条铁律。

### 9.3 ★★ 抓到的真 bug：`setConfig` 不转发 PID 配置

`AimController::setConfig()` 原实现是：

```cpp
void setConfig(const ControllerConfig& cfg) { cfg_ = cfg; }   // ← 只写 cfg_
```

但 `pid_` 是**独立对象**，持有自己的 `PidConfig` 副本。后果：

- 六个增益、时间常数、限幅、`pFullScalePx` **全部被忽略**；
- PID 一直用 `PidConfig` 的默认值跑；
- **界面/配置改了完全没反应，不报错、不留痕。**

这正是本仓库反复踩的**"死旋钮"**坑（与 `deadzonePx` 第一次的"声明了没人用"同类）。

**它是怎么被发现的**：接完线写 `control_wiring_test` 时，有一条断言是
"同一个误差下 `Kp` 大 ⇒ 输出大"。它失败了 —— 两组 Kp 给出**完全相同**的
`counts=(23,12)`。反推 `23 / (dt·e) = 34.5` ⇒ 实际用的是默认 `Kp=35`，
而不是传进去的 10。**没有这条断言，这个 bug 会一路带到真机上，
表现为"调参怎么调都没用"。**

修法：`setConfig` 里补 `pid_.setConfig(cfg.pid)`。

★ 教训与 §5.1 的死区一致：**"配置项存在" ≠ "配置项生效"**。
接线这类改动的验证重点不是"编译过"，而是**"改了值，输出真的变了"**。

### 9.4 接线回归（`control_wiring_test`，63 条断言）

覆盖：类别桶（含越界 classId ⇒ Delete 的安全默认）、15 个字段逐个搬到位、
新鲜度门禁恒为开，以及**"配置真的驱动控制"**三条：
Kp 影响输出、Delete 桶不产生控制、滞回倍数真的改变选靶结果。

**11 处反向变异全部变红**（含 9.3 那条 `setConfig` 不转发，以及 5 处 dt 门禁）。

★ **本用例初版写错过一次**：验证滞回的几何把准星直接放到了目标 B 上，
于是 A 被甩到 220px 外 —— 那是"锁定目标不见了"，**任何 k 都拦不住**，
不是滞回该拦的情形。改成"准星放在两目标之间、B 只近 1.75 倍"后才真正区分出
k=1.3（切）与 k=5.0（不切）。**测试的几何前提本身也要算一遍，不能想当然。**

### 9.5 安全闸门

★ `HotkeyProfile::ctl_enabled` **默认 false**。新增的控制链在真机验证过之前
**不该自己动鼠标**。打开后才经 `MouseThread::sendRawMove` 真的下发。

★ `aim_loop.cpp` **惰性构造** `MouseThread`（旧控制链删除后程序里已无别的实例），
`reset()` 时 join 它的 `moveWorker_` 并清空未发队列 —— 否则"停了之后还动一下"，
且重复启停会累积线程。

★ `tick()` 的异常在 `trt_detector.cpp` 里被 `try/catch` 吞掉：
控制层是新增的、没上过真机，**它出问题不该把整条推理管线拖下水**。
（刻意不打日志 —— 每帧一条会把日志刷爆。）

## 10. 前后端对齐（2026-09-17 第三轮续2）

接线（§9）之后发现"参数虽然能改，但界面和配置对不上"。本节记录**具体对不上在哪、怎么修的**。

### 10.1 最严重的一处：一个类别，两套桶

| | 谁维护 | 谁读 |
|---|---|---|
| `config.class_filters` | **`TargetPage`**（界面上点的） | `detector` 的 `applyDeleteBucketFilter` |
| `hotkeys[].aim_classes` | 只有 `config_bridge`，**单向** | **控制器** |

★★ **后果：用户在 TargetPage 上设的类别，控制器完全看不到。**
控制器读的 `aim_classes` 只能手改 ini —— 这就是"前后端对不上"的核心。

**修法**：控制器**两源都读**，合并规则：
1. 先按 `class_filters`（全局）铺桶
2. 再用 `aim_classes`（逐热键）把出现的类别**提升**为 `Aim`
3. `aim_classes` 里超出全局范围的补进桶数组
4. 两源都没有 ⇒ `Delete`（未知类别不瞄）

★ **只提升、不降级** —— 逐热键写"Aim"是更具体的意图，不该被全局 `Delete` 吃掉。

### 10.2 ★★ 隐含契约：`ClassBucket` 的数值

`toControllerConfig` 用 `static_cast<int>(cf.bucket)` 直接解释，依赖
`ClassBucket{Delete=0, Filter=1, Aim=2}` 的数值顺序与 `case` 标签一致。

**给枚举重排序会编译通过，但 Filter 静默变成 Aim。**
已在 `aim_loop.cpp` 加三行 `static_assert` 把它变成编译期错误
（★ 实测：重排序后确实编不过）。

### 10.3 6 项参数此前写死在代码里

`maxDistancePx` / 稳定器 5 项（`matchCenterRatio` / `areaRatioTol` / `kSnapMult` /
`minAspect` / `maxAspect`）/ `randomSeed` —— 它们**只存在于 `control/` 的默认值里，
没有配置槽位**，等于谁都调不了。已补 8 个配置槽位（load / clamp / save 三处对齐）。

### 10.4 `config.hotkeys[]` 曾经没有任何写入者

上一轮删控制链时把 `HotkeyPage` 也删了 —— **删过头了**。它带走的不只是死掉的瞄准参数，
还包括**热键列表管理**、`aim_classes` 编辑、准星找色开关、动态 FOV，
而这些背后是**活着的**子系统。

★★ **后果：`config.hotkeys[]` 从那时起没有任何写入者** ——
只在启动时从 ini 读一次，界面再也改不动它。

**修法**：重建为 **`AimSettingsPage`**（`qt_ui/pages/`），右栏 6 张卡：
触发按键 / 视野 FOV / 瞄准类别 / 准星找色 / 动态 FOV / **控制器参数（22 项）**。

★ 与旧页的区别：旧的 `触发卡 / BossAim卡 / 轨迹曲线卡 / 尺度调度卡` **全部不恢复** ——
它们描述的是已经不存在的那条链（PID-EventSync / 尺度调度 / 轨迹整形）。

### 10.5 ★★ 两个实测踩到的坑

**(1) `flattenProfile` 放在 `aim_loop.cpp` 里 = 零覆盖。**

它是 22 条逐字段赋值，而 `aim_loop.cpp` 要 include OpenCV/Windows，本机编不了。
反向变异时 *"不读 classFilters / 不回填 maxDistancePx"* 两条**全绿** ——
因为测试根本没编到那个文件。搬到 `aim_loop_config.cpp`（只依赖 `config.h`）后都会变红。

★★ **教训：变异"全绿"时先确认那条变异是否有效。**
我第一条变异写的是把 `flat.classFilters.reserve(...)` 换掉 ——
而 `reserve()` **只影响容量**，那是**无效变异**，不是覆盖缺口。
改成变异真正的写入循环（`emplace_back`）后立刻变红。

**(2) 前向声明写错命名空间。**

`struct HotkeyProfile;` 若写在 `namespace runtime::aim_loop { ... }` 里面，
就声明成了 `runtime::aim_loop::HotkeyProfile` —— 与 `config.h` 的 `::HotkeyProfile`
**是两个不同的类型**。编译报的却是 *"member access into incomplete type"*，
而且指向 `config.h`，**很误导**。必须放在文件顶部、命名空间**之外**。

### 10.6 回归

`tests/control_wiring_test.cpp` 现在 **120 条断言**，**13 处反向变异全部变红**，覆盖：

- `flattenProfile` 的 22 条逐字段搬运（★ 这是本轮补上的最大缺口）
- 类别桶两源合并（含"只提升不降级"、Filter 正反两面、数值契约）
- 新增 6 项参数真的进控制器、且真的改变行为
- dt 门禁（两层防线各管一段：公式层挡 `dt<=0`，策略层挡超上限）
- 端到端：TargetPage 设的 Filter **真的**不产生控制
