# PID-EventSync 档（移植 AimMagic 1.0.30 全链路）

> 2026-09-15 新增。开关：`aim_mode`（`[hotkey.N]` 段）。
> **`aim_mode = 0` 是默认值 = 现役纯反馈档**，本档引入的所有代码路径一行都不生效，
> 行为与本档存在之前逐位相同（有回归钉住：`tests/aim_eventsync_test.cpp` §[1]）。

本文回答三件事：**抄了什么**、**为什么某些东西没抄**、**怎么验证**。
R/E 语料：`Downloads\AimMagic_RE_extracted\AimMagic_RE\v1030\`（只读，未执行）。

## 1. 一句话

AimMagic 的「PID-EventSync」= **每推理帧消费一次** + **跟踪器给身份与速度** +
**每轨一份预测状态机** + PID。前两项已经搬进来了；第三项的**结构**搬进来了；
它的**数字**（以及两条需要「每计数像素」的换算链）**没有**搬 —— 见 §4。

```
推理帧 ──► 选靶(既有 selector) ──► 跟踪器(新) ──► 预测状态机(新) ──► PID(既有) ──► 计数
                                       │                  │                │
                                    身份/速度          每轨系数          在途补偿(计数域)
                                    IoU+最近邻       0.1爬 / 0.2落        u -= beta·N/W
```

误差注入点与现役档**完全相同**（提前量加在算误差之前），所以下游的尺度调度、
PID、在途补偿、亚量化保护、轨迹曲线**一行都没改**。

## 3. 与现役档的确切差别（只有三处结构差别 + 三件新增）

### 3.1 结构差别（状态住在哪）

1. **身份从哪来**：现役档用 selector 的 `target_generation`；EventSync 档用跟踪器
   的 `trackId`。跟踪器的 id 有粘滞性（IoU + 最近邻），所以它换号≈真换目标，于是
   「真换目标」判据不再需要 `跳变 ≥ 25px` 那道闸（`boss_aim.cpp` 里分支写明）。
2. **提前量住在哪**：现役档是一份**全局** `AimPredict` 状态（速度来自紧挨瞄点的
   α-β 滤波）；EventSync 档是**每条轨迹**一份系数与平滑状态（速度来自该轨迹的
   采样窗）。换目标不串状态，短暂漏检不清系数。
3. **丢目标时清不清**：现役档立即 `reset()` 控制器历史；EventSync 档**不清** ——
   轨迹真的死掉（`max_age` 到期，跟踪器换 id）才走「真换目标」复位。
   ★ 依据是 §3.4 的实测：身份变化占 7% 的帧 ⇒ 每秒清 8 次 ⇒ 积分永远攒不起来。

### 3.2 新增的三件（默认全部**不生效**）

| 件 | 默认 | 打开后改变什么 |
|---|---|---|
| ⑤ 在途换算链（像素域） | **关闭**（窗口 0） | 在途补偿从计数域换成 AM 的像素域做法；**强制关掉** `inflight_beta` |
| ⑥ 自运动项 | **关闭**（gain 0） | 提前量多一项正比于自身瞄准速度 |
| ③ 尺寸门限（速度域） | 生效 | 决定预测系数涨不涨；**第二条要求自己在动** |

★ 相同之处（**不要**以为换档把这些也换了）：PID 形式、时间归一化增益、
**计数域**在途补偿（默认路径）、亚量化保护、取整零头、尺度调度、轨迹曲线、
扳机 FSM —— 全部共用。

★★ **重要**：因为 ③ 的门限第二条要求"自己在动"，而 ⑥ 默认关闭时自身速度仍会被
喂进跟踪器（`setAimVelocity` 每拍都调，用锚点滤波器的速度）—— 所以
**目标在动 + 你在甩枪** 时系数照样能涨起来。⑥ 关掉不等于预测不工作。

## 4. k̂ 的更正（2026-09-15）—— 第一项与第二项已移植

> **本节推翻本文件早期版本的一整段结论。** 早期版本写着"在途补偿链与自运动项
> 不移植，因为它们都需要 k̂，而 k̂ 在双机架构下测不出来"。**那个结论一半是错的。**

### 4.1 复查语料的结论：AM 的 k̂ 是**用户手填的常量**，不是测量值

早期版本依据的是 `docs/aimmagic-comparison.md` §6.7，那一节追的是 **`pid_calib`**
（**甩枪档**的自动标定，`FUN_14006bf50`：发已知计数 → 读光标 → 反算 counts-per-pixel）。
那一节本身**没错** —— 它依赖单机架构（程序、光标、游戏同机），在本项目双机架构下
确实不成立。

**但它不适用于 EventSync 档。** 复查 `v1030/ANALYSIS_v1030.md` 后确认，EventSync 档
用的是另一个量：

| 键 | 默认 | 夹取范围 | 见 |
|---|---|---|---|
| `kalman_counts_per_pixel_x` | **1.0** | [0.001, 10000] | ANALYSIS 行 143 / 794 |
| `kalman_counts_per_pixel_y` | **1.0** | [0.001, 10000] | ANALYSIS 行 144 / 795 |

它在代码里的**全部用途**就是一个带下限的除数（`FUN_140067000` 行 1172–1209）：

```c
// 行 1187-1188: 发送环窗口内把计数求和(窗口下界 = now − mouse_effect_delay_ms)
dVar56 += (double)(int)plVar33[1];       // Σ dx (计数)
dVar57 += (double)*(int*)(plVar33+0xc);  // Σ dy (计数)
// 行 1198-1205: 取倒数前先夹下限 DAT_1401f8000(防除零)
dVar50 = max(counts_per_pixel_y, DAT_1401f8000);
dVar51 = max(counts_per_pixel_x, DAT_1401f8000);
// 行 1208-1209: 换算成【像素】, 送进预测器与误差合成
*(double*)(puVar40+0x28) = dVar57 / dVar50;   // y 像素
*(double*)(puVar40+0x20) = dVar56 / dVar51;   // x 像素
```

**没有任何在线估计、观测器或最小二乘。** 配置槽位 `0x90/0x94` → 流水线结构体
`0xea8/0xeb0` → `0x520/0x528`（`FUN_140067000` 行 366–367 逐字段拷贝），就是一个
用户填的常量。

> **默认 1.0 的语义是"1 计数 = 1 像素"，也就是不做换算。**
> AM 把"k̂ 填错"的风险**交给用户承担**，而且它单机架构下用户填的就是自己游戏的真实值。
> 本项目用户**同样可以手填**（他在自己游戏里知道灵敏度），所以这条路是通的 ——
> **不能让程序自动测量**（那才是不成立的部分）。

### 4.2 ⑤ 在途补偿链（已移植）

落点：`mouse/aim_tracker.h` 的 `noteSend()` / `inflightPixels()`，
误差合成在 `mouse/boss_aim.cpp`。

| AM | 本实现 | 说明 |
|---|---|---|
| 时间戳窗口（`now − mouse_effect_delay_ms`） | **定长环形缓冲** | 与 `aim_pid.h` 计数域补偿同一套做法：可复现、不依赖时钟抖动 |
| 窗口内计数**求和** | 窗口内计数求和 | 同 |
| `÷ counts_per_pixel` | `÷ (k̂ 或 0.001)` | 同，含 AM 的防除零夹取 |
| 直接送进误差合成 | `÷ 窗口拍数` 再送 | ★ **必要的偏差**，见下 |

> ★ **为什么必须除以窗口拍数**：AM 求的是"一个延迟窗口内发出去的总量"，
> 而我们要扣的是"本拍该扣多少"。不除会导致同一批计数被重复扣 W 次 ——
> 这正是本项目在途补偿的实测教训（1000fps 尾段 8.30px，见 CLAUDE.md 要点②）。
> 除完之后与 `u -= beta·N/W` **完全同构**，只是量纲从计数换成了像素。

★★ **与计数域补偿互斥（代码强制）**：两者是同一个 Smith 预测器的两种做法。
`AimEngine::tick()` 在 `aim_mode == 1` 时**自动把 `inflight_beta` 置 0**。
同时开会把同一批在途指令扣两次 = 过补偿 = **正反馈发散**。

默认**关闭**（`esync_inflight_window_ms = 0`）：打开它等于把在途补偿从"不需要 k̂ 的
计数域"换成"需要用户填对 k̂ 的像素域"。已验证的老路子是前者。

### 4.3 ⑥ 自运动项（已移植，但默认关闭 + 三道夹取）

AM 的预测偏移里有一项吃 `runtime+0xC04`（自身瞄准速度）。这一类自运动补偿正是本项目
在 `1a5a792` 删掉的 `predictive_controller`：它把**像素/计数标定增益放在反馈回路内部**，
标定不准就在锚点附近每拍反向极限环（不是抖动，是持续来回摆）。

**移植时保留 AM 的形状，但加三道夹取：**

1. `esync_self_motion_gain` **默认 0**（不生效）；
2. 幅度硬夹取 **±1.0**（`kSelfMotionMaxGain`）；
3. 输出仍走**同一个硬像素上限**，且**两项相加之后**再夹一次（否则同时开两项可突破上限）。

★ 用法上必须说清楚：AM 的预测系数有**第二个条件**（见 §4.4），
**自己没在动时系数只落不涨**。所以不开这一项时，即使目标在动，系数也涨不起来。

### 4.4 ③ 尺寸门限（已改成**速度域**）

AM 的判据是（`FUN_14006e470` 行 119–146，一条 if/else）：

```
条件(涨) =  位移 > max(30, 0.75×size) × (系数×1.5 + 1)     ← ① 目标动得够快
         || |自身瞄准速度| <= fVar9(≈3.5057 px/帧)          ← ② 自己没在动
```

★★ **注意 ② 是"或"，而且它是"落"那一支的条件** —— 原文：
`if (① <= 位移 || ② <= 自身速度) { 系数 -= 0.2 } else { 系数 += 0.1 }`。
也就是说：**只有"目标位移够大 且 自己也在动"时系数才涨。**

原文 ① 吃的是**本帧位移**（像素）。照搬到本项目**不能工作**：它隐含假设"相邻推理帧
之间的位移"与框宽同量级，而 120fps 下 300px/s 的目标每帧只走 2.5px，60px 宽的框门限
却是 45~112px —— 差 20~45 倍，**门限恒不成立，系数永远爬不上去，预测被静默关掉**
（比不移植更糟：用户会以为"预测坏了"，而代码里没有任何报错）。

**改法：只换量纲，不换常数。** 把"每帧位移"换成"每秒位移"（÷ 帧间隔）：

```
v > max(30px, 0.75×框宽) × (1 + 1.5×系数) ÷ 帧间隔
自身速度 > 3.5057 ÷ 帧间隔
```

三个常数（30 / 0.75 / 1.5）与自身的 3.5057 **一个都没改**，只是把帧率从判据里显式
拿出来 —— 换任何帧率都还原 AM 的原意。

> ★ 两个条件都接上之后，这个 FSM 的手感是：**你在甩枪、目标也在动 → 加提前量；
> 目标停下或你停下 → 立刻收手**。这也解释了 AM 为什么叫它"自摇领先量"。

### 4.5 仍未移植项

- **轴锁**（`FUN_140057df0`）：输出侧整形，本项目已有 `mouse/aim_path.h` 承担同类职责。
- **`aim_follow_x/y` 输出增益**（`FUN_140067000` 行 1269）：与 `pidf_kp_*` 重复，
  本项目用 PID 增益表达。
- **`pid_calib` 自动标定**：见 §4.1，那条路依赖单机架构，**仍然不成立**。
  本档的 k̂ 由用户手填，不做自动测量。

## 6. 配置槽位

全部是**新增键**，所以 **`pidf_mapping_version` 不推进**（版本号是"旧槽位语义变更"
的迁移机制，这里没有任何旧槽位被改语义）。老配置缺这些键 ⇒ 取结构体默认 ⇒
`aim_mode = 0` ⇒ 行为逐位不变（`config_migration_test` §[7] 钉住这条）。

| 键 | 默认 | 含义 |
|---|---|---|
| `aim_mode` | 0 | 0 = 现役纯反馈档；1 = EventSync 档 |
| `esync_min_hits` | 3 | 连续命中多少帧算"确认轨迹"（AM 原值） |
| `esync_max_age` | 5 | 漏帧多少帧后删除轨迹 = 滑行窗口（AM 原值） |
| `esync_assoc_radius_px` | 80 | 关联最近邻门限（框心距离） |
| `esync_assoc_iou` | 0.20 | 与锁定轨迹的 IoU 门限（0 = 只靠最近邻） |
| `esync_vel_window_ms` | 100 | 速度采样窗；0 = 逐帧重算（不推荐） |
| `esync_counts_per_pixel_x` | **1.0** | ⑤ 每计数像素（AM 的 `kalman_counts_per_pixel_x`）。1.0 = 不换算 |
| `esync_counts_per_pixel_y` | **1.0** | ⑤ 同上（Y 轴） |
| `esync_inflight_window_ms` | **0** | ⑤ 在途换算窗；**0 = 整条链关闭**。上限硬夹 46ms（死区） |
| `esync_inflight_beta` | **1.0** | ⑤ 在途换算强度（AM 无额外增益，= 1.0）。夹 [0, 4] |
| `esync_self_motion_gain` | **0.0** | ⑥ 自运动补偿增益；**0 = 关闭**。夹 ±1.0 |

预测强度、尺寸区间、硬上限、噪声门与现役档**共用同一组槽位**（`pidf_predict_*`）——
换档不该让用户把提前量重填一遍，而且这样两个档的预测强度可以直接对照，
差别只剩下"状态住在哪"。

★★ **`esync_inflight_window_ms > 0` 时会自动关掉 `pidf_inflight_beta`**（代码强制，
见 `boss_aim.cpp`）。两者是同一个 Smith 预测器的两种做法，同开 = 扣两次 = 发散。

UI：`qt_ui/pages/HotkeyPage.cpp` 的「瞄准档位（PID-EventSync）」一段。

**没有验证到的**（必须说清）：

- **实机手感**。逻辑测试用假游戏（世界速度 + 46ms 延迟 + 框心整数量化），
  它证明的是"有界、收敛、降级等价"，**不证明**实机上比现役档更好。
- **`boss_aim.cpp` 的接线本身**。闭环测试手搭的是同一条算式，不含 selector；
  接线正确性只由主程序编译通过保证。
- **⑤ 在途换算链的实机效果 —— 而且它依赖用户填对 k̂。** 逻辑测试证明了"比例对、
  有界、窗口能被夹住、关闭时逐位一致"，但 **k̂ 填错的后果没有被测试覆盖** ——
  因为那取决于用户的真实灵敏度，程序无从判断。用法上建议：**先只用计数域那项**
  （那是已验证的路子），想完整复刻 AM 形态时再打开 ⑤ 并把 k̂ 填对。
- **`use_prediction_tick` 与 EventSync 的互斥**只在代码分支上保证，没有跑过
  同时开启的实机对照。

## 8. 写这个跟踪器时踩的坑（都是回归抓出来的）

★★★ **「关联不上就接管锁定」在一帧多候选时会让【最后喂进来的那个】赢。**
`offer()` 的三级关联里，③ 新建轨迹必须顺便接管锁定（否则两个不同目标会串成
同一个 id，"换目标复位"永不触发）。但接口允许一帧喂多个候选，于是每个"关联不上"
的候选都去抢锁 ⇒ 本帧**最后**一个候选赢。而调用方的意图恰恰是"先喂的优先级高"。

实测症状（`aim_tracker_test` §[2b]）：两个远隔目标 A(400,300) / B(900,300) 交替出现，
先喂 A 后喂 B，结果锁定一直停在 **B** 上，A 死了以后 id 完全没变 —— 也就是
"换目标"这件事被静默吞掉了。

修法：加 `lock_taken_this_frame_`，`beginFrame()` 清零，三个分支都尊重它
（一帧只认第一次定下的身份）。修完 A→B 的接管 id 从 `2→2`（错）变成 `1→2`（对）。

★★ **`min_hits` 绝不能挡锁定。** 最初的 `locked()` 要求 `confirmed`，等价于
"目标刚露头 3 帧内完全锁不上"（`aimmagic-port-spec.md` §2.3 实测过这个坑）。
现在 `locked()` 不看 confirmed；`min_hits` 只用于遥测标记与"锁定轨迹死后能否
接管"。

★★ **速度不能逐帧差分。** 8.3ms 的相邻两框心差分把量化噪声放大成几百 px/s 的
假速度（静止目标实测噪声 p99=46px/s）。所以速度必须走采样窗并**跨帧持有**。
★ 顺带一个语义细节：噪声门判据必须用**严格大于**（`speed > floor`），
否则门限填 0 时"任何速度都算动"，目标停下来了系数还挂在 1，提前量永不收手
（这条也是回归抓出来的）。

★★ **系数 FSM 只在 `predictionLead()` 里推进。** 调用方每拍必须调它一次，
**且只调一次** —— 调两次等于一拍走两步（爬升会看到 0.2/帧）。
`boss_aim.cpp` 的接线正是每拍一次。

## 9. 2026-09-15 第二轮（移植 ⑤⑥ + ③ 改速度域）踩的坑

★★★ **"这个量测不出来"必须先问"它到底是测的还是填的"。**
我第一轮把 `pid_calib`（甩枪档的**自动标定**，确实依赖单机架构、确实不成立）的结论
直接套到了 EventSync 档，于是判定"k̂ 不可得 ⇒ ⑤⑥ 不能抄"。**这是错的** ——
EventSync 档用的是 `kalman_counts_per_pixel_x/y`，一个**用户填的常量**。
两个量同名（都是"每计数像素"）、来源完全不同（一个在线反算、一个手填），
混为一谈就得出一个过于保守的结论，白白砍掉两项功能。

> **教训**：写"某功能不可实现"的结论时，必须指名道姓写出**是哪个函数/哪个槽位**
> 让它不可实现。如果只能写出"这个量测不出来"而说不出"AM 在**这一档**是怎么拿到的"，
> 那个结论就还没查到底。

★★★ **双条件门里藏着一个"或"，我漏了整整一轮。**
`FUN_14006e470` 行 133–135 的完整条件是
`if (门限 <= 目标位移 || |自身速度| <= 3.5px/帧) { 落 } else { 涨 }`。
我第一轮只抄了第一条，于是把它当成"目标在动就涨"。

**漏掉第二条的后果是双向的**：
- 在**本档**：预测会在"自己在甩枪但目标静止"时错误地涨起来（多发提前量）；
- 反过来接自运动项时：不喂自身速度 ⇒ 系数**永远不涨** ⇒ 我们会以为"预测坏了"。
  实测就是这样：FSM 用例里 `vel=(0,0) valid=0`、系数恒 0，查了半天才发现
  ① 目标每帧走 166px 超过 80px 关联门限（每帧新建轨迹、速度窗攒不满）
  ② 自身速度压根没接。

> **教训**：反汇编里的复合条件要看**完整的那一条 if**，包括 `||` 后面那一半；
> 只看第一个比较就下结论，会把一个"与"误读成充分条件。

★★ **`predictionLead()` 里的早退分支会连带跳过新加的功能。**
它原本有两处早退：`!t->confirmed`（错，见上）和 `size_w <= 0`（形态外）。
自运动项加进去之后，第二处早退会把**与框大小无关**的自运动补偿也一起吃掉。
修法：形态外分支里仍然计算自运动项。

> **教训**：往一个"分层计算 + 早退"的函数里加新项时，要检查**每一处 `return`
> 是否应该带上新项**；这类 bug 的测试症状是"功能在某个参数区间静默失效"。

★★ **`min_hits`（confirmed）不该挡预测，和它不该挡锁定是同一条理由。**
`predictionLead()` 原本 `!t->confirmed` 直接返回 false ⇒ 目标刚露头的头 3 帧
预测不工作。AM 的预测状态机**没有 confirmed 这个概念**（它每帧都推进系数）。
已在同一轮一并修掉。

★ **测试用例本身也会"跟丢"。** 用 20000px/s 的目标测 FSM 时，每帧位移 166px
超过默认 80px 关联门限 ⇒ 每帧新建轨迹 ⇒ 速度窗永远攒不满 ⇒ `vel_valid` 恒为 0。
这不是代码 bug，是"目标快到跟丢"的物理必然 —— 但**测试必须先把这个前提写清楚**
（放宽 `assoc_radius_px`），否则测的是"跟丢了"而不是"门限不成立"。

★ **"逐位一致"的前提随功能增加而变化。** 第一轮 EventSync 只有预测一件新东西，
所以"关预测 ⇒ 逐位一致"。现在有三件，前提必须改成**三件全关**，
而且每一件都要有**反向验证**（开着必须不同），否则那条一致性断言会随功能增长
慢慢变成空转。本轮给 ⑤⑥ 各补了一条反向验证。
