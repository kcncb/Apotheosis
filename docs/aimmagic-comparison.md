## 0. 一句话结论

**三个能力差在三个完全不同的地方，不是一个 PID 调参问题：**

| 你抱怨的 | AimMagic 的做法 | 本方的做法 | 性质 |
|---|---|---|---|
| **扳机很快** | 命中判定与按键执行在**同一次 tick 内串行**（中间不跨帧）；延迟门初值 0 ⇒ **首枪永远零延迟**；判定用**已被预测改写的框心** | 每检测帧评估一次；判定用**滤波后的锚点 + 限速/惯性/120 ms 保持的枢轴**；两个门禁口径不一致，实测 30% 的帧互相打架 | 架构差 |
| **压枪很好** | 有**独立的「后坐力控制」模块 + 独立线程**：录制/回放 `{rel_x,rel_y,delay_ms}` 弹道表，**开环前馈**，与自瞄完全并行 | **完全没有这个模块**。压枪只能靠 PID 误差反馈去追被抬起的准星，稳态误差 ≈ `v_recoil/(k·Kp_y)` ≈ 12 px | 缺功能 |
| **瞄准更好** | 控制器吃**未滤波的框心/瞄点**，**无死区**；末段靠 `kp_floor` 增益调度；跨帧持有速度与积分 | 5 px 死区；`anchor_filter_ms=0` 让 **X 轴速度恒为 0**；换目标清积分与前馈；末段靠死区而非增益调度 | 架构差 |

### 一个必须先说清的修正

**【实测 · 反编译】** 从 `v1030/ANALYSIS_v1030.md` §6.3 读到本机 AimMagic 的实际配置值是
`flick_scale_x/y = 3.225806`、`flick_damping = 0.06` —— 这两个是 **Scale 控制器** 的参数，
不是 PID 档案的。也就是说**你现在跑的 AimMagic 用的是控制器类型 `Scale`**，
而 Scale 是**事件驱动**的（"每个最新推理结果只消费一次，因此总位移不再依赖 1000Hz PID 循环"）。

**结论修正**：在 Scale/EventSync 下，AimMagic 的**瞄准输出同样是"一帧一次"**，
和本方的节拍一样（§1 里那个 1 kHz 内环只对 `PID-FrameSync` 档成立）。
所以**节拍不是它瞄得更好的主要原因**，真正的原因是另外三条：

1. **压枪不在回路里**（独立线程 + 开环弹道表）—— 这是决定性的，也是你缺的整个模块；
2. **判定与控制吃的是未滤波信号，且无死区**；
3. **末段用增益调度而不是死区**（§3.1 / §3.2）。

顺带算一下它 Scale 的有效增益：`3.225806 × 0.06 = 0.1935 counts / 像素误差`，纯比例、无积分无微分。
而本机 X 轴每帧是 `dt·Kp = 0.0083 × 100 = 0.83 counts/像素` —— **本方每帧给出的位移是它的 4.3 倍**。
所以"它瞄得更准"**不是靠更大的增益**，恰恰相反：它靠的是**不丢精度**（无死区、不过滤、积分不被清）。

§1 的节拍分析仍然有效、仍然值得做（它对 `PID-FrameSync` 档和未来的 1 kHz 内核是必要的），
但请把它排在 P1，而不是 P0。

## 1. 次根本的一条：控制节拍（control cadence）

> 读本节前请先看 §0 的修正：本条对 `PID-FrameSync` 档成立，对你当前在跑的 `Scale` 档不成立。
> 保留它是因为它是本方"加不动增益"的直接原因，而且值得作为 P1 修复。

### 1.1 AimMagic：`PID-FrameSync` 档是 1 kHz 控制线程，与推理解耦

**【代码证据】** `v1030/ANALYSIS_v1030.md` §6.2（行 655-687）原文：

```c
/* 普通路径：定时等待 1 ms，即 ~1000 Hz PID 迭代 */
lVar37 = now_ns() + 1000000;
while (!*(char *)(lVar17 + 0xe40)) {          // 0xe40 = 停止请求
    lVar16 = now_ns();
    if (lVar37 <= lVar16) break;
    FUN_1401d9c74(lVar17 + 0xdf8, lVar45, uVar14);   // timed wait(condvar, 1ms)
}
```

推理线程把结果交给控制线程；控制线程**不等下一帧推理**，自己 1 ms 一拍地迭代。
QML 侧对另一条路径的说明反过来印证了这个分档（`qml_z/当前_PID_配置档位*.qml:153`）：

> "EventSync 每次只消费最新的一帧推理结果并发送一次 PID 位移，**不会在 1000 Hz 输出循环中持续复用该结果**。"

也就是说：**`PID-FrameSync` 的高频内环会持续复用最新一帧的框做预测推进**，
而 `EventSync` / `Scale` 降级成"一帧一次"。

### 1.2 本方：控制节拍 = 检测节拍

**【代码证据】** `runtime/mouse_thread_loop.cpp:637-666`：

```cpp
if (!hasNewDetection)
{
    ...
    // ── 控制节拍: 没有新检测就跳过, 与老实现一致 ──────────────────────
    // 老 AVA 链路(以及它的 PIDF)是【每个新检测 tick 一次】。
    ...
    continue;
}
```

而 `dt` 就是两次 tick 的墙钟间隔（同文件 802-806 行）。在本机配置下采集 120 fps、模型 416，
所以**控制器、扳机、输出全部只有 ≤120 Hz**，一拍 8.33 ms。

### 1.3 差在哪（不是"总位移"，是相位裕度）

`u = dt·Kp·[…]` 这个形式是时间归一化的，所以**同样增益下每秒总位移与拍率无关** —— 这一点本方做对了。
差的是**采样滞后**：

- 闭环延迟 ≈ 采集卡前延迟 + 推理 + tick + HID/游戏/显示。当时按 `capture_age_offset_ms = 50`
  这个手填估计值，加推理与显示，实际按 50~60 ms 量级算。
  > **【2026-09-13 更新】`capture_age_offset_ms` 本身已删除**（它是猜不是测，且控制器纯反馈、
  > 不吃延迟估计）。上面这个 50~60ms 是**当时的估算口径**，不是实测值；真实延迟以延迟探针
  > 的日志为准（它给出的是下界，不含采集卡内部 HDMI→USB 流水线）。
- 本方采样周期 8.33 ms；
- AimMagic 采样周期 1 ms。

采样保持引入的相位滞后是 `ω·T/2`。在同一个穿越频率上，8.33 ms 的采样滞后是 1 ms 的 **8.3 倍**。
结果是：**AimMagic 可以用比本方高得多的回路增益而不自激**，所以它"跟手"；本方为了不抖只能把增益压低
（本机 Y 轴 `pidf_kp_y = 40`，只有 X 轴 100 的 40%），低了就"顶不住后坐力"。

**【推断】** 这解释了你现在的现象组合：X 轴快、Y 轴闷；一加 Y 轴增益就开始抖/画圈。
这不是调参水平问题，是拍率缺少裕度。

### 1.4 改法（不需要重写控制器）

把控制线程从"检测驱动"改成"时间驱动 + 有界预测"：

1. 把 `mouse_thread_loop` 的 `if (!hasNewDetection) … continue;` 换成**独立 1 kHz（或 500 Hz）节拍**。
   没有新检测时**不要重置状态**，用 `AnchorObserver` 走 `use_measurement=false` 的**预测分支**
   （`anchor_observer.h:126-132` 已经实现了这条路径），速度继续推进锚点。
2. 已经删掉的"独立控制时钟"（记录在 `docs/control-architecture.md:62-74`）正是这个思路，
   当时删它的理由是"dt 按检测间隔算会改变 D 项/前馈学习率" —— 那是个实现细节，
   用**控制拍自己的 dt** 就解决了，不需要把整条路径删掉。
3. 内环节拍与输出节拍要分开：内环 1 kHz 迭代，但**每 N 拍合并发一次串口**（见 §4），
   否则 1 kHz 打串口会自己把写延迟堆成新的死区。
4. **`timeBeginPeriod(1)` 本项目已经做对了** —— `Apotheosis.cpp:225` 启动时调、`:517` 退出时还。
   这一条不能省：Windows 上条件变量定时等待的默认粒度约 15.6 ms，
   不提高分辨率的话"1 ms 定时"会退化成 ~64 Hz，整个 1 kHz 内环的设计就不成立
   （AimMagic 的导入表里同样有 `timeBeginPeriod`）。

## 2. 压枪：它有一个你没有的模块

### 2.1 AimMagic 的「后坐力控制」是独立子系统，而且是**独立线程**

**【代码证据 · 反编译闭合】** 压枪的生产者与录制器是 `FUN_140085410`（869 行），
anchor 串为 `[aim_color, record_enabled, record_sample_ms, record_fixed_interval, record_source,
gate_aim_key_down, gate_target_locked, gate_target_on_screen]`，
由主 tick `FUN_14007e5c0` **行 404 每 tick 调用一次**。

弹道步结构 = **12 字节 `{int rel_x; int rel_y; int delay_ms}`**（行 696-720，
源元素步长 0x28、取 `[0]`/`[5]`/`[10]`）。
成品向量发布到 `runtime+0xA38`（begin/end/cap = `0xA38/0xA40/0xA48`）+ 就绪位 `runtime+0xA31 = 1`，
然后唤醒**独立的压枪线程**（信号量 `+0x9E8`、停止位 `+0xA30`）。

**【代码证据 · 线程身份已闭合】** `FUN_140077f40` 行 803-873 创建两个线程：

```c
行 814  (*DAT_1401f08e0)(0,0, FUN_140062910, puVar16);   // 瞄准线程
行 852  (*DAT_1401f08e0)(0,0, FUN_1400629a0, puVar23);   // 压枪线程 → handle +0x988 / id +0x990
```

两个 trampoline 已直接读文件复核：

- `FUN_140062910` → `FUN_140067000` ⇒ **`FUN_140067000` 就是瞄准工作线程体本身**
  （它内部 `runtime+0xDF8` 那个条件变量等待就是这条线程自己的节拍器），
  不是"被谁每拍调用的库函数"。
- `FUN_1400629a0` → **`FUN_14006b630`** ⇒ **压枪线程体 = `FUN_14006b630`**
  （RVA `0x14006b630-0x14006ba1b`，约 1003 字节）。它**自己不含任何 anchor 字符串**，
  所以按字符串永远搜不到；线程名来自它的 MSVC EH catch handler（`FUN_1401e0180` 的 `"recoil worker: "`）。

**这一点极其重要**：压枪的回放在**自己的线程上按弹道表里的 `delay_ms` 走时**，
既不受检测帧率限制、也不受自瞄控制回路限制。

**【代码证据 · 回放循环 `FUN_14006b630`】**

```asm
6b6e8  _Cnd_wait (runtime+0x9e8, mutex 0x998)     ; 空闲等唤醒
6b745  xchg byte [runtime+0xa31], 0               ; 原子清 ready
6b74f  copy vector<step> (0xa38/0xa40/0xa48) → 本地快照
6b787  movzx ebx, byte [runtime+0xa50]            ; ★ move_mode "merge" 标志
6b796  解锁 runtime+0x998                          ; ★ 先放锁再发送
6b7a0  for (step = begin; step != end; step += 0xc); // 12 字节步
6b7af    if (runtime+0xa32 抢占 || runtime+0xa30 停止) break;
6b7e9    call FUN_140077200                        ; ★ 发射
6b823    delay_ms = step[+8] → deadline = now + delay*1e6
6b953    FUN_1401d9c74(runtime+0x9e8, mutex, ms)    ; ★ 定时条件变量等待（不是 Sleep）
```

**每一步的 `delay_ms` 用的是"定时条件变量"而不是 `Sleep`** —— 抢占 / 停止 / 新弹道上膛
都能**立即打断**当前等待。这是一个直接可抄的实现要点。

**【代码证据 · `move_mode` 的真实语义 —— 单流合并，不是两条并行流】**

| 模式 | 行为 |
|---|---|
| `separate`（默认） | 每步**立即**独立发一次 HID 移动，label = `"recoil"` |
| `merge` | 位移**原子累加**到 `runtime+0xA78`(dx)/`+0xA7C`(dy)，并 `notify runtime+0xDF8`（**瞄准线程的条件变量**）；瞄准线程在自己 tick 里原子取走清零（`FUN_140067000` 行 1756-1763），**加进本拍输出之后**（1759/1764-1765），最后合成路径**每段发一次** label=`"aim"` 的合并移动（1865-1924） |
| `merge` 但自瞄未激活（`runtime+0xA80 == 0`） | **静默退化**为独立的 `"recoil"` 发送（不丢位移） |

⇒ **压枪位移注入在控制器（PID / Scale）之后，绝不进入自瞄误差。**
两条回路不会互相积分成振荡 —— 这是"压枪稳、瞄还准"能同时成立的**结构性原因**。
而且 merge 会**强制多跑一次瞄准 tick**（`FUN_140067000` 行 326-327 的事件驱动等待谓词
显式包含 `+0xA78/+0xA7C != 0`），所以合并不会因为"水位没变"而丢一拍。

**【代码证据 · QML】** `qml_z/默认弹道下拉模型_顶部_无默认___弹道组__与组管理下拉分离_.qml`：

| 配置键 | 中文标签 | 默认 | 含义 |
|---|---|---|---|
| `recoil_enabled` | 启用后坐力控制 | false | 总开关（scope=1，Group 级） |
| `gate_right_down` | 门控: 右键按下 | false | 启动条件 |
| `gate_aim_key_down` | 门控: 自瞄按键按下 | false | 启动条件 |
| `gate_target_locked` | 门控: 有目标被锁定 | false | 启动条件 |
| `gate_target_on_screen` | 门控: 画面有目标 | false | 启动条件 |
| `move_mode` | 单独移动 / 合并移动 | separate | **后坐力位移与自瞄位移是否合并成一次输出** |
| `record_enabled` | 启用录制 | false | |
| `record_source` | 录制方式：自瞄移动 / 光流 / 准星找色 | aim | **用哪一种观测来量后坐力** |

门控函数 `FUN_14005f510`（21 行）把五个开关**全部 AND** 起来；
`move_mode` 在行 151-163 解析（"separate"/"merge"）。

UI 原文（同文件 175-176、203-204 行）：

> "每个组保存一条**相对移动序列**，可在下方按「一行一个点」编辑。"
> "不按自瞄键直接左键时走此弹道；按了自瞄键则严格按该键绑定走（互不影响）。"

**注意一个反证**：`smart_recoil_enabled`（"智能压枪"，在找色页）是**死键** ——
只在 anchor 串里存在，找色函数 `FUN_140080430` 里没有任何 recoil/`0x534`/`0x538` 消费点。
也就是说它的压枪**完全不是**"用找色做闭环"，就是纯开环弹道回放。

### 2.2 本方的压枪现状

**【代码证据】** 全仓库检索 `recoil|后坐力`，只有注释：

- `mouse/boss_aim.cpp:231-233`：「积分(Ti=1s)永远攒不起来 → **顶不住后坐力这种持续推力 → 压枪压不住**(实测 38% 的帧 |ey|>10px)」
- `runtime/mouse_thread_loop.cpp:99`：准星参考点「真实后坐力抬枪(几百 px/s)完全不受限」
- `crosshair/crosshair_detector.cpp:19-26`：找色 ROI 「兼顾武器全自动后坐力向上跳动的自适应窗口」

即：**没有任何一处代码是"压枪"**，全都是"让 PID 顺带把被抬起的准星拉回来"。这是闭环追踪，
天生比开环前馈慢一个环路延迟（50 ms 以上），而且它跟"瞄目标身上某个点"这同一个回路抢同一个误差，
必然互相妥协。

### 2.3 为什么闭环天生压不住

打连发时，后坐力是一个**持续的外力**：每秒钟把准星抬高 `v_recoil` 像素。
PID 要到"误差攒起来"才开始出力，稳态误差是

```
e_ss ≈ v_recoil / (k · Kp)      （k = 每计数多少像素）
```

本机：`v_recoil = 300 px/s`、`k = 0.593`、`Kp_y = 40` → `e_ss ≈ 300/(0.593·40) ≈ 12.7 px`。
也就是**准星常驻偏低十几像素**，要靠积分（`ki=1`，Ti=1 s）在 1 秒左右慢慢磨掉 ——
一梭子早打完了。这就是"压枪压不住"的定量解释。

AimMagic 那边这个量是**前馈直接给掉的**，不进误差环，所以稳态误差接近 0。

### 2.4 改法（按性价比排序）

**A. 先做最小可用版（1 天量级）**
在 `HotkeyProfile` 加一组"压枪弹道"，格式就照抄 AimMagic：`(rel_x, rel_y, delay_ms)` 序列 + 启动门控。
播放器放在 `mouse_thread_loop` 里、**与 `engine.tick()` 的输出相加**后再 `sendRawMove`：

```
drive_dy = out.dy + recoil_player.step(now_ms, firing)   // firing = trigger.phase == Pressed
```

**五条硬要求（都来自它的实现，逐条有据）**：

1. **注入点必须在控制器之后**。AimMagic 的 `merge` 是把位移累加到 `runtime+0xA78/+0xA7C`
   再由瞄准线程**加进本拍输出**（`FUN_140067000` 行 1756-1763），
   **不是**加进 PID/Scale 的误差。这是"压枪稳、瞄还准"能同时成立的结构性原因 ——
   两条回路各自闭环，不会互相积分成振荡。**这一点千万别做错。**
2. **播放用绝对截止时刻 + 可中断的定时等待**，`delay` 不要用 `Sleep`。
   它的回放循环用 `FUN_1401d9c74(condvar, mutex, ms)`（`6b953`），
   所以抢占 / 停止 / 换弹道能**立即打断**当前等待。用 `Sleep` 的话停火要等完当前 `delay` 才停，
   表现为"松手后还在压"。
3. **自己一条线程**，按 `start + Σdelay` 走时，**不要用检测帧数计时**（掉帧就漂），
   也不要挂在检测 tick 上（那就退化成本方现在的闭环追）。
4. **默认 `separate` 语义 = 每步立即独立发一次**，label 区分来源；
   想做平滑再上 `merge`（合并成一次）+ `damping` 分摊，不要一上来就合并。
   注意它的 `merge` 会**强制多跑一次瞄准 tick**（事件驱动等待谓词显式包含 `+0xA78/+0xA7C != 0`），
   否则合并位移会因为"本轮没有新推理"而被吞掉 —— 本方若走 merge 也要防这一手。
5. **门控全 AND、且要有兜底**。它那四个门控（右键 / 自瞄键 / 有锁定 / 画面有目标）默认全 false
   是一票否决；另外 `merge` 但自瞄未激活时会**静默退化**为独立发送，**不丢位移**。
   本方要照抄这条兜底，否则"没按瞄准键但按左键"的弹道会凭空消失。

**B. 让它能自动量出来（这是它真正的杀手锏）**
`record_source = aim_color` 对应的就是**准星找色**。本方已经有 `crosshair/` 模块，
所以可以：开火期间不要瞄，只读准星找色结果，按 `record_sample_ms = 20` 采样
`(Δx, Δy)`，开火结束存成一条弹道。这一步做完，"换枪重调"从半小时变成十秒。

采样器也有一条值得抄的细节：它的 `FUN_14005f590` 累加 `(dx, dy, elapsed)`，
到点 push 一步后**把时间余数结转**（`st[4] -= interval`），所以按 20 ms 采样不会累积漂移。

## 3. 瞄准：四个具体差距

### 3.1 无死区 vs 5 px 死区

**【代码证据 · 本方】** `build/cuda/Release/config.ini:114-115`：

```

pidf_deadzone_y = 5
```

`aim_pid.cpp:139-162`：死区内直接 `return 0`。也就是**误差小于 5 px（离开要 7.5 px）时控制器完全不出力**。
配置注释自己写着"死区等于主动丢精度"，但本机开着 5。

**【代码证据 · AimMagic】** 它没有死区。它的入口只有：

```c
out = cli(...);                  // 1.0.30 有 min_position_offset / horizontal_deadzone，
                                 // 但 QML 默认都是 0.0（qml_z/当前_PID_配置档位*.qml:339-347）
```

**改法**：把 `pidf_deadzone_x/y` 设回 0，改用 3.2 的增益调度来防末段过冲。

### 3.2 增益调度：大误差降增益（**方向与直觉相反**）

**【代码证据 · 逐位核对的反汇编】** `ghidra_out\pid_core.txt` 行 24-531（`FUN_140056f10`）。
反汇编 0x140057042-0x14005706A，条件（`COMISD`/`JBE` 逐标志位核对过）：

```c
if (profile == "PID-Adaptive" && |kp_floor| <= |e|)
    Kp = kp_floor;
```

**即：`kp_floor` 是在"误差大于等于 kp_floor"的区段把 Kp 换成小值 —— 它是"收敛增益"，不是"末段保底"。**
QML 注释两边都印证（`qml_z/当前_PID_配置档位*.qml:204/271`）：

> `x_kp_floor` — "Free 用作**启动Kp**，Adaptive 用作**收敛Kp**；同步控制器只使用唯一Kp。" 默认 `0.05`

另外 `FUN_1400579f0` 行 875-879：Free/Adaptive 的启动段把 Kp/Ki 从 `kp_floor` 按
`fcount / warmup` **线性爬升**（就是 1.0.8 报告 §3.6 那个"增益软启动"）。

> **修正**：我上一版把这条说成"大误差降增益、小误差满增益、末段咬得住"，**方向说反了**。
> `kp_floor` 只服务"大误差段别冲"和"起步别冲"。
> **真正让它"咬住最后几像素"的机制是别的东西**：是 §3.2b 的取整余数 + 无死区，
> 而不是 kp_floor。这对改法有影响 —— 见 3.2b。

### 3.2b 取整余数：本方已经做对了（逐条核对过）

**【代码证据 · AimMagic】** `FUN_140067000` 行 1500-1618：

```

counts = round_half_away(dVar50);   // 发送
runtime+0xCD0 = dVar50 - counts;    // 把残差存回去
```

所以它的稳态误差可以真的走到 0，没有"不足 1 个计数就永远不发"的死区。

**【代码证据 · 本方】** `aim_pid.cpp:242-268` 是**同一件事**：

```cpp
double want = u + carry_;
long counts = std::lround(want);
...
carry_ = std::clamp(want - static_cast<double>(counts), -kCarryClamp, kCarryClamp);
```

而且 `tests/aim_pid_test.cpp:315-335` 有一条**专门验这个**的回归：

```cpp
// 单独验"余量": 关掉积分, 只看 P 项是否把亚计数误差攒着发出去。
check(nonzero > 0, "亚计数误差不会被丢掉(余量会攒到下一拍)");
```

**结论：这一条本方不缺，不需要改。** 我核对时还确认了 `AimPathDriver` 在
`Mode::Linear` 下直接透传（`aim_path.h:120-125`）且 `rx_/ry_` 恒为 0，不会引入二次量化。

> 所以"末段咬不住"的真实原因只剩一个：**5 px 死区**（§3.1）。
> 因为按 §3.2 的修正，`kp_floor` 并不是末段机制，那么"末段不冲过头"这件事
> 本方就**只剩死区在顶** —— 于是它必然要牺牲精度。
> **这正是 §7 里 P0 那条"死区设 0 + 加 P 项增益调度"的真正理由**：
> 你要补的不是"抄 kp_floor"，而是补一个**只在末段生效的**增益调度，
> 位置与 AimMagic 不同（它是大误差降增益，你要的是小误差保增益）。

> 参考：桌面的 `pid1.cpp` 里那套 `kp_integral()` / `adjust_integral()` 增益调度
> （`kp_gain` 从 0 自适应到 1，阈值 `kp_gain_threshold = 1920`、`integral_gain_threshold = 50`）
> 和 `smoothTerm()` 那个 `(x·(1+4x²/15)/(1+3x²/5))` 软化函数，就是 AVA 的做法，
> **不在你现役链路里**。可以用，但注意 `1920` 是按 1920 宽的检测图定的，
> 你的检测边长是 416，阈值要按比例缩到 ~416 才有同样含义。

**【代码证据 · AimMagic】** 速度在**跟踪器**里按 track 维护，带**采样窗**（`v1030/ANALYSIS_v1030.md` §4.3）：

```c
    velX = track[+0x20];  velY = track[+0x24];

    velX = (curX - lastX)/dt * K1 + oldVel * K2;   // 出窗才重新估
    ...

```

而且**预测偏移是在选靶之前就写回框心的**（§4.2）：

```c
*pfVar14 = fVar19 + *pfVar14;    // 预测偏移直接加到框中心
```

所以后续的选靶、扳机判定、PID 全都吃的是**预测后的框**。

**【代码证据 · 本方】** 两个观测器各给一半速度，其中：

- **X 轴**：`boss_aim.cpp:290` → `fb_x.target_velocity_px_s = anchor_obs_x_.velocity()`。
  但 `anchor_observer.h:68-75`：

  ```cpp
  // 延迟线攒够之前不报速度
  if (!initialized_ || pushed_ < 3) return 0.0;
  ```

  而这又直接受 `anchor_filter_ms` 支配 —— 本机 **`anchor_filter_ms = 0`**（最终写到 `config.ini:120`），

- **Y 轴**：`boss_aim.cpp:294` → `motion_y_.targetVelocityPxPerSec()`，来自

**改法（按顺序）**：
1. `anchor_filter_ms` 至少设到 8~15（`config.h:90` 的注释本意就是默认 8，现在 0 = 关）。
   它同时是速度门：关掉位置滤波 = 顺带关掉速度前馈。**这一条是当前最便宜的修复。**
2. Y 轴的速度换用 `anchor_obs_y_`（α-β）而不是最小二乘拟合窗口，与 X 轴同源、同一个门；
   `aim_motion` 那个拟合器退回它唯一不可替代的职责：**在线估 `k̂`（每计数像素）**。
   > ★ **2026-09-16 补正**：说 AM"不需要 counts-per-pixel"的那半句是**错的** ——
   > AM 真的拿它当除数（`FUN_140067000` 行 1208/1209，`kalman_counts_per_pixel_x/y`），
   > 只是它**默认 1.0 ⇒ 恒等**，所以看起来像没有这个机制。**机制真实存在**
   > （真值：`docs/aimmagic-ground-truth.md` §6 / §8 第 15–16 条，本文 §6.7.1）。
3. 让速度**跨帧持有**（照 AimMagic 的采样窗做法），而不是每帧重建。
   现在 `boss_aim.cpp:244-254` 在 `target_switched` 时把速度清零，
   而你自己在 230 行记过「实测 2282 次身份变化里 1256 次瞄点跳变不到 25px」「身份变化占 7% 的帧」——
   这个清零让积分和前馈每秒被打断 8 次。

> **一条重要的对照：AimMagic 的默认档压根不做速度前馈。**
> 逐位核对过的反汇编显示 `FUN_140056f10` 的同步档走 `0x140057300 MOVSD XMM12,0`
> —— **前馈项 `+0x30/+0x38` 在 `PID-FrameSync` 下恒为 0**；QML 里 `x_kf` 也只对
> `PID-Adaptive` 可见。它做"提前"靠的是 §6 那条**像素域预测改框**，
> 而那条路**用 counts-per-pixel 只是做一次除法换算**（`kalman_counts_per_pixel_*` 默认 1.0
> ⇒ **恒等**，所以"看着像没消费"；**它确实被消费**，见 ground-truth §6 L1208-1209 / §8 第 15 条）。
>
> 所以本节不是"它有一个你没有的前馈"，而是"**它的前馈不依赖标定，你的依赖**"。
> 这也正是本项目历史上 `predictive_controller` 被删的原因（把写死的像素/计数标定增益
> 放进反馈回路内部）。**这条不影响 P0 的优先级**：`anchor_filter_ms` 那一行仍然要改，
> 因为它是 X 轴速度/前馈的总开关；但别指望改完就等于抄到了 AimMagic。

### 3.4 换目标复位：积分永远攒不起来

**【代码证据 · 本方】** `boss_aim.cpp:225-254` 与 `mouse_thread_loop.cpp:852-853`：

```cpp
out.target_switched = out.motion_suppressed && anchor_jump >= 25.0f;
if (out.target_switched) { pid_x_.reset(); pid_y_.reset(); … }
```

注释里已经把这笔账算清楚了：「积分(Ti=1s)永远攒不起来 → 顶不住后坐力」「38% 的帧 |ey|>10px」。
**25 px 的门限仍然太松**：后坐力抬枪本身就常常一帧跳 25 px 以上，
于是"压枪过程中"恰好反复触发 `target_switched` → 反复清积分 → 永稳压不住。

**【代码证据 · AimMagic】** 它不复位控制器状态；它靠**跟踪器身份**的 stickiness 与
`i_box_lost_hold_ms`（默认 20 ms，"积分离框宽限"）来容忍短时丢框。

**改法**：
- `target_switched` 的判据应该是**身份真的变了**（tracker 的 generation 变了**且**旧轨迹已死），
  而不是"瞄点跳得多"。至少把 25 px 提到"大于一个框的高度"量级。
- 加 `i_box_lost_hold_ms` 的等价物：框消失 ≤20 ms 不清积分。

## 4. 输出下发：它有一次"打包"，本方每拍一发

**【代码证据 · AimMagic】** `scale_delivery_ms`（"位移分发时长(ms)"，默认 0，范围 [0,100]）
与 `scale_max_move_x/y`（"单帧最大移动"，默认 9999）。语义是：把一帧算出的大位移
**在 delivery 窗口内分摊成多次下发**。

**【代码证据 · 本方】** `mouse.cpp:143-175`：MAKCUNEW 走**直发**：

```cpp
if (makcu_new_) {
    const auto t0 = std::chrono::steady_clock::now();
    const bool ok = makcu_new_->move(dx, dy);      // ← 阻塞式串口写, 在控制线程上
    ...
}
```

而 `MakcuNew::move` 是 `sendFrame()` → `serial_.write(frame, 11)`，在 `writeMutex_` 下**同步写**。
也就是说：**控制线程被串口写阻塞**。11 字节 @ 6 Mbaud 的线时间是 ~18 µs，
但 `serial::write` 有驱动/超时开销，实测每拍几毫秒是常见的。
在 8.33 ms 的节拍里，这几毫秒是**直接加进死区的**。

**改法**：
1. 控制线程只做决策，**输出交给 `moveWorkerLoop`**（那条路已经有 latest-only 覆盖语义 `latest_move_slot.h`）。
   现在 MAKCUNEW 绕过了它，等于把串口写放回了实时路径。
   注意 `mouse.cpp:150-154` 的注释：绕过 worker 还顺带让 `appliedD*`/`lastLatencyUs_` 失效 —— 所以这一步同时修好遥测。
2. 引入 `scale_delivery_ms` 的等价物：一拍算出的大位移分摊到 2~4 个写包，
   但**总位移守恒**（不要丢尾数）。这对压枪的"均匀下压"手感帮助很大。

## 5. 扳机：为什么它"很快"

【代码证据】两侧的**首帧逻辑其实一样快**，差在别处。

| 项 | AimMagic | 本方 |
|---|---|---|
| 判定基准 | **预测后的框**（预测偏移在选靶前已写回框心） | `out.anchor`（经观测器滤波的锚点） |
| 命中区 | 按类别可覆盖的子区间 + 小目标独立参数 + 类别专属 | bbox × `trigger_y_percent`，外加"人体边界"硬门 |
| 评估频率 | 1 kHz（控制线程） | ≤120 Hz（检测帧） |
| 时序分辨率 | 1 ms | 8.33 ms |
| 最小延时 | 下限 30（`0x1e`，ns 时间戳） | 无下限；0 = 立即 |
| 时间基 | 全程 **ns** | `steady_clock` → ms（`duration_cast<milliseconds>`） |
| 随机抖动 | `random_delay` 参与起/按/松三段 | 三段 jitter 都有 |
| 命中判定的精度 | 用预测框心 | 用**带 5 px 死区的锚点** |

### 5.1 时序量化

`mouse_thread_loop.cpp:1006-1007` 把时间降到毫秒：

```cpp
const int64_t now_ms = std::chrono::duration_cast<std::chrono::milliseconds>(
    now.time_since_epoch()).count();
```

配合 ≤120 Hz 的评估频率，`trigger_fire_delay`、`trigger_fire_duration`、`trigger_fire_interval`
全部被量化到 8.33 ms 的格子上。想要 5 ms 的按压时长？实际会是 8.33 ms 或者 0。
连点模式（`fire_duration > 0`）的节奏会明显发"木"。

**改法**：时间基改 ns（照它），并且把扳机 FSM 移到 1 kHz 内环里评估（与 §1.4 同一件事）。

### 5.2 命中判定用了"慢变量"，而且两个条件口径不一致

`mouse_thread_loop.cpp:976-992`：

```cpp
const double scale = std::max(0.1, profile_ptr->trigger_y_percent / 100.0);  // 本机 = 1.0
const double tx_range = out.bbox.width * scale * 0.5;      // ±0.5·w
const double ty_range = out.bbox.height * scale * 0.5;     // ±0.5·h  ← 垂直容差

const bool in_tolerance = std::abs(pivot.x - out.anchor.x) <= tx_range &&
                          std::abs(pivot.y - out.anchor.y) <= ty_range;      // ① 以【瞄点】为中心

const double top_limit = out.bbox.y - out.bbox.height * 0.12;                // ② 以【框顶】为基准
const double bottom_limit = out.bbox.y + out.bbox.height;
const bool inside_body_geometry = (pivot.y >= top_limit) && (pivot.y <= bottom_limit);

const bool in_zone = in_tolerance && inside_body_geometry;
```

三个独立的问题叠在一起：

1. **判定的两个输入都不是当帧真值。**
   - `out.anchor` 在 `anchor_filter_ms > 0` 时是滤波值；
   - `pivot` 是**限速 1500 px/s + 一阶惯性（τ 10~50 ms）+ 120 ms 丢帧保持**的静态准星参考点
     （`mouse_thread_loop.cpp:89-180`）。
   AimMagic 用的是**当帧已被预测改写的框心**。

2. **① 与 ② 参考点不同**：① 以**瞄点**为中心（瞄点 = 框内 `y_offset` 处，本机配置 0.9，
   即框顶下 10%），② 以**框顶**为基准。这两个中心差了 `0.1·h`，而垂直容差只有 `0.5·h`，
   于是上半边的可用空间被两套口径切得七零八落。

3. **【实测】`ty_range` 比框本身还宽。** 实测 `ty` 的 p50 = 38.4 px、p90 = 102.8 px，
   而候选框高度常在 130~150 px。所以 ① 几乎不拦人，真正在拦人的是 ②；
   一旦准星落到瞄点上方，① 报"在区内"而 ② 报"在框外"。

**【实测 · 这就是扳机抖动的机制】**
- 2615 个可解析扳机帧里，**30% 的帧上 ① 与 ② 结论相反**（8.6% 只有 ① 通过，21.3% 只有 ② 通过）；
- 整场会话中 `in_zone` 的**连续段长度 100% ≤ 2 帧**（≤16 ms），
  相位分布 Idle 16145 / Pressed 2864 / Cooldown 156 ——
  也就是**"点一下就松、再点一下"，从来没有形成过稳定按住**。

**改法**：把 ①② 合并成**一个以瞄点为圆心的判定区**（半径按框的短边比例给），
删掉"人体边界"这条独立门禁；同时命中判定改用**原始**锚点与**原始**枢轴
（`raw_anchor` 已在 235 行算出来，`crosshair_runtime::read()` 里也有未滤波命中点），
滤波只用于控制回路。这一条改完，`in_zone` 的连续段长度会立刻从 1~2 帧变成几十帧。

### 5.3 一个次要隐患（已被实测证实）

`top_limit = bbox.y - 0.12*bbox.height`、`bottom_limit = bbox.y + bbox.height`，
而 `ty_range = bbox.height * 0.5 * scale`，`scale = 1.0`。于是垂直容差本身是
`±0.5·h`，已经比 bbox 上下各多出一点点，只靠 `inside_body_geometry` 兜住上半部分。
**实测已经看到两个条件互相打架（见 5.2）**。把 `trigger_y_percent` 调小（比如 70）
会让两个条件同向收紧，调大则互相打架。
建议把"命中区"统一成一个按比例定义的矩形（照它的 `X范围/X偏移/Y范围/Y偏移` 四系数），
而不是"容差 + 边界"两套并存。

## 5.4 AimMagic 的扳机为什么"零延迟"（反编译闭合）

**【代码证据】** 主 tick `FUN_14007e5c0`（1022 行）内的顺序：

```
行 291  FUN_1400824e0   → NMS(176/208) → 跟踪器(219) → 预测(646)
行 740  FUN_1400886f0   扳机命中判定 → 写 runtime+0xF3
行 390  FUN_140088130   扳机时序状态机（消费同一拍的 +0xF3）
行 404  FUN_140085410   压枪
```

**命中判定与按键执行在同一次 tick 内串行，中间不跨帧。**
延迟门 `runtime+0xBA8` 是一个"下次允许动作"的纳秒时间戳：

- 行 63-66：`now = clock(); if (gate && now < gate) return;`，门初值 0 ⇒ **第一拍必然通过**；
- 行 139/153（按住分支）：`delay = delay_fn(start_delay@+0x170, random_delay@+0x17C);`
  `if (delay > 0) { gate = now + delay*1e6; return; }` ⇒
  **`start_delay` 默认 0 时 `delay_fn` 直接返回 0，根本不进延迟分支**；
- 真正的下限只出现在"连点"分支：行 94-101 取 `max(30, delay_fn(press_delay, random_delay))`，
  行 199-201 取 `max(10, …)` ⇒ 默认 `press_delay = 0` 时只有 **30 ms 地板**，约 33 次/秒。

随机延迟用的是 **`std::mt19937` + `uniform_int_distribution`**（TLS 里惰性构造，
`FUN_140079980`），不是 `rand()`；两参数任一为 0 就直接返回 `min` ⇒
**`random_delay` 默认 0 时整条时序完全确定性**。

触发模式枚举（`FUN_140088130` 行 67-72）：`0=无, 1=智能连点, 2=连点, 3=持续, 4=智能持续`；
开镜方式：`0=无, 1=点按右键, 2=长按右键`。
`runtime+0x974` 是 **1.0.30 新增**的字节，标记"本次 tick 是否已按下过"。

**命中判定 `FUN_140088790`** —— 四系数写法（与 §5.2 本方那两套口径对比）：

```c
left = (box[0] - w*0.5f) + w * offsetX;          // 以框中心放大后的左上
命中 = (left < aimX && aimX < left + w*scopeX)   // X 范围
    && (top  < aimY && aimY < top  + h*scopeY);  // Y 范围
```

**两轴独立、开区间、一个区间管完**，没有第二条"人体边界"门禁。
四系数来源：小目标（`small_target_threshold_x/y` 默认 20/25）→ 该**类别**的覆盖值；
否则 → **按键级**。默认 `scope=1.0 / offset=0.0` ⇒ 判定区就是整个框。
`aimX/aimY` 就是**已被预测改写过的框心**。

**速率结论（重要，修正了常见误解）**：扳机**没有独立的高频线程**，
评估频率 = 自瞄 tick = 推理帧率（`FUN_14007e5c0` 行 291 → 390 同一个 tick 内），
主循环默认**不限速**（`max_fps` 默认 0）。所以它"快"不是靠评估频率，
而是靠 **同 tick 串行 + 首枪绕过延迟门 + 判定用预测框心** 这三条。

## 5.5 它现在跑的 Scale 控制律（定量，用于对照）

**【代码证据】** `FUN_140067000` 行 1307-1345 原文：

```c
if (*(longlong*)(frame+0x4c8) != *(longlong*)(frame+0x100)) {   // ★ 新推理结果（水位比对）
    dVar53 = flick_scale_x(+0x100) * errX(frame+0x534) * flick_damping(+0x108) * (frame+0x650);
    dVar54 = flick_scale_y(+0x104) * errY(frame+0x538) * flick_damping(+0x108) * (frame+0x658);
    iVar43 = (int)round_half_away(clamp_mag(dVar53, max(scale_max_move_x, 1.0)));  // → X 鼠标计数
    iVar36 = (int)round_half_away(clamp_mag(dVar54, max(scale_max_move_y, 1.0)));  // → Y 鼠标计数
    // 行 1396-1431：scale_delivery_ms 分期
    if (scale_delivery_ms > 0) { ratio = clamp(Δnow / (ms/1000), 0, 1);
                                 iVar43 = round(iVar43 * ratio); ... }

```

要点：

- **纯比例，无积分无微分**，误差 `+0x534/+0x538` 是**未滤波的原始误差**（零相位滞后）；
- 增益 = `counts_per_pixel × 力度`。本机实测 `3.225806 × 0.06 = 0.1935 counts/像素`；
- `scale_max_move_x/y` 默认 **9999.0**（≈不限幅）；
- `scale_delivery_ms` 默认 **0** ⇒ **一拍发完，不摊到多拍**；
- **每个推理结果只消费一次**（`+0xE50` 水位比对）；水位相等就无限期睡在条件变量上；
- 非事件驱动时才走 `now + 1000000 ns` 的 1 ms 定时等待（≈1000 Hz）。

**它对本方最直接的一条启示**：在同一个检测帧里，它的输出就是**完整的那一步位移**；
本方的 `pidf_limit_x/y = 0`（内置 200 计数/拍）也不会截断（实测 `cmdx` p90 = 5.77），
所以这一项两边**都是对的**。真正的差别还是 §3.1/§3.2/§3.3/§3.4 那四处。

**另一条值得抄的**：它把"移动"和"按键"统一到**同一个驱动对象的三条虚方法**上
（`FUN_1400774e0`：`vtable[+0x10]` 移动、`vtable[+0x18]` 按下、`vtable[+0x20]` 抬起），
自瞄 / 压枪 / 宏 / 自动背闪全部复用，**在上层做矢量合成**。
本方现在 MAKCUNEW 是"控制线程里直写串口"，既阻塞了实时路径，也让多源输出（未来的压枪）
没有统一的合成点（§4）。

### 6.7 `pid_calib` 到底量的是什么（2026-09-13 追查结论）

> 本节是为填上面 §6.5 那个**死引用**补的：原文档引用了 `§6.5`，但那一节从来没写下来，
> 导致后来（2026-09-13）我们照着自己的理解去做"测量"，连错两次。
> 把能确证的和不能确证的分开记在这，避免再犯。

**【已证】`FUN_14006bf50`**（label = `"calib"`，见 `AimMagic_1030_trigger_recoil.md:1059`）：

```
读光标 -> 发一次移动(param_5 个计数) -> 再读光标
返回 param_5 / |Δ像素|   = counts-per-pixel
```

**【已证】它的控制律是开环的、纯比例的**（`FUN_140067000` 行 1307-1345，§5.5）：

```
counts = round(flick_scale × err × flick_damping)
```

`flick_scale` **就是原始 counts-per-pixel**（QML 原文：「校准值现在保存原始 counts-per-pixel」）。
**它对"标定值准不准"是零容忍的** —— 没有积分去兜底，k 错了多少，瞄偏就错多少。

**【不能确证 · 关键】它读的是哪台电脑的光标。**

原始镜像 `AimMagic_RE\` 与 `ghidra_out\` 已在早期清理中删除，**无法再反汇编复核**。
文档只写了"读光标"，没写 API。两种可能：

| 可能 | 在本项目双机架构下是否成立 |
|---|---|
| `GetCursorPos`（只能读本机） | **不成立** —— 程序跑在采集机，"挪了"的是游戏机，本机光标与游戏画面无关 |
| 某种跨机读取 | 成立，但**没有任何证据支持** |

**【本项目实测 · 2026-09-13】** 工具 `cursor_probe`（已删除）在采集机上发 100 计数：
本机光标稳定走 247px（散布 0.0%）。**这个数只反映采集机的指针加速，与游戏灵敏度无关** ——
证明"读本机光标"这条路在本架构下必然量错。

**【结论 / 不要重复的错】** 本项目的拓扑是

```
游戏机 --HDMI--> VC-009PRO 采集卡 --USB--> 采集机(程序 + CMP 40HX + MAKCU)
游戏机 <--------------- MAKCU 盒子输出(插在游戏机) ---------------┘
```

**"每计数像素"是游戏机的属性，只能在游戏画面里量。** 曾经试过的两条路都错：

1. ❌ 用 `anchor_observer` 的输出当测量源 —— 它**职责就是把这个量减掉**
   （`predicted = pos + vel·dt - k·u_eff`），且大步长会触发 40px 野值门限整拍丢弃。
   实测甩 469 计数只报出 31.1px。详见 `control-architecture.md`。
2. ❌ 用采集机的 `GetCursorPos` —— 见上，两台机器。

**能做对的只有**：从**游戏画面**里取一个不依赖检测的参照（例如背景特征位移 /
准星在画面内的位移），并且不要经过 `anchor_observer`。

> **【2026-09-13 更新】连这条也不做了。** 用户决定改抄**原神 AI 的纯反馈路线**
> （高增益 + 输出整形, 无前馈、无预测）—— 见下方 §6.8。
> 一旦去掉前馈, `k̂` 这个量整个不再需要, 测量问题自然消失。

### 6.7.1 【2026-09-15 更正】EventSync 档的 k̂ **不是测量出来的，是用户手填的**

上面 §6.7 追的是 `pid_calib`（**甩枪档**的自动标定，`FUN_14006bf50`：
发已知计数 → 读光标 → 反算 counts-per-pixel）。那一节是对的，但它**不适用于
EventSync 档** —— 我在移植 EventSync 时把两者混为一谈，得出"k̂ 无法获得所以
第一项不能抄"的结论，**那个结论是错的**，在此更正。

**EventSync 档用的是完全不同的一个量**：`kalman_counts_per_pixel_x/y`
（配置槽位 `0x90/0x94`，流水线结构体 `0xea8/0xeb0` → `0x520/0x528`）。

**【已证】它是普通的用户设置项，不是测量值** —— `ANALYSIS_v1030.md` 行 143-144 / 794-795：

| 键 | 默认 | 夹取范围 |
|---|---|---|
| `kalman_counts_per_pixel_x` | **1.0** | [0.001, 10000] |
| `kalman_counts_per_pixel_y` | **1.0** | [0.001, 10000] |

它在代码里的**全部用途**就是一个带下限的除数（`FUN_140067000` 行 1198-1209）：

```c
// 行 1187-1188: 发送环窗口内把计数求和(窗口下界 = now − mouse_effect_delay_ms)
dVar56 += (double)(int)plVar33[1];       // Σ dx  (计数)
dVar57 += (double)*(int*)(plVar33+0xc);  // Σ dy  (计数)
// 行 1198-1205: 取倒数前先夹一个下限 DAT_1401f8000(防止除零)
dVar50 = max(counts_per_pixel_y, DAT_1401f8000);
dVar51 = max(counts_per_pixel_x, DAT_1401f8000);
// 行 1208-1209: 换算成【像素】, 送进预测器与误差合成
*(double*)(puVar40+0x28) = dVar57 / dVar50;   // y 像素
*(double*)(puVar40+0x20) = dVar56 / dVar51;   // x 像素
```

**没有任何在线估计、没有观测器、没有最小二乘。** 就是一个用户填的常量。
默认 **1.0** 的语义是"1 计数 = 1 像素"，也就是**不做换算**。

> **这对本项目意味着什么**：AM 把"k̂ 填错"的风险**交给用户承担**，而且它是
> **单机架构**（程序、光标、游戏在同一台机器），用户填的就是自己游戏的真实灵敏度。
> 本项目是双机架构，用户**同样可以手填**（他在自己游戏里知道灵敏度），
> 所以这条路是通的 —— 只是**不能让程序自动测量**（那才是不成立的部分）。
> 因此移植方案 = **手动槽位 + 默认 1.0**，与 AM 完全一致。

#### 关键的量纲换算

```
它: Kp = 1.08 【计数/像素/拍】 x 120 拍/秒 = 129.6 计数/(像素·秒)
我们: Kp = 50  【计数/(像素·秒)】
=> 它的等效增益是我们的 2.6 倍
```

纯 P 回路追匀速目标的稳态滞后 = `v / (Kp·换算)`:

| 目标速度 | Kp=1.08 | Kp=0.37 |
| --- | --- | --- |
| 100 px/s | 1.3 px | 3.8 px |
| 200 px/s | 2.6 px | 7.6 px |
| 300 px/s | **3.9 px** | 11.4 px |

**3.9px 肉眼就是"跟死了"。所以它不需要前馈 —— 增益够高, 滞后自然就小。**

#### 它压住高增益抖动的三件套

1. **`smooth_max_pixel` (30)**: 大误差时输出被限成恒速。这既是"防冲过头", 也是它敢开高 Kp 的前提。
2. **`pid_kd` (0.02)**: 轻微阻尼。
3. **输出整形** (`enable_curve_move` + `min_curve_distance=15` + `submovement_strength=0.15`
   + `enable_power_law`): 大体位移不一步发完, 而是**分段/曲线化**下发 —— 把"一步冲过去"
   变成"分几步走过去", 从输出侧削掉了过冲。

#### 用户实机体感 (2026-09-13 口述)

- **Kp 开大导致的抖动, 靠"震荡抑制"完全能压住, 基本感受不到。**
  (对比: 我们的做法是加前馈去补, 复杂度高得多)
- **Kp + Ki 都调太大 → 移动目标"一抽一抽"**。这是**极限环**, 由**链路延迟**造成:
  发的指令要过很久才在画面生效 → 控制器以为没动 → 继续加力 → 指令终于生效已过头 → 反向 → 循环。
- **采集卡延迟 + 硬件延迟低的话, Kp/Ki 调大一点点就肉眼紧跟, 且不管目标怎么动都不抽。**

> **结论: 延迟是唯一的约束。** 延迟低 → Kp 能开大 → 不需要前馈。
> 前馈是"绕过延迟约束"的另一条路, 代价就是需要标定 k̂ —— 这正是本项目当前痛苦的来源。

#### 本项目的改法 (待实施)

**删掉**(全部是跟 AimMagic 学的, 属于"预测"范畴):
- `mouse/anchor_observer.h` (α-β 观测器 + 速度前馈)
- `mouse/aim_motion.h/.cpp` (在线估 k̂、速度估计、拟合窗口)
- `aim_pid` 里的前馈项 (`in_flight` Smith 补偿 + `paired_px` 配对补偿)
- 「每计数像素」测量功能 + `aim_px_per_count_*` 配置 + 全部标定遥测

**换成**原神式的纯反馈:
- 纯 PID (P + 小 I + 小 D), 无前馈、无预测
- 增益调度 (连续, 非硬切换) 代替死区
- 输出限幅 **(相当于 `smooth_max_pixel`)**
- 输出整形 (大位移分段下发)

**青出于蓝的点**(原神方案的弱点):
- 它的 `smooth_max_pixel` 是**硬限幅**, 在大误差段把增益砍成常数 —— 牺牲了收敛速度。
  我们可以用**连续饱和 / 增益调度**代替, 两端都要(大误差快冲、小误差不冲)。
- 它的输出整形靠**固定曲线预设**; 我们可以做得更自适应。

**实施前必须先测**: 本项目的端到端延迟到底比原神高多少。
若延迟相近 -> Kp 可直接开大, 纯 PID 就够; 若明显更高 -> 得先降延迟(采集/推理/发送), 否则 Kp 一开大就抽。

## 10. 「跳起来 / 刚露头就秒锁我」——第四次采集的实测

用户的原始描述：**"他可以跳起来的时候瞬间锁到我头上然后扳机死我，或者我刚露也能这样"**。
这一节专门查了这个场景，全部数据来自 `chain_live.log` 的 `(L,5)` 目标层 × `(L,2)` 控制层配对（16550 帧）。

### 10.1 实测：先瞄准失败，再靠"宽容区"盖上

| 指标 | 实测 |
|---|---|
| `switch`（真换目标，身份变 + 瞄点跳 ≥25px） | **345 次 = 2.08% 的帧** |
| `track_id` 变化 | **745 次 = 4.50% 的帧，平均每 22.2 帧（185 ms）一次** |
| `coasting`（滑行 / 预测框） | 725 帧 = 4.4% |
| 全局 `\|ey\|` | p50 = **4.5 px**、p90 = 24.2 px、mean = 10.4 px |
| **换靶那一帧 `\|ey\|`** | p50 = **15.1 px**、p90 = **71.0 px**、mean = 28.2 px、max = 182 px |
| **换靶后第 1~6 帧 `\|ey\|` p50** | 16.1 → 14.4 → 13.9 → 14.0 → 14.0 → 12.4 px（**p90 一直挂在 60~71 px**） |

**这张表就是病灶**：换靶之后误差**不是几帧内收回去，而是连续 6 帧以上卡在 12~16 px（p90 60~71 px）**。
正常帧的 p50 是 4.5 px，说明控制器本来能咬到 4.5 px —— 但**一旦发生"目标跳出来/露头"这种换靶，就再也回不到那个水平了**。

### 10.2 那 12~16 px 的卡位是怎么来的（三个叠加）

**① `switch` 触发时把积分与前馈清零，之后没有东西把残余误差补掉。**
`boss_aim.cpp:244-254` 在 `target_switched` 时 `pid_x_.reset(); pid_y_.reset();`。
按 P-only 回路，稳态误差 = `偏移 /(k·Kp)`。要在 Kp_y=40、k=0.593 下维持 14 px，
需要有约 **330 px/s 的等效持续偏移** —— 这就是换靶瞬间"实际在动的东西"。
积分本该在 1 秒内把它磨掉，但它刚被清零，而**换靶平均每 22 帧就来一次**，
所以它永远等不到 1 秒。

**② `AnchorObserver` 的野值门限 ±40 px。**

```cpp
// anchor_observer.h:135-141
if (gate_ > 0.0 && std::abs(residual) > gate_)   // gate_ 默认 40.0
{
    last_gated_ = true;
    pos_ = predicted;      // ★ 不校正
    return pos_;
}
```

跳起来/露头的瞬间，画面里的瞄点就是会一次跳几十上百像素
（实测换靶帧 `jump_px` p90 = 71 px、max 182 px）。**超过 40 px 的整拍被丢弃**，
观测器退化成纯靠历史速度外推，而且**不会自动重新对齐** —— 它要等残差自己回到 40 px 以内。
换靶后 p90 一直挂在 60~71 px，正是因为这个门限把"重新捕获"那一拍也一起丢了。

**③ `pivot` 的 120 ms 丢帧保持 + 限速滑回。**

```cpp
// mouse_thread_loop.cpp:104, 149-152
static constexpr int kHoldMs = 120;
if (since_hit <= kHoldMs) return;   // 丢帧保持: 参考点不动
```

敌人跳起来挡住准星 → 找色命中断掉 → **pivot 原地冻结 120 ms**，
超时后再以 1500 px/s **限速**滑回几何中心。这期间 `err = anchor − pivot` 里的
`pivot` 是错的，PID 在为一个假目标出力。

### 10.3 为什么"他"看起来是"瞬间锁头"，而你是"漏一拍"

两边**都没有**真正的"瞬间" —— 输入延迟是同一量级（你实测 `inference_ms=8.8`、
`publish_to_aim=0.15`、`aim_to_hit≈10.9 ms`）。差别在**换靶之后谁能稳住**：

| | AimMagic | 本方 |
|---|---|---|
| 关联门槛 | `min_hits = 3`、`max_age = 5`（`FUN_140089ac0` 行 448-450，命中计数 `track+0x2C`） | 缓存已按需求删除（`lost_target_cache_frames = 0`） |
| 选靶粘滞 | trackId 优先 → 最近邻 → **沿用上一拍瞄点**（三级，`FUN_1400824e0` 行 680-720） | 身份变即复位控制器 |
| 身份变化频率 | 不重锁（靠粘滞） | **平均每 185 ms 一次**，每次都清积分/前馈 |
| 误差收敛 | 一次到位的比例控制 + `scale_max_move = 9999`（不限幅） | 换靶后卡在 12~16 px |
| 压枪 | 独立线程开环喂（§2） | 靠同一个回路追，进一步拉大误差 |

**关键差异不是"他锁得快"，是"他锁上之后不松、也不重锁"**，而你每 185 ms 就重来一次，
每次重来都把那 12~16 px 的收敛过程从头走一遍 —— **而这正好覆盖了跳起/露头那 3~5 帧的窗口。**

### 10.4 那为什么他还能"死你"——扳机的宽容区把它盖住了

回到 §5.2 的实测：你的 `in_zone` 容差 `ty` 中位 38 px、p90 103 px，**是整框级别**。
所以即使 `|ey|` 卡在 14 px，`in_tolerance` **照样判true**，扳机照样按下去。

**这就是"快准狠"的错觉来源**：

- **对手视角**：他锁上你的头 → 误差几个像素 → 全自动扫你 3~5 帧 → 你死。
- **你的视角**：你锁上他 → 误差 14 px（但在 38 px 宽容区里，所以扳机在响）→
  你以为锁住了 → **然后 1 帧之后 `in_body` 或 `in_tol` 翻掉，扳机松开**（§5.2 的 100% ≤2 帧）
  → 你打出去一两发，其中还有一部分是**从你身上往他身上扫过去的路上开的**（宽容区太大）。

所以你的枪声听起来是"哒…哒…哒"，他的是 "哒哒哒哒哒"。**同样按住鼠标，你只打出一两发。**

### 10.5 针对这个场景的修法（追加到 §7 的 P0）

| 优先级 | 动作 | 针对本节的哪一条 |
|---|---|---|
| **P0** | `lost_target_cache_frames` 从 0 调到 **8~15**（约 70~125 ms），并让"漏一两帧"走 track 预测分支而**不 reset 控制器** | 10.2 ①：止住每 185 ms 一次的积分清零 |
| **P0** | `switch` 判据改为"**身份真的变了**"（旧轨迹已死）而不是"瞄点跳 ≥25 px" | 10.2 ①：跳起来本身就会让瞄点跳 >25 px，现在的判据把这个当成换靶 |
| **P0** | `AnchorObserver` 野值门限 ±40 px **改成自适应**：换靶/大跳变后进入一段"重捕获窗口"，窗口内不做野值丢弃 | 10.2 ② |
| **P0** | `pivot` 的 `kHoldMs = 120` 缩短，并在丢帧时**不要用冻结的 pivot 参与控制**（宁可用几何中心或标记该拍无效） | 10.2 ③ |

## 11. 「PID 死区震荡」——实测频率与机制

用户报告：**"我的 PID 目前会死区震荡"**。代码里已经写了一次补丁

但用户仍然感觉得到 —— 说明补丁压住了症状，没修根因。下面是实测。

### 11.1 实测：输出确实在抖

从 `chain_live.log` 的 `(L,2)` 控制层统计（16550 帧 / 138.4 秒）：

| 指标 | 实测值 |
|---|---|
| **该拍完全不动（`\|cmdy\| < 0.5`）** | **10687 帧 = 64.6%** |
| **输出 动/不动 翻转** | **1411 次 = 10.20 次/秒** |
| 输出方向翻转 | 991 次 = 7.16 次/秒 |
| 小误差段（`\|ey\| < 10px`，占 69.7%）的 `\|dpy\|` | mean 0.21、p50 **0.00**、p90 **0.15** |

**10.2 次/秒与代码注释里"实测每秒 11 次"几乎一致** —— 补丁没改掉这个数字，
因为**这个频率不是迟滞能改的，它由死区宽度和回路增益共同决定**。

### 11.2 机制：迟滞只改变了"退出阈值"，没改变"退出后的输出有多大"

`aim_pid.cpp` 的死区逻辑（带迟滞）：

```cpp
deadband_active_ = deadband_active_ ? (abs_error < leave_threshold)   // deadband*1.5 = 7.5px
                                    : (abs_error < params_.deadband_px);  // 5px
if (deadband_active_) { carry_ = 0.0; ...; return 0; }   // ★ 完全不出力
```

于是形成一个**极限环**：

1. 误差被压到 5 px 以内 → 进死区 → **本拍输出 0**
2. 控制停了，但**扰动没停**（后坐力抬枪、目标横移、观测器外推误差、框抖动）
3. 误差涨到 7.5 px → 退出死区 → **满增益 + 已累积的积分一起放出来**
4. 输出远大于"刚好走 7.5 px"所需的量 → **冲过去 → 反向 → 回到第 1 步**

**关键：迟滞把"进入门槛"设成 5、退出门槛设成 7.5，只改变了环的宽度，
没有改变第 3 步的过冲量。** 过冲量由 `Kp·e` 决定，7.5 px × Kp_y=40 已经是
**每帧 180 counts**（按 k=0.593 是 107 px/帧 = 12800 px/s 的等效速度），
对着一个只要走 7.5 px 的误差 —— **过冲 14 倍**。这就是极限环的振幅来源。

**实测周期对得上**：`|cmdy| < 0.5` 占 64.6% → 平均每周期"停"约 64.6/35.4 ≈ 1.8 拍，
加上回路延迟（检测 8.3 ms + 推理 8.8 ms + 显示，共 4~5 拍），
周期 ≈ 6~7 拍 ≈ 50~58 ms ≈ 17~20 Hz。与实测 10.2 Hz 同量级（我按 138 秒的均值算，
期间包含非交战段，所以偏低）。

### 11.3 第二个贡献者：微分项低通时间常数 < 拍间隔（这是个真 bug）

```cpp
// aim_pid.cpp:18
constexpr double kDerivativeTau = 0.006;   // 6 ms
// aim_pid.cpp:167
const double alpha = std::clamp(dt / (kDerivativeTau + dt), 0.0, 1.0);
```

实测 `dt_ms` p50 = **8.3 ms**。于是

```
alpha = dt / (tau + dt) = 8.3 / (6 + 8.3) = 0.58
```

**α = 0.58 意味着"新值占 58%"，也就是这个一阶低通在 8.3 ms 的采样周期下
几乎不起作用。** 一阶低通的等效时间常数必须 ≥ 2~3 倍采样周期才有意义，
而 6 ms **小于** 8.3 ms 的拍间隔 —— 这个低通按设计意图是失效的。

后果：检测框每帧量化台阶是 ±1~2 px（`precise_boxes` 是 `Rect2f`，但模型输出本身有量化），
在未滤波的裸差分下：

```
raw_derivative = Δe / dt = 1.5px / 0.0083s ≈ 180 px/s
d_px = Kd · derivative = 0.01 · 180 = 1.8 px 等效
```

**单帧 1.8 px 的等效误差尖峰**，占小误差段（p50 = 4.5 px）的 40% —— 而且它是**单帧尖峰**，
下一帧 D 项就翻回来。这就是"输出在高频小幅度地抖"的那一半来源。

> 实测 `|dpy|` 在小误差段 p50 = **0.00**、p90 = 0.15、mean 0.21：
> 说明 D 项**大部分帧是 0，偶尔跳一下** —— 正是"未滤干净的量化噪声"的特征签名。

### 11.4 为什么 AimMagic 没有这个问题（三个机制，缺一不可）

| | AimMagic | 本方 |
|---|---|---|
| **死区** | **没有死区**。末段靠连续的比例输出自然收敛，不制造"停—放"循环 | 5 px 死区 + 1.5 迟滞，制造极限环 |
| **微分滤波** | `1 - exp(-dt·40π)`，τ ≈ **7.96 ms** —— 注意它是**时间常数形式的帧率无关低通**，而且作用在**微分项**上，dt 变化时等效带宽恒定 | `kDerivativeTau = 6 ms` **固定小于拍间隔**，α=0.58，几乎不生效 |
| **首拍微分** | `frame_count == 1` 时 dTerm **直接置 0**（`0x14005719B XORPS XMM6,XMM6`） | `first_` 只把 `prev_error_` 初始化，**不把 D 项清零** |

### 11.5 修法（按顺序，前两条一起做）

1. **`pidf_deadzone_x/y` 设 0，同时给 P 项加连续增益调度**（§3.2b 的 `g(e)=min(1, e_hi/|e|)`）。
   这两条**必须一起**：只删死区不加调度，末段会开始冲；只加调度不删死区，极限环还在。
   调度把 `e_hi` 设在 80~120 px，则 7.5 px 处 `g ≈ 1`（满增益，精度不丢），
   而大误差段增益自动降到 `e_hi/e`，不再有过冲。
2. **`kDerivativeTau` 从 6 ms 提到 20~25 ms**（≥ 2.5 倍拍间隔），
   或者干脆把 `pidf_kd_x/y` 设 0 先验证一遍 —— 你的 D 项在小误差段 p90 只有 0.15 px 等效，
   **收益远小于噪声代价**。
3. **首拍把 D 项清零**（照 AimMagic 的 `XMM6=0`），避免开镜/换靶第一下吃到未定义的导数。
4. （可选）`anchor_filter_ms` 设 10 —— 它从**源头**削掉框抖动，
   等价于把 D 项的输入先滤一遍，与第 2 条叠加效果更好。

> **验证方法**：改完之后重跑一场，看 `chain_live.log` 里
> **`|cmdy| < 0.5` 的占比**和**"动/不动翻转次数/秒"**。
> 目标是把 64.6% 和 10.2 次/秒分别压下去 —— 这两个数字就是"死区震荡"的直接体检指标。

## 9. 结论

AimMagic 的扳机快、压枪稳、瞄准准，**不是因为它 PID 调得比你好**：

- 你现在跑的档位是 **Scale**：纯比例、无积分无微分、每帧 `0.1935 counts/像素`，
  比本方 X 轴每帧的 `0.83 counts/像素` **小 4.3 倍**。
- 它的 PID 档（`PID-FrameSync`）也是手写实现，`x_ki`/`x_kd` 默认都是 **0**，
  只用 `1-exp(-dt·40π)` 一阶低通 + `kp_floor` 增益调度。

它赢在**三件架构上的事**：

1. **压枪是独立的前馈子系统 + 独立线程**：可录制的 `{rel_x, rel_y, delay_ms}` 弹道表，
   按自己的时基回放，既不进误差环也不受检测帧率限制。
   → 后坐力这个**持续外力**被前馈直接抵消，而不是"等误差攒起来再追"。
   本方**完全没有这个模块**，压枪的稳态误差被算出来就是 ≈12 px（§2.3）。
2. **判定与控制吃的是未滤波信号，且没有死区**：命中判定用预测后的框心，
   控制用未滤波的框心/瞄点，末段靠 `kp_floor` 增益调度而不是死区。
   → 末段不丢精度，也不需要在精度与稳定之间二选一。
3. **状态跨帧持有**：速度估计带采样窗、积分有 `i_box_lost_hold_ms`（20 ms）宽限、
   控制器不因身份重锁而复位。
   → 没有"每秒被打断 8 次"的问题。

本方现役控制器（时间归一化的 `u = dt·Kp·[e + Ki∫e + Kd·d]` + 在线估 `k̂`）**形式是对的、前提更干净**，
输在**传感器与执行器上挂了几个静默的开关**（`anchor_filter_ms = 0` 让 X 轴速度恒为 0、
5 px 死区、换目标清积分与前馈）、**扳机判定用了两个口径不一致的慢变量**，
以及**根本没有压枪模块**。

修 §7 的 P0 五项 + 补后坐力模块，这三处手感的差距就能收掉大部分。
