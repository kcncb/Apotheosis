# 自动调参 agent (靶场模式)

> 2026-09-14 新增。让大模型根据**真实运行日志**自动整定 PID 参数。
> 同日两次改版: ①从"一个开关一直连调"改成 **模式选择 + 开始/结束, 一次一轮**;
> ②采样边界从"按住瞄准热键"改成 **两次按钮点击之间的日志**。

## 1. 这是什么

一个**按次触发的调参器**: 你点「开始采样」, 正常去打一段, 点「结束并调一轮」——
它把**这两次点击之间**的真实运行日志算成指标, 交给大模型判断该往哪调, 然后把
参数**安全地**写回去。**一次只调一轮。**

```
靶场: 选模式 → 点「开始采样」   ← 在日志上打起始标记
        ↓
  你去打(静止靶 / 动态靶 / 甩枪 / 跟枪, 随你)
        ↓
  点「结束并调一轮」            ← 打结束标记
        ↓
  取两条标记之间的全部日志 → 判可用性 → 算指标
             → 问 LLM → 夹取 → 写参数 → 生效
        ↓
  你自己去打几枪、跟几下, 用体感判断这轮变好还是变坏
        ↓
  觉得还没到位 → 再点「开始采样」(模式可以换)   觉得可以了 → 停手, 参数就留着
```

### 1.1 为什么是"一次一轮"而不是自动连调

★★ 这是**人的节奏**, 不是机器的节奏。三个理由:

1. **连调十轮你分不清是哪一轮起的作用。** 每一轮改的都是同一组参数的叠加,
   最后你只有一个"总共变好了/变坏了"的印象, 无法归因。
2. **中间几轮的数据本身是脏的。** 你刚被改了参数, 手感还没适应 —— 那几拍
   你打出来的动作是"在适应新参数", 不是你的稳定水平。拿它做判断是错的。
3. **判断标准是你的体感。** 数字只能告诉你"误差中位小了 0.3px"; 只有你知道
   这一枪到底是不是更舒服。所以必须留出"你打几枪"的时间。

所以界面上**没有**自动循环、没有"两轮间隔"旋钮 —— 那些都被删掉了。

### 1.2 为什么采样边界是"两次按钮点击"(而不是按住热键)

★★ 这是**实测教出来的**。第一版按"按住瞄准热键"切段, 并配了一条判据
"中途换目标必须为 0"。结果用户的实际反馈是: **一直提示中途换了目标。**

查下去发现是判据读错了量。`Sample::switched` 来自 `boss_aim.cpp`:

```cpp
out.target_switched = out.motion_suppressed && anchor_jump >= 25.0f;
```

它的真实含义是 **"瞄点跳变 ≥25px"**, 也就是**玩家在甩枪** —— 不是"换了目标"。
正常跟枪里每次甩都触发, 于是几乎每一段都被判成脏数据。

> ★ **教训: 判据本身比被测现象更容易出错。**
> 凡是要拦人的门限, 都得先问"它读的那个量, 语义到底是什么",
> 而不是"名字看起来像什么"。这一版据此把判据压到最少 —— 只留真正会影响
> 统计量的那几条。

现在改成: 点「开始采样」记下当前日志位置, 点「结束」记下终点, 取两者之间。
这样做还有两个额外好处:

- **不依赖任何引擎信号** —— agent 层不用读热键状态、不用 hooks, 能在纯逻辑
  测试里独立编译和验证;
- **不会误触发** —— "我按了开始, 现在开始算"是一个不需要任何解释的约定。

### 1.3 三种模式

| 模式 | 你做什么 | 判据侧重 | 给模型的额外输入 |
|---|---|---|---|
| 1. 静态目标调参 | 往靶子上甩几次、再停住不动 | 首次到位时间、过冲峰值、稳态残差、翻转率 | — |
| 2. 动态目标调参 | 去追一个横移/走位的目标 | 跟随残差中位/p90、机动后重新咬合、有无振荡 | 目标运动特征(尺寸离散度) |
| 3. 体感调参 | 正常打 + **用文字写下你的感受** | **以你的描述为主证据**, 日志数字为佐证 | **你的原话** |

★★ 三个模式的**数据来源完全相同** —— 都是"两次按钮点击之间的日志"。
区别只在: ①判断这段数据配不配这个用途; ②给模型什么解读指令。

★★ **动态模式下靶子怎么动没有固定要求。** 不需要你按某种轨迹走位, agent 会
从日志里自己分析这段运动(速度/方向变化/尺寸变化), 你按平时实战的方式追就行。

★★ 为什么"体感"要以用户的话为主证据: 数字测的是"准星离瞄点多远", 测不到
"这个跟枪手感对不对"。你说"抖"但翻转率很低时, 更可能是检测层面在抖, 或者
你说的"抖"其实指别的现象 —— 无论哪种, **你感受到的不舒服是真实的**, 值得调。

## 2. 为什么只用真实日志, 不用仿真

仿真台 (`tests/aim_acceptance_test.cpp`) 需要两个**假设值**: 每计数多少像素
(`k̂`)、以及各种延迟。而:

- `k̂` 是**游戏机的属性**, 双机架构下**无法测量** (两条反推路径均已实测证伪,
  见 `docs/aimmagic-comparison.md` §6.7)。真实游戏有多款, 每款都不同。
- 延迟随采集卡/游戏/分辨率变化。

所以仿真结论**不能直接搬到实机**。而 agent 吃的是**真实运行日志** ——
延迟、`k̂`、检测噪声全都隐含在里面, 一个假设值都不需要。

> 测试台的作用是**摸架构的能力上界**(提示"最好的情况大概什么样"),
> 不是给出可直接使用的参数。实机参数只能来自真实数据 —— 这就是本模块存在的理由。

## 4. 为什么写回要走 live_tune 而不是直接改内存

程序里**已经有**一条完全正确的重载路径 (`ConfigProfiles::load` 里的
`config.loadConfig()` + `runtime_config::publish()` + `syncFromRuntime()`),
`live_tune` 就是它的触发器。

自己再写一套"直接改 config 结构再 publish"会有**两份真相**:
界面上的输入框不会跟着变, 用户看到的参数和实际在跑的不一致 ——
这正是 `CLAUDE.md` 里记过的「配置文件里是 100, 实际在跑 20」那类事故。

走 live_tune 还免费获得它的**内容体检**: 半截文件 / 关键键缺失会被拒绝,
不会把默认值悄悄写进去 (那个坑见 `live_tune.cpp` 步骤 0 的注释)。

## 5. 安全设计

### 5.1 三层防护, 全部独立于 LLM

| 层 | 规则 | 为什么 |
|---|---|---|
| **单步幅度** | 每次改动 ≤ ±20% | 防止一拍把 Kp 从 35 跳到 200。迭代十几次也能跨一个数量级 |
| **beta 不对称** | 上调 ≤ ±10%, 下调 ±20% | §4.3: 补**过头**会正反馈发散, 补**不足**只是回到原来的延迟 |
| **绝对值域** | 与 UI spinbox 范围一致 | 免得出现"界面上显示不出来的值"这种诡异状态 |

**NaN / Inf 一律回落到原值** —— 模型给出垃圾值时参数不动。

### 5.2 自动回滚 (不问模型)

满足任一条件直接退回上一组**已知可用**的参数, 且**本轮不请求模型**:

| 条件 | 判据 |
|---|---|
| 发散 | 尾段(时间上的后 25%)误差中位 > 前 25% 的 3 倍且 > 5px, 或 `err_max > 500px` |
| 自持抖动 | 下发 ≥ 40 次且符号翻转率 ≥ 85% |
| 明显变差 | 本轮 p90 > 上轮 p90 × 1.3 且 > 1px |

> ★ 回滚要求"**明显**变差"才触发: 实机数据噪声大, 一点点波动就回滚会让 agent
> 永远在原地打转。

### 5.3 会话语义 / 数据干净度

采集是一个**会话**: 点「开始」打开, 点「结束」关闭并立刻出一轮结果。
会话没开时**不收样本、不写参数** —— 靶场外的正常使用完全不受影响。

退出程序时 (`aboutToQuit`) 删掉 `live_tune.enable` 哨兵, 不留一个能改参数的
活动入口。★ 会话本身不需要显式取消: 它只是个区间标记, 没有后台线程 ——
没点「结束」就没发过请求、也没改过参数。

★★ **一次运行属于哪个模式, 在点「结束」那一刻定稿。** 采样中途不允许改模式
(界面会把下拉框禁用), 否则同一段数据会被一半按静态、一半按动态解读。

#### 5.3.1 采样边界: 两次按钮点击之间的日志

点「开始采样」时记下**当前日志位置**(`SampleBuffer::pushed()`, 一个单调递增的
绝对序号)作为起点; 点「结束」时记下终点, 取 `[起点, 终点)` 之间的全部样本。

★★ **为什么不按"按住瞄准热键"切段**: 见 §1.2 —— 那条路配套的判据读错了
`target_switched` 的语义, 把玩家甩枪当成了换靶, 几乎每一段都被拒。
现在这条路不读任何引擎信号, 也就没有可被误触发的状态。

★★ **段的切分用【绝对序号】而不是缓冲区下标。** `push()` 返回的序号单调递增、
不因淘汰而变。用下标的话, 用户采样超过缓冲区容量(约 68 秒)之后起点会被挤掉,
切出来的段就不是"开始到结束"了 —— 而且这种错误**不会报错**, 只会让指标悄悄
变得不准。用绝对序号时, `range()` 会把已淘汰的部分裁掉(不报错), 剩下的数据
仍然可用, 够不够交给下面的样本数判据决定。

#### 5.3.1b ★ "点了开始却收到 0 条" —— 一个哨兵值被当成重置用

改到按钮划界之后, 用户实测报"一直显示这段数据只有 0 条"。根因不在采样逻辑,
而在**两层交界的那个状态变量**上:

`Runtime::begin_session()` 里曾经有一行 `last_seq_ = 0;`。
而 `feed_from_chainlog()` 用 **0 当"尚未初始化"的哨兵**:

```cpp
if (last_seq_ == 0)
{
    last_seq_ = seq - total;   // 跳到"当前缓冲最旧一条"
    ...
}
```

它的用意是"第一次接入时不要把历史全灌进来"。但点「开始」把它归零之后,
下一次 feed 会认为自己是**第一次接入**, 于是把起点重设到*当前最旧一条*、
同时把 `seq` 赋成同一个值 —— 循环 `for (i = last_seq_; i < seq; ++i)`
**一条都不跑**。结果就是: 点「开始」之后永远采不到样本。

> ★ **教训: 一个变量如果有"哨兵值", 就不要拿它当"重置"用。**
> 重置和未初始化是两件不同的事, 复用同一个值会让"重新开始"被误读成
> "第一次开始"。修法是**根本不重置它** —— `last_seq_` 本来就一直指向
> "已消费到哪一条", 而点「开始」只需要让 tuner 在*当前绝对序号*上打个
> 起点标记, 两者互不干扰。

★★ **这个 bug 只测 agent 那一层是抓不到的** —— `AutoTuner` 自己完全正确,
它只负责"在 pushed() 上打标记"。问题出在 `Runtime` 喂数据的那一侧, 所以
回归必须把**真实的 Runtime + 真实的 chainlog** 接起来跑。`tests/CMakeLists.txt`
里 `autotune_test` 因此追加了 `autotune_runtime.cpp`(该层不依赖 Qt, config
读写是通过 `RuntimeHooks` 注入的函数指针)。回归在 `tests/autotune_test.cpp`
§[13]: 点开始 → 喂 200 条 → **断言收到 200 条**(旧代码恒为 0), 并单独验证
第二次采样同样有效(哨兵 bug 的另一个后果是"第二次点开始也收不到")。

#### 5.3.2 可用性硬判据 (`judge_segment`, 独立于 LLM)

不满足就**不发请求**, 直接把中文原因显示给用户, 让他重采。

★★ 这一组判据的原则: **只挡会让统计量失真的事, 不挡"用户的动作"。**
凡是"我觉得这样不好"但实际不影响统计量的, 一律不拦 —— 拦了只会让用户
反复重采。(上一版就是在这里翻车的, 见 §1.2。)

| 判据 | 门限 | 为什么 |
|---|---|---|
| 样本数 | ≥ 60 条 | 少了算不出可信分位数 |
| 时长 | ≥ 0.8 秒 | 短于此基本没有稳态段 |
| 有效框高 | 必须 > 0 | 没有框高就说明这段压根没有检测 |
| 覆盖率 | ≥ 50% | 数据太断续, 指标不可信 |
| 野值跳变(>40px) | ≤ 12 (+1/200 条) | 检测框跳到无关位置会污染误差统计 |
| 模式错配(仅静态模式) | 尺寸离散度 ≤ 0.60 | 选静态但目标明显在远近变化 → 提示改用动态模式 |

#### 5.3.3 覆盖率是怎么算的 (★ 两次算错的教训)

**定义**: `coverage = 正常间隔的样本数 ÷ 总样本数`,
其中"正常间隔" = `dt_ms ≤ 中位数 × 4`。

为什么要这么绕, 而不是简单地"实际条数 ÷ 应有条数"? 因为**后者算错过两次**,
而且两次都是同一个毛病: **用一个可能错的模型去推测"本该有多少条"**。

第一版公式是 `n ÷ (跨度 ÷ 平均dt)`, 有两个缺陷:

1. **分母把"程序没在跑"的死时间也算进去了。** 实测用户日志里有
   9.5s / 9.9s / 12s / 18s / 29.6s 的空洞(那段时间瞄准循环没有输出帧),
   跨度除以平均 dt 就把这些死时间算成了"本该有的样本数"。结果: 4454 条
   **零丢帧**的正常数据被判成 **31.9%**, 每段都过不了门限。
   用户侧的现象就是 —— **"为什么会覆盖率一直不够"**。
2. **平均 dt 会偏大。** 实测 `mean(dt_ms)=9.26ms` 而典型步进只有 `8.3ms`
   (少数慢帧把均值拉高了), 所以即使一段完全连续, 算出来也是 **111%**
   而不是 100% —— 这个量域上就不对。

更根本的问题是: `dt_ms` 是引擎自己报的**每拍间隔**, 它本来就记录了"这一拍
之前空了多久" —— **直接看它就够了, 根本不需要推测**。

> ★ 教训: 凡是"算一个比值"的判据, 先问分母是怎么来的。
> 如果分母是推出来的(而不是量出来的), 那个模型错了就会表现成
> "明明数据没问题却一直告警", 而且**不会报错**, 只会静默地给出错误结论。

**回归**: `tests/autotune_test.cpp` §[12] —— 走真实代码路径
(`begin_session → push → end_session`), 钉住三个数:
连续段 = 100%(不是 111%)、一次 30 秒断档只掉 ~0.25%(旧公式掉到 20%)、
每 5 条断一次则明显下降(门限没有形同虚设)。

> ★ **甩枪不算脏数据。** 玩家在采样期间的正常瞄准动作(甩枪/微调/跟随)会
> 带来大的误差峰值, 那是真实操作的一部分, 不是噪声。提示词里也明确告诉了
> 模型这一点, 让它看**稳态段**的残差而不是全程峰值。
>
> ★ **覆盖率门限故意放得松**(旧版 0.75 → 现在 0.50): 用户中途松手、丢一下
> 目标都是正常的, 只要还有足够多的有效样本, 指标就仍然可信。

### 5.4 一键回退

「恢复最初参数」退回**第一次点「开始」之前**的那一组。

> ★ 是"第一次", 不是"上一次" —— 连调几轮之后回退会一路退回原点。
> 这是有意的: 需要一个确定无疑的安全落点, 而不是在几个中间态之间来回跳。

## 6. 一个必须知道的陷阱: 残差小 ≠ 不抖动

**误差中位可以只有 0.2px, 同时每拍在下发 ±1 计数的抖动。**

这是任务书 §5 描述的量化陷阱。光看残差完全区分不出来, 所以指标里
**单独有「翻转率」**, 并且它有独立的回滚判据。

日志实证: Kp=100 时 43~54% 的帧在下发 ±1、符号翻转 79%, 而框自身逐帧变化
中位仅 0.06px (**不是检测噪声**)。

> agent 的提示词里明确写了这条, 并要求"翻转率高 → **降低** Kp"。

## 7. 指标定义

全部在 `autotune_metrics.h`, 只测**可判定**的性质 (`tests/autotune_test.cpp`)。

| 指标 | 定义 | 说明 |
|---|---|---|
| `err_median` / `p90` / `p99` / `max` / `rms` | 误差幅值 `hypot(ex,ey)` 的分位数 | 用原始误差 `ex/ey`, 不是扣完前馈的 `eux/euy` |
| `overshoot_x/y` | **误差反号后**能达到的最大幅值 | ★ 只统计反号样本, 否则"目标刚出现时的大误差"会被当成过冲。两个方向都出现过才算"有反号" |
| `flip_ratio` | 指令符号翻转 / 非零下发 | ★ 零指令**不计入**(否则"偶尔停一下"会被误判为抖动) |
| `divergent` | 尾段中位 > 头段 ×3 且 > 5px, 或 `err_max > 500` | ★ 必须按**时间顺序**取头尾 |
| `switches` / `suppressed` | 窗口内 `target_switched` / 运动压制次数 | ★ 只作参考。`target_switched` 的真实含义是"瞄点跳≥25px"(= 甩枪), **不是**"换了目标" —— 不要拿它当数据质量判据(见 §1.2) |

### 7.1 一个已修复的真 bug (值得记住)

发散判据最初写成: 先 `std::sort(mag)`, 再从排序后的数组取"前 25%"和"后 25%"。

**"前 25%"于是变成了"误差最小的 25%", "后 25%"变成"误差最大的 25%"** ——
时间顺序完全丢失。后果: **任何一段有大小起伏的正常收敛数据都被判成发散**
(最大的必然比最小的大 3 倍以上)。agent 会一直在原地回滚, 永远调不动。

修复: `mag` 保持时间顺序, 分位数走 `ordered` 副本。
回归见 `tests/autotune_test.cpp` 的 `[7] 发散判据 (时间顺序回归)`。

## 8. 参数表

| 参数 | 含义 | 范围 | 单步 | 备注 |
|---|---|---|---|---|
| `kp` | 比例增益 | 1 ~ 300 | ±20% | 计数/(像素·秒) |
| `ki` | 积分增益 | 0 ~ 20 | ±20% | 1/秒。★ 别低于 0.3, 否则匀速跟踪有永久滞后 |
| `kd` | 微分增益 | 0 ~ 0.30 | ±20% | 秒。延迟越大越该调大 |
| `beta` | 在途补偿强度 | 0 ~ 3.0 | 上调 ±10% | 无量纲。实测最优 1.6 附近, >3 必发散 |
| `psat_px` | P 项饱和阈值 | 0 ~ 1000 | ±20% | 0 = 关闭 |
| `scale_on` | 尺度调度开关 | 布尔 | — | |
| `scale_max` | 近处上限 | 1.0 ~ 2.0 | ±20% | ★ 与 Kp 相乘, 乘积 ≳52 会自激 |
| `scale_min` | 远处下限 | 0.30 ~ 1.00 | ±20% | 允许 < 1.0, 远处真的降增益 |

**基准框高（H₀）不在上表里** —— 它不是模型能"调"的参数, 而是 agent 从真实数据里
**学**出来的观测值。让 LLM 去猜"用户当时在多远"是荒谬的。

### 8.1 基准框高由用户手动设定
尺度调度的公式是 `s = clamp((h/H₀)^γ, s_min, s_max)`, 其中 `H₀` 的含义是
**"你的参数是在多远的距离上调出来的"**。

★★ **设基准与调参会话完全无关。** 界面上是一个按钮:

```
站到平时交战的典型距离上, 对着目标停一两秒
   ↓
按「以当前距离设为基准」
   ↓
取最近约 7 秒框高的中位数  →  写进配置(持久化)
```

★ **为什么不做成"跑调参时自动学"**(曾经那样做过, 已改掉):
那个设计有个明显漏洞 —— **不跑调参就永远学不到**, 尺度调度恒为中性,
用户会以为这功能坏了。而"参数是在哪个距离调的"跟"调参有没有在跑"
其实是**两件独立的事**:
- 你可能手动在某个距离调好了参数, 根本没跑过调参
- 你可能先调好参数, 才想起来还有这个功能
- 调参改的只是那几个 PID 值, 与"基准在哪"无关

而且旧实现在会话结束时才落盘, 直接关程序那一次采样就白采了。

★ **为什么用中位数**: 遮挡/出画会产生离群的小框, 均值会被拉偏。
★ **为什么至少要 30 条**: 不凭几帧就下结论 —— 数据不够时按钮会明确告诉你
"需要 30 条检测数据, 现在 N 条", 而不是静默用垃圾数据设个基准。
★ **为什么要求"停一两秒"**: 缓冲里是最近约 7 秒的框高。一边快速拉近拉远
一边按, 中位数反映的是那段移动过程, 不是你想当标准的那个距离。

**实现要点**: `Runtime::sample_target_height()` 用一个 `atomic<double>` 环形
数组(`kHeightRingSize = 900`, 120fps 下约 7.5 秒)。瞄准线程每帧写、UI 线程
按按钮读, **不加锁** —— 单槽读写本身原子, 最坏只是读到略过时的值, 而中位数
对个别样本的新旧完全不敏感。热路径上不做任何可能阻塞的事。

**发送给 LLM 的内容**: 指标摘要 + 当前参数 + **这一段数据的来历**
(按住热键时长 / 样本数 / 覆盖度 / 换目标次数 / 框高分位)。**不含画面**,
不含原始日志。

> ★ 为什么要把"这一段数据的来历"也发过去: 模型需要知道这段时间的用户意图是
> **持续追踪一个目标**, 它才会把误差解读成"跟随能力", 而不是"用户没在瞄"造成
> 的随机误差。数据干净度也是同理 —— 让模型自己知道它看到的数据有多可信。

## 9. 怎么用

1. **控制 → 自动调参** 页面。
2. 填 LLM 接口 (OpenAI 兼容):
   - DeepSeek: `https://api.deepseek.com` + `deepseek-chat`
   - 本地 ollama: `http://127.0.0.1:11434`, Key 留空
3. **点「测试连接」** —— 填完先测一次。
4. **选模式**:
   - **静态目标**: 往靶子上甩几次再停住
   - **动态目标**: 去追一个移动的靶(靶子怎么动无所谓)
   - **体感**: 还要在下面写一句你的感受(比如「跟枪拖后腿」)
4b. **选「改动幅度」** —— 见 §9.4。觉得改了半天没感觉就选**激进**。
5. **点「开始采样」**, 然后正常去打 —— **甩枪、跟枪、换目标都随意**。
   建议持续 **3~5 秒**以上。数据条数会实时显示在状态栏里。
   > ★ 如果你用的是**推理模型**(`deepseek-reasoner` / QwQ / 各种 thinking
   > 变体), 先把上面的**「最大输出」调到 4096 以上** —— 思考也占这个预算,
   > 太小会只剩思考、没有正文。见 §9.3。
6. **点「结束并调一轮」**(会等几秒, 光标变成等待形状)。
7. 看表格新增的那一行; **点任意一行**看那一轮的完整细节
   (数据来历 / 你的描述 / 指标 / 模型想要 vs 实际生效 / 夹取 / 模型原话)。
8. **去打几枪、跟几下**, 用体感判断这轮变好还是变坏。
9. 还想继续 → 回第 4 步(**可以换模式**: 比如先用动态调跟随, 再用体感微调手感)。
10. 不满意整体结果 → 点「恢复最初参数」。

### 9.1 什么时候会「没出结果」

表格里那一行会在「结果」列写明原因, 都是可以直接照着改的:

| 提示 | 怎么办 |
|---|---|
| 这一段数据太少 / 只有 N 条 | 点「开始」后多打一会儿(至少 1 秒, 建议 3~5 秒) |
| 这一段只有 N 秒 | 同上 —— 时间太短没有稳态段 |
| 没有有效的目标尺寸 | 识别没开或没框住目标; 确认锁到目标再采 |
| 数据不连续(连续样本只占 N%, 中间有 N 处断档) | 识别没在跑, 或采样期间切了程序/页面; 保持识别在跑重采 |
| 有 N 次位置突变 | 检测在跳, 检查识别质量 |
| 选「静态」但尺寸变化大 | 改用**动态目标**模式重采 |
| 体感模式需要你先写一句感受 | 在「你的感受」框里写一句 |
| 样本太少(32 条) | 同"太短" |
| **模型的思考过程把输出预算用光了** | 把「最大输出」调大(建议 4096+), 或换非推理模型。见 §9.3 |
| HTTP 401 / 404 / 429 / 5xx | 见 §9.2 的表 |

> ★ 这些都不是错误, 是**数据可用性把关**。宁可让你重采一次, 也不要拿一段
> 不可用的数据把参数调歪 —— 参数调歪的代价比多按一次按钮大得多。
>
> ★ 但判据是**故意留松**的: 甩枪、中途松手、偶尔丢一下目标、程序中途卡一下
> 都**不会**被拒。如果实机用起来还是觉得太严、老要重采, 把具体提示告诉我,
> 我按实际情况放宽。

### 9.2 「测试连接」按钮

真正发一次最小请求 (让它回一个 JSON), 验证**地址 / Key / 模型名**三件事都对。

**失败会告诉你下一步改什么**, 而不是只报"不通":

| 现象 | 提示 |
|---|---|
| 域名解析失败 | 地址拼错了? (WinHTTP 12007) |
| 无法连接 | 服务没起? 端口错了? 防火墙? (12029) |
| 请求超时 | 超时 (12002) |
| TLS/证书错误 | 本地 http 请勿用 https (12175) |
| HTTP 401 / 403 | API Key 无效或无权限 |
| HTTP 404 | **地址或模型名不对。检查接口地址是否多写了 `/v1`** |
| HTTP 429 | 触发限流 |
| HTTP 5xx | 服务端错误 |

★ 请求在**后台线程**发出 —— 超时最长 120 秒, 在 UI 线程上跑会让窗口假死。

★ 成功时还会**额外检查回答里有没有 JSON**: 如果模型不听话(不回 JSON),
调参时会解析失败, 这里会提前警告你。

★ 成功时也会**检查输出预算用得凶不凶**: 本次用量超过 `max_tokens` 的八成
就会警告。原因见 §9.3 —— **测试连接通过 ≠ 真调参能通过**。

**已实测验证的失败路径** (真发请求):
- 空配置 → 立刻返回, 不发起请求
- 不存在的域名 → `域名解析失败(地址拼错了?) (WinHTTP 12007)`
- 本地无服务的端口 → `无法连接(服务没起? 端口错了? 防火墙?) (WinHTTP 12029)`
- 真地址 + 无效 Key → `HTTP 401: Authentication Fails, ... is invalid`

### 9.4 ★ 「改动幅度」三档: 保守 / 平稳 / 激进

**为什么加这个。** 用户实测反馈: "试了两次显示已应用但是体感没什么变化"。
查下来三轮加起来 **Kp 只动了 10%、Ki 一动没动** —— 这个幅度体感上不可能有感觉。

根因是两处叠加:

| 位置 | 原来是什么 | 问题 |
|---|---|---|
| 提示词 | "幅度要克制 —— 宁可小步走稳, 不要大改" | 模型本来就保守, 再叮嘱它更不敢动 |
| 硬夹取 | 每轮最多 ±20% | 额度本身也小 |

更麻烦的是: 当参数**明显偏离**合理区间时(Ki=5.0 而默认是 1.0, 差 5 倍),
每轮 20% 的步子**永远走不到那里**。

**现在:** 界面上多了一个下拉框, 由你决定这一轮允许改多大。

| 档位 | 单轮上限 (Kp/Ki/Kd) | beta 上调上限 | 什么时候用 |
|---|---|---|---|
| 保守 | ±10% | +5% | 数据不太可信, 或只想微调 |
| **平稳**(默认) | ±20% | +10% | 默认档, 与原行为一致 |
| 激进 | ±50% | +20% | 当前参数明显不对, 想一次调到位 |

★★ **这个旋钮最关键的设计点是"两处必须一致"**: 提示词告诉模型"你最多能改
±50%", 而夹取只放 ±20% —— 用户就会看到"选了激进还是没变化"。
所以 `apply_limits()` 的额度直接取自同一个 `StepStyle`。

★★ **选激进不会让 AI 乱改。** 它仍然要按指标给方向, 只是不再畏手畏脚;
绝对值域的硬边界(kp ≤ 300 等)始终生效。**beta 的上调三档都额外收紧**
(5% / 10% / 20%) —— 因为 beta 补过头会正反馈发散, 与 Kp/Ki 性质不同。

★ 档位记进每一轮的历史里, 详情页会显示「改动幅度: 激进」—— 因为"改了多少"
和"结果如何"必须一起看才有意义。

**回归**: `tests/autotune_test.cpp` §[15] 钉住三档的额度、提示词差异、以及
"提示词里不再出现「幅度要克制」"; `tests/autotune_layout_test.cpp` 断言界面上
三档都在且写着正确百分比。

### 9.5 ★★★ 「显示已应用, 体感却没变化」—— 参数其实没生效 (2026-09-15 实测)

**现象.** 用户原话: "当前项目的自动调参不好用, 体感根本不明显"。

**根因不在模型调得少, 而在参数压根没进到控制器里。** 实机两处硬证据:

| 文件 | Kp | Ki | Kd |
|---|---|---|---|
| `configs/CF.ini` (active.txt 指着的方案) | **15.0** | **5.0** | 0.010 |
| `configs/live_tune.ini` (实际在跑的) | **6.2** | **3.3** | 0.024 |

而界面上一直显示「已应用」。

**链条**(时间戳来自 `live_tune_ack.txt`): 21:03 用户切换配置方案 → `CF.ini` 在
21:04 落盘 → autotune 在 21:05~21:09 连续调用 12 次 `live_tune.ini` 写入。
问题就出在这 12 次写入上:

```cpp
// runtime/live_tune.cpp  applyLiveFile()
config.loadConfig(path);      // ★ loadConfig() 会把 config_path 指到 path!
```

`Config::loadConfig()` 的第一件事就是 `config_path = <传进去的路径>`。于是调参
通道每应用一次, **落盘目标就被永久重定向到 `live_tune.ini`**。而 `ConfigBridge`
是靠 `saveConfig()` 落盘的, 它有这条规则:

```cpp
if (target == "config.ini" && !config_path.empty())
    target = config_path;          // -> live_tune.ini
```

结果: 界面上任何修改、以及退出时的 flush, **全都写进了 `live_tune.ini`**,
用户激活的方案 `CF.ini` 再也没被读过。用户手改 `CF.ini` 当然"没有任何效果"。

> ★ **教训: 一个有副作用的"读"函数, 调用方必须知道它会改全局状态。**
> `loadConfig()` 名字听起来是纯读取, 实际上同时改了"以后往哪写"。任何
> "读一份副本再应用"的调用方(live_tune / 调参 agent)都会踩到 —— 所以要
> **解析前存下、解析后还原**, 把副作用限制在那一次调用里。

**修了三处**:

1. **`live_tune.cpp`**: `loadConfig()` 前后保存/还原 `config_path`
   (新增 `Config::configPath()` / `setConfigPath()`) —— 副作用的根, 必须堵死。
2. **写回改为"验证生效"** (`autotune_hooks.cpp::write_and_verify`): 旧写法是
   **发出去就算成功**(saveConfig → 改名 → `return true`)。但"写到文件"和
   "运行时用上了"之间隔着轮询、内容体检、`loadConfig`、`publish` 四道关。
   现在只有**运行时快照真的变成新值**才算成功; 2 秒内没等到就返回 false, 并把
   **"想要 / 文件里 / 实际在跑"三个值**一起写进错误信息。
3. **`KnobsSetter` 带出错误** (`bool(const Knobs&, std::string& err)`): 原来
   只有一个 `false`。现在 `run_one_round` 在写回失败时把这一轮标成**失败**
   (而不是"已应用"), 界面弹出「这一轮没有生效」并附上底层原因。

> ★ **判据必须取"运行时那侧可观测的证据", 而不是"我们这边动作做完了"。**
> 这就是本次事故的全部教训 —— 旧代码每一步都做对了(写盘成功、原子改名、
> 体检通过), 唯独没有人去问一句"控制器现在到底在用哪个值"。

**回归**: `tests/autotune_test.cpp` §[16] —— 走**真实的 `run_one_round`**
(注入模型回答, 见 `set_reply_fn`), 断言"写盘成功但运行时不采用"时这一轮
**必须带错误**。★ 已做反向验证: 把判据退回成无视返回值, 该节 **3 项立刻变红**,
恢复后全绿 —— 否则不知道测试在测什么。

> ★ 之所以能测到这一段, 是因为把模型回答做成了可注入的 `ReplyFn`。
> 真正决定成败的判据在网络请求**之后**, 不注入就永远只能测周边小函数 ——
> 而"周边全绿、判据写错"恰恰是最危险的情形(第一次写这组测试时就是这样:
> 只测了 `set_` 的接线, 把 `run_one_round` 的判据改错, 测试依然全绿)。

**顺带一提**: 「已应用」现在按结果着色(绿=生效 / 黄=回滚 / 红=没生效),
失败会**弹窗**而不是只往表格里塞一行 —— 原来的失败形态是静默的, 静默的失败
会让人以为"这功能不好使", 而不是"这次没成, 再来一次"。

### 9.6 ★★★ 「一直没能真正生效!!」—— 界面把陈旧值整片灌了回去 (2026-09-15 二次排查)

**现象.** 修完 §9.5 之后用户反馈仍然「一直没能真正生效!!」。

**这次的证据在运行时日志里, 而且是一个"不对称"。** `chain_live.log` 的
`reason=pid_params` 事件(每档参数生效时记一条):

```
x=(kp=15.0) y=(kp=15.0)     <- 会话开始
x=(kp=30.0) y=(kp=15.0)     <- 调参改了, 只有 x 动
x=(kp=50.0) y=(kp=15.0)
x=(kp=60.0) y=(kp=15.0)     <- 一直到会话结束, y 永远是 15.0
```

**自动调参是同时写 x 和 y 的**(`write_knobs_to_config` 里两个轴赋同一个值),
所以"只有 x 变、y 永远不动"必然是**有人把 y 又盖回了旧值**。

**根因: `HotkeyPage::reloadFromRuntime()` 只重建了下拉, 没重读参数控件。**

```cpp
void HotkeyPage::reloadFromRuntime() { rebuildGroupCombo(); }   // 修复前
```

而本页的写回是**"控件当前值整片写回 config"**:

```cpp
hp.pidf_kp_x = m_pidfGain[0]->value();
hp.pidf_kp_y = m_pidfGain[1]->value();     // <- 陈旧控件值
```

于是形成一条静默的**陈旧值回灌**链路:

1. 自动调参改了配置 → 触发 `configLoaded`;
2. 本页收到信号只重建下拉, 六个瞄准参数 spinbox **仍显示旧值**;
3. 用户之后在本页改**任何**别的控件(视野/扳机/曲线…), 都会走
   `saveUiToCurrentProfile()`, 顺手把六个陈旧值整片写回去;
4. 参数被悄悄改回去 —— **不报错、不留痕**。

> ★ **教训: "整片写回"式的界面 + "外部会改配置"的机制放在一起时, 控件必须
> 在每次外部变更后重读。** 否则那个界面不是"显示", 而是一个随时会把旧值
> 灌回去的缓存。`saveUiToCurrentProfile` 这个写法本身就把"控件值"当成了
> 权威副本 —— 那要求**每一个**改 config 的入口都同步刷新控件。

**旁证(为什么只有这一页中招)**: `TargetPage` / `SessionPage` / `HardwarePage` /
`CrosshairPage` / `CapturePage` / `AiModelPage` / `DebugPage` **都**在
`configLoaded` 上重读控件, 只有 `HotkeyPage` 漏了 —— 而它第 87 行的注释还
写着"所有瞄准参数都要按新方案重建"。**注释描述的是意图, 代码做的是别的事。**

**修法**: `reloadFromRuntime()` 里追加 `reloadProfileFromConfig()`
(按当前档位调 `loadProfileToUi()`, 后者内部有 `m_loading` 守卫, 期间
`setValue` 触发的 `valueChanged` 不会反过来写回)。

**回归**: `tests/autotune_reload_test.cpp` —— 把这条链路的数据后果写下来:
①模拟"陈旧缓存整片写回"→ 断言参数确实被打回旧值(复现实机现象);
②模拟"重读之后写回"→ 断言不再污染; ③走真实 `Runtime` 写回路径断言
"调参确实同时写 x/y", 从而把日志里的不对称唯一地归因到界面回灌。

### 9.3 ★ 「测试连接成功, 但显示没 content」—— 推理模型的输出预算

**实测踩到的坑。** 现象是地址、Key、模型名都填对了, 测试连接也是绿的,
但真点「结束并调一轮」就报"响应里没有 content 字段"。

**根因: 推理模型的思考过程和正文共用同一个输出预算。**

带思维链的模型(`deepseek-reasoner`、QwQ、各种 `-thinking` 变体, 以及很多
网关自带的思考模式)会先产生一大段 `reasoning_content`, 而**推理 token 也
算在 `max_tokens` 里**。预算被思考吃光之后, 上游返回
`finish_reason: "length"` + `content: ""` —— 正文一个字都没有。

这在多个上游都被记录为已知失败模式, 不是本项目特有的问题。

**为什么"测试连接"却是好的** —— 这一点最容易让人误判:

| | 测试连接 | 真调参 |
|---|---|---|
| 提示词 | `请只回复一个 JSON: {"ok":true}` | 系统提示 + 指标 + 参数 + 数据来历 |
| 思考量 | 极小 | 大一个量级 |
| 结果 | 有正文, 绿灯 | 预算被思考吃光, 正文为空 |

**所以: 测试连接通过, 只证明"地址/Key/模型名"三件事对, 不证明"预算够"。**

**已做的三件事:**

1. **默认 `max_tokens` 从 800 提到 4096**(`LlmConfig::max_tokens`), 给"思考 +
   正文"都留余量。
2. **界面上加了「最大输出」输入框**(范围 256 ~ 32768), 你可以自己调大。
   ★ 这个字段会一起持久化, 也会一起推给 runtime —— 漏推它就会重现这个 bug。
3. **错误信息改成能定位问题的**: 以前只有一句"响应里没有 content 字段
   (模型可能只返回了 reasoning)", 现在会按情况给出**上游的实际证据**:

| 上游表现 | 我们说什么 |
|---|---|
| `finish_reason: "length"` | 「模型的思考过程把输出预算用光了, 正文被截断」+ 实际用掉的 token 数 + 让你去调「最大输出」 |
| 有 `reasoning_content`、没有正文 | 「模型只返回了思考内容」+ 思考字符数 |
| 完全不是 OpenAI 格式 | 把**响应原文开头一段**显示出来, 并提示检查模型名 |
| HTTP 4xx/5xx | 除了状态码, 还把上游 `error.message` 一并显示 |

> ★ **这次的教训**: 原来那句报错把"可能的两个原因"混在一句话里, 用户拿它
> 查不出所以然 —— 而真正的原因(预算被吃光)恰恰没被提到。
> **错误信息必须携带能定位问题的证据**(上游说了什么), 而不是只描述我们
> 这边的失败状态。

**回归**: `tests/autotune_test.cpp` §[14]。之所以能离线测, 是因为把响应解释
从 `chat_completion` 里拆成了公开的 `parse_completion_body(resp, http_status,
max_tokens)` —— 网络不可重复, 但"上游返回了这样的 JSON, 我们该怎么理解"
完全可以判定, 而出错的正是这一层。用例里放了**真实的响应体**(推理模型截断、
只有思考、非预期格式、401、空体、带转义引号)逐条断言诊断结论, 并钉住
"默认 `max_tokens` ≥ 4096"这条, 防止以后又被调回去。
